## 1. Правила приёмки

**P0** — критический путь демонстрации. Провал, пропуск без письменного waiver или «нестабильный» результат P0 блокирует переход к следующему этапу и демонстрацию.

Проверка считается выполненной только если:

1. она запущена на изолированной среде с зафиксированными версиями, датой/временем и seed;
2. проверен и успешный путь, и предусмотренный отказ;
3. сохранены доказательства: HTTP-код, строка БД/история, скриншот, лог или hash;
4. повторный запуск не создаёт дублей и не переписывает историю;
5. в отчёте явно указано, что было выполнено, а что пропущено.

**Пропуск не равен успеху.** `pytest`-skip, «ручная проверка не требуется», mock вместо inference и скрытая ошибка в UI фиксируются как «не выполнено», а не как «пройдено».

## 2. Тестовые роли и доступы

Для P0 используются четыре целевые роли v1: `admin`, `dispatcher`, `engineer`, `executor`. Источник истины — [API-контракты](../docs/architecture/api_contracts.md) и [архитектура](../docs/architecture/system_architecture.md).

| Роль | Тестовые аккаунты | Разрешено в P0 | Запрещено | Что проверяет |
|---|---|---|---|---|
| `admin` | `qa_admin` | Справочники, пользователи, site scope; чтение в доступных объектах | Приёмка работы, выполнение «в полях», назначение без роли dispatcher | P0-01, P0-02, P0-03 |
| `dispatcher` | `qa_dispatcher` | Импорт Excel, генерация плана, создание задания, назначение бригады, отмена `draft`/`assigned`, сравнение прогнозов | Приёмка/отклонение работы, выполнение работ, перенос обязательного срока, self-accept | P0-05–P0-12, P0-21 |
| `engineer` | `qa_engineer`, `qa_engineer_2` | Утверждение операции, чтение выполнения, приёмка/отклонение с причиной, просмотр прогнозов, резолюция по просрочке | Полевое выполнение, приёмка собственной работы; назначение — только если матрица будет расширена | P0-04, P0-08–P0-10, P0-16–P0-20 |
| `executor` | `qa_executor_1`, `qa_executor_2`, `qa_executor_unqualified` | Свои назначенные задания, старт, чек-лист, показания, фото, отправка отчёта | Назначение другим, изменение нормо-часов, приёмка, чужие задания | P0-13–P0-15, P0-18 |

Дополнительные аккаунты:

- `qa_engineer_executor` — роли `engineer` + `executor`; нужен для проверки запрета собственной приёмки.
- `qa_outsider_site_b` — пользователь Site B; нужен для проверки site scope.
- `qa_observer` — опциональный read-only аккаунт для доменного «Главного руководителя»; в v1 отдельной роли нет.

### 2.1. Соответствие доменным ролям

| Домен (`user_flows.md`) | Целевая роль v1 | Примечание |
|---|---|---|
| Главный руководитель | `qa_observer` (read-only) | Отдельной роли в v1 нет; если аккаунт используется, он не должен менять данные |
| Главный инженер | `engineer` + резолюция по просрочке | Отдельной роли в v1 нет; повышенные полномочия должны быть явно описаны в матрице прав |
| Инженер | `engineer` | Приёмка, отклонение, утверждение операции |
| Техник | `executor` | Выполнение и отправка отчёта |

**Расхождение, которое нельзя скрывать.** В доменном описании инженер назначает задачи, а в целевом API назначение выполняет `dispatcher`. Для P0 принят API-контракт. Если продукт решит иначе, нужно одновременно изменить матрицу прав, `ROLE_PERMISSIONS`, API-контракт и P0-02.

Текущий `ROLE_PERMISSIONS` в `backend/app/schemas/maintenance_api.py` — **черновой** и не содержит, например, отдельного `operation:approve` и `execution:review`. До реализации auth его нужно привести к согласованной матрице; иначе P0-02 блокируется.

### 2.2. Статусы

В тестах используются статусы API-контракта. Доменные и DB-названия — только как отображение:

| Домен | API v1 | Текущее поле БД | Комментарий |
|---|---|---|---|
| `created` | `draft` | `draft` | Совпадает |
| `assigned` | `assigned` | `assigned` | Совпадает |
| `in_progress` | `in_progress` | `in_progress` | Совпадает |
| `on_review` | `submitted` | `in_review` | Требуется mapping-тест |
| `returned` | `rework_required` | `rework` | Требуется mapping-тест |
| `completed` | `accepted` | `completed` | Требуется mapping-тест |
| `is_overdue` | отдельный boolean | отдельного поля в текущей БД нет | Не статус; должен вычисляться/храниться отдельно |

Пока mapping не согласован, API-тесты проверяют статусы API, а SQL-тесты — состояния БД. Смешивать их в одном ожидаемом результате нельзя.

## 6. Настоящие результаты моделей

**Сейчас настоящих результатов моделей нет.** В репозитории отсутствуют обученная модель прогноза, веса CLIP, runtime inference и размеченный тестовый набор. Всё, что проверено, — это формат DTO и fixtures.

| Метод | Что реально есть | Метрики | Корректное утверждение на 29.10.2026 |
|---|---|---|---|
| Алгоритмический прогноз | Только fixtures и проектные правила | Нет | Реализации нет; даты из примеров — не результат runtime |
| AI-прогноз (RandomForest) | Нет модели, датасета, feature schema, seed | Нет | `unavailable`/`MODEL_NOT_READY`; качество не заявляется |
| Фотоанализ (CLIP) | Нет весов и inference | Нет | `unavailable`/не выполнено; точность не заявляется |
| Оркестратор | Только fixtures с общим snapshot | Нет | Контракт проверен; политика в runtime не исполнялась |

Fixture `synthetic_demo` **не является** результатом модели. Валидатор подтверждает лишь то, что примеры соответствуют схеме, ссылкам и выбранной дате. Записанный ответ модели, выданный за живой inference, запрещён.

Когда модели появятся, к каждому результату должны прикладываться:

- `model_ref`, версия кода/весов, commit или SHA-256 артефакта;
- hash датасета, границы train/test по времени и оборудованию, seed;
- target и baseline на той же выборке;
- MAE в днях, доля опозданий, покрытие, число тестовых событий;
- время inference и пиковая память на демонстрационной машине;
- для CLIP: hash набора кадров, prompt set, версия модели, примеры `uncertain`/`not_verifiable`/`unavailable`;
- имя и дата того, кто проверил метрики.

Без этих данных допустимо показывать только `unavailable` и ограничения, но нельзя называть модель «работающей» или «точной».

## 7. Ограничения демонстрационных данных

### Набор A — данные заказчика

- Исходный файл: `docs/customer/techical_service_schedule.xlsx`; SHA-256 `8608662fe5d66519e990f65d1377f3fad32c1e6d29d6524dc4aeed24cd079957`.
- Подтверждены шесть операций, ТО1/ТО2, периодичность, численность и числа норм; в октябре — **93 ежедневные отметки** (3 × 31).
- Год в Excel не указан. Октябрь **2026** — демонстрационное допущение, а не подтверждение заказчика.
- Даты ТО2 (1.4–1.6) в октябре пусты; календарь ТО2 должен показывать «даты требуют уточнения», а не выдуманное распределение.
- Нормы 60/48/30 не определены как человеко-часы, часы бригады или годовой бюджет. `planning_duration_minutes` остаётся пустым до подтверждения.
- Нет истории выполнения, отказов и завершённых работ; нельзя создавать фиктивные факты за 1–25 октября.
- Нет квалификаций и допусков; проверка допусков — демонстрационное допущение, а не данные Excel.
- Импорт имеет статус `draft`; реальные назначения по неуточнённой длительности запрещены.

### Набор B — `synthetic_demo`

- Отдельное оборудование и операция очистки, пять явно заданных дат, `allowed_lead_days=6`, бригада 2 человека, подтверждённая длительность 60 минут.
- Синтетические эксплуатационные события и разрешённые тестовые фото. Полный сквозной процесс проходит только на B.
- Все JSON-примеры в `docs/architecture/contracts/examples.json` имеют `data_origin=synthetic_demo`; UUID, hash и фото — формат, а не существующие ресурсы.
- Синтетический график нельзя подписывать как утверждённый заказчиком; метка `synthetic_demo` обязательна в API, UI, отчётах и на экране сравнения.

### Общие правила

- Все календарные даты — в timezone Site (`Asia/Yekaterinburg` для демонстрации); naive timestamps отклоняются.
- На экране и в ответах API должны быть различимы: `customer`, `synthetic_demo`, `unavailable`, `needs_input`.
- Нельзя выдавать preview A за утверждённый график, а fixtures — за загруженные данные или живой inference.

## 8. Требования к отсутствию дублей заданий

Дубли запрещены на четырёх уровнях: генерация, создание задания, повторная команда и приёмка.

| Уровень | Инвариант | Как проверяется |
|---|---|---|
| Генерация вхождения | Ключ идемпотентности: `(site_id, binding_id, rule_version_id, occurrence_date, sequence_no)`; для несвязанного правила — без `binding_id` | Повторный `POST /plans/generate` возвращает те же вхождения; в БД нет новой строки |
| `schedule_entries` | UNIQUE по `(site_id, schedule_plan_id, binding_id, planned_date, sequence_no)` и отдельный вариант для несвязанного правила | SQL 001/002/003; повторная вставка отклоняется |
| `work_orders` | `UNIQUE (site_id, schedule_entry_id)` — не более одного задания на вхождение | P0-11; повторный `POST /tasks` не создаёт вторую строку |
| `work_assignments` | `UNIQUE (site_id, work_order_id, user_id)` | P0-12; повторное назначение того же исполнителя отклоняется |
| `work_reports` | `UNIQUE (site_id, work_order_id, revision_no)` | P0-15/P0-18; повторная сдача не создаёт вторую ревизию |
| `evidence_files` | Уникальный `storage_key`; файл относится к одной попытке | P0-14; повторная загрузка не создаёт второй файл |
| Приёмка | Одно принятое решение и одно принятое событие на попытку/задание; повторная приёмка запрещена | P0-17; проверка `accepted` + истории + аудита |
| HTTP-команды | `Idempotency-Key` учитывает principal и маршрут; тот же payload возвращает прежний результат, другой payload — 409 `IDEMPOTENCY_CONFLICT` | P0-21; повтор и параллельный запрос |

**Нюанс `sequence_no`.** Разные `sequence_no` — это законные разные вхождения в один день, а не дубль. Генератор обязан **повторно использовать** тот же `sequence_no` при retry. Если бизнес-правило требует одно вхождение в день, `sequence_no` фиксируется равным 1, и это проверяется отдельно.

**UI не заменяет сервер.** Двойной клик и повтор после таймаута должны быть безопасны на backend; блокировка кнопки — только дополнительная защита. Повтор после `503` выполняется с тем же `Idempotency-Key`, иначе возможен дубль.
