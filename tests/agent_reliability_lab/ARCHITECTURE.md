# Путь запроса и проверяемые границы

Штатный `POST /api/v1/assistant/conversations/{id}/messages` проверяет сессию, владелец чата, текущий объект и роль. Маршрут сохраняет выбранную версию графа и снапшот модели на обращение. `run_turn` получает право обработки записью `worker_claimed_at`. v3 выполняет `plan → next_requirement → read/selection/projection/task/action → quality_gate → compose` и хранит контрольные точки в схеме `assistant_checkpoints`.

План может быть детерминированным либо использовать модель для роутинга, семантического разбора, ревью требований и выбора инструментов. Чтения проходят через тот же серверный RBAC, что и обычные API. Предложение изменяющего действия ожидает решение владельца в отдельном графе и повторно проверяет полномочия, отпечаток и ревизию. Предметные данные, реестр требований и доказательства сохраняются в закрытом `assistant_turns.workflow`. Сессия, заголовки и поля с секретами передаются в runtime и входят в другой контур хранения.

Явная ссылка на прежнее сравнение извлекает последний валидированный результат того же владельца, объекта и роли. Источники для продолжения читаются заново. Запрошенная дата участвует в вычислении просрочки и актуальности регламента. Для выбора из равных результатов используется UUID. События диагностики связывают идентификаторы запуска и узла с метаданными модели, инструментов, токенов и завершения.

Стенд пользуется реальным FastAPI, PostgreSQL и конфигурацией модели. Подготовка данных и oracle подключаются к отдельной тестовой БД. Запросы пользователя, выдача, планы и подтверждения проходят HTTP-обработчики. Oracle считает ожидаемые данные по предметным таблицам и не вызывает агентные transports. Трассы каждого эпизода включают узлы, факт выполнения через v3, модель, состояние требований, выбранные сущности, метрики и предметные хеши до и после сценария. Подробнее о контрактах приложения можно прочитать в [документации Agent v3](../../docs/architecture/assistant-architecture-v3.md).
