# TL03 и последующие изменения физической схемы

Реализованная база: SQL 001–008. Минимальные ограничения TL03 находятся в 004,
runtime — в 005, назначения — в 006, генерация — в 007, сотрудники/смены — в 008.
Это описание текущего хранения, а не список ожидающих согласования решений.

- Норма хранится десятичным значением с тремя знаками; единица и отдельная
  длительность входят в параметры конкретного правила и снимок задания.
- Операция имеет устойчивый ID, её исполняемая версия привязана к правилу.
  Инструкция, чек-лист и требования фиксируются в новой версии.
- Календарное вхождение связано с binding и точным оборудованием; создание
  work order, двух прогнозов, решения и idempotency response атомарно.
- Два метода используют одинаковый полный ForecastSnapshot и hash. Канонические
  результаты и решение сохраняются независимо от выбранного метода.
- Попытки исполнения, фото и решения приёмки сохраняются отдельно; прежние
  назначения не удаляются при переназначении или отмене.
- Регулярные смены используют общую календарную модель. Срок работы сотрудника,
  квалификации, отсутствие и занятость учитываются при подборе и подтверждении.

Сопоставление всех runtime-сущностей: [dto_db_mapping](../architecture/dto_db_mapping.md).
Изменения схемы вносятся очередной миграцией; применённые файлы не редактируются.
Новая база и upgrade с данными проверяются `scripts/verify.py --browser`.
Рабочая БД не используется для разрушающих тестов. У SQL-администратора остаётся
прямой доступ; запреты HTTP-сервиса не заявляются immutable-триггерами всего каталога.
