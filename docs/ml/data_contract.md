# Данные для рекомендации срока ТО

## Граница данных

Источник регламентов — [разбор Excel](../architecture/customer_schedule_analysis.md): 1.1–1.3 — ТО1 ежедневно, по одному работнику и числовой норме 1; 1.4 — ТО2 пять раз в год, два работника, норма 60; 1.5 и 1.6 — ТО2 раз в квартал, один работник, нормы 48 и 30. Значение нормо-часов и его связь с длительностью требуют подтверждения заказчика. Частота 5/год и квартал не задают конкретные даты. Плановые отметки не являются фактами ТО, отказами или результатами измерений.

Excel не содержит историю отказов и аварий, диагностические измерения и их тренды, наработку, деградацию, замечания, подтверждённые факты потребности в обслуживании. Для обучаемого прогноза нужны датированные события и их исходы, идентификация оборудования и режимов эксплуатации, единицы и качество измерений, история счётчиков и их сбросов, а также достаточно независимых наблюдений и отдельная временная проверка на реальных данных. Определение целевого события и горизонт прогноза необходимо согласовать с инженером. Количественную точность до такой проверки заявлять нельзя.

## Контракт состояния v1

`ml_service.app.forecast.api.invoke` принимает JSON `ConditionRequest`; `ml_service.app.forecast.condition.Recommendation.model_json_schema()` выдаёт JSON Schema ответа. Примеры — [forecast_examples.json](forecast_examples.json). Время с часовым поясом, наблюдения после `as_of`, нечисловая наработка и неизвестные поля проверяются Pydantic. История, замечания, наработка и измерения необязательны: отсутствие не означает нормальное состояние. Измерения не сравниваются с порогами без согласованных единиц и нормативов. `risk_level` — только отражение указанной человеком критичности замечаний, а не вероятность отказа; `unknown` не означает низкий риск.

При неполном наборе возвращается `insufficient_data`; при наличии истории, наработки и хотя бы одного замечания или измерения — `unavailable`, пока пригодная модель не подтверждена. `data_quality.sufficient` означает только наличие этих полей, а не статистическую пригодность. Дата отсутствует в обоих случаях; `uncertainty` сообщает, что точность не оценена. Клиент может передать поставщика результата явно; ошибки JSON, структуры, исключение и истечение времени ожидания возвращаются отдельно. Время ожидания не останавливает выполняющийся поток поставщика: внешний сервис должен иметь собственный таймаут и ограничение ресурсов.

## Связь с ALG и backend

Общий `maintenance-0.1` описан в [схемах backend](../../backend/app/schemas/maintenance.py). Вызов `predict_condition_for_snapshot(snapshot, condition=None)` из `ml_service.app.forecast.backend_adapter` принимает `ForecastSnapshot` и возвращает `ForecastResult(method="ai")` с теми же идентификаторами и хешем снимка, которые использует ALG. Опциональный `ConditionRequest` передаёт замечания и измерения: его оборудование, происхождение и `as_of` должны совпадать со снимком. Без дополнения адаптер извлекает принятые события и наработку из снимка. Прогноз срока для заказчика недоступен; регламентная дата не копируется в `recommended_date`. Внимание: DTO не содержит отдельных структур качества и риска, поэтому адаптер выдаёт только ограниченные признаки в `warnings`, а полный `Recommendation` доступен через отдельный контракт состояния. Эквивалентность структур DTO проверяется тестами; действующий интегрированный оркестратор в ветке отсутствует, и согласование с владельцами ALG/BE ещё необходимо.

Демонстрационная модель обучена только на искусственно сгенерированной цели, отмечена `synthetic_demo`; разброс деревьев — не калиброванный доверительный интервал. Метрики на синтетике не измеряют качество на заказчике. Синтетика не должна автоматически применяться к данным заказчика. Регламентный срок определяет ALG, и рекомендация состояния не должна подменять или переносить обязательный срок.
