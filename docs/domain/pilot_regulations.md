> **Уточнение ALG01, 31.10.2026.** Ниже сохранён материал аналитика с исходными
> числами и прежними демонстрационными вариантами. Исполняемые правила теперь
> зафиксированы в [scheduling_rules.md](../algorithms/scheduling_rules.md).
> Предложения шага 73 дня, автоматического переноса выходных и первого ТО в день
> ввода не приняты генератором ALG02. `confirmed=true` в старой таблице подтверждает
> распознавание частоты, но не утверждение basis/anchor, длительности или дат заказчиком.
> Для исполнения нужен полный подтверждённый `RecurrenceRule`.

## 2. Статус подтверждения данных (Что подтверждено, а что требует уточнения)

* **Подтверждено исходным Excel-документом заказчика:**  
  * Состав из 6 базовых операций для узла «Тепловой пункт (комплекс устройств)».  
  * Деление операций на виды технического обслуживания: `ТО1` (операции 1.1, 1.2, 1.3) и `ТО2` (операции 1.4, 1.5, 1.6).  
  * Параметры ежедневных процедур `ТО1` (1.1–1.3): периодичность `1/день`, нормативная численность `1 чел.`, трудоемкость `1 нормо-час`, фактическое заполнение сетки за октябрь (31/31 день без выходных).  
  * Периодичность операций `ТО2`: для операции **1.4** зафиксировано `5/год` (2 чел., 60 нормо-часов); для операций **1.5** и **1.6** зафиксировано `1/квар` (1 чел., 48 и 30 нормо-часов соответственно).  
* **Требует уточнения у заказчика (Открытые вопросы):**  
  * Точное календарное распределение плановой операции **1.4** (`5/год`) по месяцам и дням года, поскольку 365 дней не делятся нацело на стандартные календарные периоды, а в октябрьском срезе клетки для всех операций ТО2 (1.4–1.6) оставлены пустыми (0/31 дней).  
  * Конкретные плановые даты (или правило отсчета от предыдущего ТО) для квартальных операций **1.5** и **1.6** (`1/квар`), так как в октябре отметки выполнения отсутствуют (вероятно, работы запланированы на ноябрь или декабрь IV квартала).  
  * Трактовка числовых значений в колонке «Нормо-часы» для тяжелых регламентов `ТО2` (60, 48, 30) — являются ли они длительностью операции на одного человека, суммарными человеко-часами всей бригады за одно выполнение или годовым бюджетом времени.

## 3. Фиксация ключевых вопросов к Заказчику

* **ВОПРОС 1 (РАСПРЕДЕЛЕНИЕ ОПЕРАЦИИ 1.4 — «5/ГОД»):** По какому алгоритму или в какие конкретные месяцы года проводится операция 1.4 (`5/год`)? Привязана ли она к началу/окончанию отопительного сезона или распределяется равномерно (каждые ~73 дня)?  
* **ВОПРОС 2 (ДАТЫ КВАРТАЛЬНЫХ ОПЕРАЦИЙ 1.5 И 1.6 — «1/КВАР»):** Какова точная дата проведения квартальных работ в IV квартале (почему в октябре стоит 0/31 отметок — работы проводятся в конце квартала или отсчитываются ровно через 3 месяца от последнего факта ТО)?  
* **ВОПРОС 3 (ТРАКТОВКА НОРМО-ЧАСОВ):** Означает ли «Нормо-часы: 60» для операции 1.4 при 2 работниках 60 человеко-часов (30 часов простоя узла при работе двоих) или 60 часов общей длительности?

## 4. Формализация правил и Демонстрационных допущений (Для планировщика и БД)

* **Правило «1/день» (Операции 1.1, 1.2, 1.3 — Подтверждено):**  
  * *Регламент:* Ежедневный непрерывный обход и контроль. Проводится 365 дней в году (включая субботы и воскресенья).  
  * *Подтверждение:* Полностью подтверждено Excel-файлом (в октябре заполнены все 31 день).  
  * *Параметры:* 1 работник, 1 нормо-час. Дедлайн — текущие сутки (23:59). При невыполнении в срок статус задачи не затирается, но выставляется отдельный признак просрочки `is_overdue = true`.  
* **Правило «1/квар» (Операции 1.5, 1.6 — Периодичность подтверждена, алгоритм расчета дат: `[ДЕМОНСТРАЦИОННОЕ ДОПУЩЕНИЕ]`):**  
  * *Регламент:* Квартальное техническое обслуживание (`ТО2`). Требуется 1 работник, трудоемкость — 48 н-ч (оп. 1.5) и 30 н-ч (оп. 1.6).  
  * *Демонстрационное допущение для планировщика:* Плановая дата рассчитывается как `last_maintenance_date + 3 месяца`. Если расчетная дата выпадает на выходной день (сб/вс), применяется правило переноса на ближайший рабочий день (понедельник) при условии, что новая дата остается внутри текущего квартала и не нарушает регламент.  
* **Правило «5/год» (Операция 1.4 — Алгоритм распределения: `[ДЕМОНСТРАЦИОННОЕ ДОПУЩЕНИЕ]`):**  
  * *Регламент:* Тяжелое обслуживание (`ТО2` — чистка узлов и агрегатов), 2 работника, 60 нормо-часов.  
  * *Демонстрационное допущение для планировщика:* До получения графика от заказчика (`confirmed: false`) используется демонстрационная политика: первая задача для нового оборудования (`last_maintenance_date = null`) ставится на дату ввода в эксплуатацию, последующие — с равномерным шагом ~73 дня (2.4 месяца) и переносом с выходных на рабочий день.

## 5. Словарь полей JSON-схемы операций (`maintenance_operations.json`)

| Поле в JSON | Тип данных | Описание | Пример значения |
| :---- | :---- | :---- | :---- |
| `operation_id` | String | Уникальный шифр технологической операции в структуре регламента узла. | `"1.1"`, `"1.4"`, `"1.5"` |
| `name` | String | Полное наименование регламентной операции согласно исходной таблице Заказчика. | `"Контроль параметров показаний приборов (давление, температура)"` |
| `to_type` | String | Вид технического обслуживания (`ТО1` — ежедневное, `ТО2` — периодическое плановое). | `"ТО1"` или `"ТО2"` |
| `frequency_type` | String | Машиночитаемый тип периодичности для алгоритма генерации задач (`daily`, `quarterly`, `custom_annual`). | `"daily"`, `"quarterly"`, `"custom_annual"` |
| `frequency_value` | String | Точное текстовое отображение периодичности из Excel-файла Заказчика. | `"1/день"`, `"1/квар"`, `"5/год"` |
| `required_workers` | Integer | Нормативная численность персонала (бригады), необходимая для выполнения операции. | `1` или `2` |
| `norm_hours` | Float | Нормативная трудоемкость выполнения операции. | `1.0`, `30.0`, `48.0`, `60.0` |
| `confirmed` | Boolean | Статус полноты данных из Excel для автопланирования: `true` — стандартная периодичность (`1/день`, `1/квар`); `false` — нестандартный период без указания месяцев (`5/год`, требует допущения). | `true` или `false` |
