## C5 — составная команда и подготовка изменения, 16.11.2026

После C4 выполнены новые, заранее не подогнанные проверки. Все пять команд «покажи …, затем переименуй equipment_id=…» потеряли второе действие: ранний read-only ответ завершал turn. Ещё пять запросов показали ошибочное распознавание UUID оборудования как инвентарного кода. Frozen C4 round 2 обнаружил два настоящих сбоя LIVE-M01/M02: модель выдумывала следующую revision/экранировала буквальное имя либо просила разрешить подготовить карточку вместо самого предложения. Эти красные протоколы сохранены.

AG-019: общий positive mutation intent запрещает ранним отчётам проглатывать действие. Поддерживаемая связка «прочитай, затем измени» сохраняет проверенный отчёт первой части и продолжает подготовку предложения. Новый optional current_only у настоящего inventory endpoint различает выбранное здание и все доступные; default остаётся прежним. Все запросы проходят серверные права, строки чужих объектов не подмешиваются.

AG-020: UUID из equipment_id больше не становится неявным asset_code. Явно указанный пользователем код в UUID-форме по-прежнему допускается как буквальный код.

AG-021: native Ollama получает read/write enum из фактического registry; history переводится в тот же object wire format без повторного экранирования аргументов. Перед показом предложения equipment/staff техническая revision берётся из авторизованного текущего backend snapshot; явное условие revision пользователя и прямой MCP не переписываются. Буквальное имя берётся из текущей однозначной команды, а не угадывается моделью. Не та операция/карточка и непрошенные поля отклоняются. Если модель остановилась на просьбе разрешить подготовку, строгий fully-specified parser разрешает максимум одно настоящее чтение и одну подготовку карточки для rename/role. Это не исполнение: права, строгая валидация, снимок, digest, подтверждение, stale/replay проверки остаются обязательными. Условные команды, несколько действий, неуказанные параметры и недостаточные права не достраиваются догадками.

Дополнительная проверка сохранности обнаружила 2/5 ошибок самого нового guard: effective staff.is_active смешивал глобальную блокировку аккаунта и membership. Backend теперь дополнительно возвращает membership_is_active/account_is_active; смена роли сохраняет сырой membership flag и employment dates. Прежний effective is_active совместим. Ошибки зафиксированы до исправления.
