# Зависимая аналитика и проверяемые ответы Orchestrator v2

23 ноября 2026 · `kran_dev` · MVP‑11, MVP‑07, MVP‑08 и MVP‑10 · PLN‑12, PLN‑14, AT‑08…AT‑12, AN06, AN07.

Главный инженер может запросить рейтинг оборудования по просрочкам и сразу проверить карточки, действующие регламенты, принятые отчёты и ближайшее ТО выбранных единиц. Инженер может открыть ранний просроченный наряд и получить список материалов, необходимых для приёмки. Исполнитель может запросить точное поле доступного наряда, включая плановое начало. В каждом сценарии пользователь получает подтверждённые данные и ссылки на их источники. Операции с изменением состояния по-прежнему требуют отдельного подтверждения.

## Исполнение поручения

1. Маршрутизация определяет разговор, чтение или действие. Из реплики восстанавливаются явно заданные идентификаторы, поля, кардинальность и понятные серверу источники. Запрос планового начала наряда с точным UUID направляется в чтение карточки, если пользователь просил показать поле. При сопоставлении незакрытых работ и действующего регламента с одним буквальным кодом оборудования сохраняются обе цели.
2. `AnalyticalRequestedResults` описывает выбор, периоды и проекции. `compile_analysis` добавляет цель отбора и зависимые цели с `SelectedInput`. `work_order_analytics` группирует наряды по PostgreSQL с учётом связей оборудования M:N, назначений, состояния, нормативного дедлайна и часового пояса объекта. Он поддерживает рейтинги оборудования и исполнителей, сравнение плановых периодов, выбор раннего просроченного задания, поиск недостающих материалов и оборудования без подтверждённого ТО.
3. `DataflowRunner` проверяет снимок отбора и разворачивает чтения по проверенным `ResourceRef`. Источник задания передаёт UUID, карточка добавляет ревизию и ID текущей попытки, проверка материалов использует все эти значения. При HTTP 409 или отказе одного источника сохраняются подтверждённые результаты соседних чтений.
4. Точное разрешение оборудования использует буквальный UUID, код или название и доступный реестр текущего объекта. Один подтверждённый результат используется для связанных чтений. При неоднозначности ответ показывает допустимые варианты, при пустом результате сообщает об отсутствии совпадения. Отказ и неполный источник сохраняют собственный статус.
5. `request_spec` версии 2 сохраняет фрагмент запроса, цель, зависимости, область, статус доказательства и факт доставки. Итоговая проверка учитывает выданные поля, строки и показатели. Объём коллекции определяется явно запрошенным форматом, числом элементов и бюджетом ответа. Для заданий и истории доступен переход к авторизованному источнику при усечении.

Связи целей, SQL-семантика, полномочия ролей и правила источников описаны в архитектурных документах. [Архитектура v2](../architecture/assistant-architecture-v2.md) · [Зависимая аналитика](../architecture/assistant-dependent-analytics.md)

## Контракты и совместимость

| Контракт | Поведение |
|---|---|
| `GET /api/v1/assistant/workspace/work-order-analytics` | Выбор группировки, метрики, даты среза и окон. Параметры `limit` и `offset` поддерживают постраничный рейтинг оборудования и исполнителей по просроченным и незавершённым заданиям. До 100 групп за чтение. |
| `GET /api/v1/assistant/workspace/tasks/{task_id}/acceptance-evidence` | Проверяет текущий UUID, ревизию и активную попытку. Возвращает сохранённые материалы и препятствия. При смене ревизии или попытки возвращает HTTP 409. |
| Задания, принятая история и календарь | Разрешённый верхний размер страницы заданий и истории — 200, обычный размер — 25. Дополнительный `next_only` выбирает ближайшую календарную обязанность у оборудования. |
| `contracts/assistant-tools.json` и `assistant-acceptance.json` | Операции зарегистрированы в существующем каталоге и учитываются аудитом REST и MCP. Матрица отдельно хранит ссылки на тесты и фактические доказательства приёмки. |
| Сохранённые поручения | Дополнительные поля размещены в существующем JSON. Чтение прежних сохранённых состояний совместимо с текущей схемой. Дополнительная SQL-миграция для этого коммита не требуется. |
| Ollama и AITUNNEL | AITUNNEL различает транспортную ошибку, JSON, схему и отказ модели. Исправимый сбой допускает один повтор генерации с тем же ID модели в общем дедлайне. Вызовы инструментов выполняются после валидации. Биллинг ответа без ID остаётся неизвестным. |

Все предметные чтения проверяют права роли и объект в существующем API. Модель не может авторизовать новое изменяющее намерение. Актуальная ревизия, подтверждение, идемпотентность и аудит продолжают действовать в штатном пути изменения. [Работа ассистента и API](../service/assistant.md)

## Открытые ограничения

- Полнота произвольной естественной формулировки зависит от интерпретации. Сервер восстанавливает проверяемые требования по поддерживаемым типам запроса, связывает нужные источники и обозначает неподтверждённые пункты.
- Источник без стабильного постраничного снимка может подтвердить только прочитанные строки. Зависимые назначения показывают точное общее число и частичный статус после достижения предела. Отдельное продолжение по исполнителю пока отсутствует.
- Зависимый календарь показывает ближайшую обязанность в заданном горизонте. Для перечня календарных событий используется самостоятельное чтение по периоду. Полнота сведений по ТО зависит от опубликованных конфигураций и принятых отчётов объекта.
- В отдельном повторе 15 случаев медиана времени хода выросла с 6,30 до 10,33 с, P95 — с 11,37 до 19,30 с. Основная измеренная разница пришлась на вызовы модели. Замеры проводились с фоновой регрессией.
- Совместимость DeepSeek и GLM проверена через сохранённые ответы и управляемый транспорт. Живой повтор ждёт отдельно согласованного бюджета. Расходы текущей серии на облачные вызовы составили 0 ₽.
