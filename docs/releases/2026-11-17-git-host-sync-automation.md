# Автосинхронизация GitHub ↔ GitVerse, 17.11.2026

## Причина и изменение

До исправления GitHub → GitVerse работал по push, а GitVerse → GitHub зависел от GitHub cron. При `*/5 * * * *` фактические schedule-запуски 17 ноября произошли в 02:04 и 10:35 UTC; пяти минут расписание не обеспечивало. GitVerse запускал унаследованный `.github/workflows/gitverse-sync.yml`, но пропускал job из-за условия с именем GitHub-репозитория: запуски 2133584, 2133893, 2134684 и 2134900 имеют `status=skipped`. Все пять веток на момент диагностики уже совпадали; последний успешный GitHub push-run 44139717320 перенёс dev `e9dd52e`.

Теперь у каждого хостинга собственный workflow: GitHub `.github/workflows/gitverse-sync.yml`, GitVerse `.gitverse/workflows/github-sync.yml`. Оба реагируют на push веток/тегов и используют общий runner. GitHub дополнительно реагирует на создание ref. Независимые резервные расписания: GitHub каждые пять минут со смещением, GitVerse четыре раза в час с интервалом 15 минут — минимум его облачных раннеров. Очередь/доступность провайдера всё равно могут задержать запуск; расписание не является SLA.

Исполняемые `scripts/sync_git_hosts.py` и `scripts/run_git_host_sync.sh` всегда берутся из GitHub `main`, а не из отправленной ветки. Контрольный код больше не зависит от обновления прикладного dev. Устаревшая личная ветка без нового workflow может ждать резервного опроса; новые ветки должны наследовать актуальный dev. Рабочие папки разработчиков не обновляются автоматически.

## Восстановление и защита данных

Перенос охватывает все Git-ветки и теги, сохраняя исходные SHA. Каждая операция записи — атомарный non-force push. При потере ответа, временном сетевом отказе, конкурирующем push или изменении refs во время проверки выполняется новый полный цикл inventory/fetch/планирования, максимум три цикла с паузами 10/30 секунд. Ранее внедрённые ограниченные повторы чтения и диагностика RPC/403 также входят в контрольную версию main.

Слепого повтора push нет: следующий цикл сначала читает фактические refs, поэтому уже выполненная запись не повторяется. Диагностика включает stdout porcelain, где Git сообщает причину отклонения атомарного push. Отчёт сохраняет все циклы, включая неуспешные, даже если последующая сверка обнаружила успешную запись. После равенства refs новые коммиты не создаются: встречные event-запуски заканчиваются без дальнейшего push.

Реальное расхождение истории одной ветки, разные одноимённые теги, отказ авторизации или сертификата не скрываются автоматическим перезаписыванием. Сохраняются обе стороны и ненулевой статус с SHA/этапом отказа. Отсутствующую ветку существующая политика восстанавливает; намеренное удаление выполняют на обоих хостингах при временно остановленных workflow. Это Git-синхронизация: Issues/PR, локальные файлы, БД и deployment приложения в неё не входят.

## Доступ

GitHub использует прежние repository secrets и read-only GITHUB_TOKEN. Для GitVerse после отдельного явного согласия владельца создан новый write deploy key GitHub, ограниченный только `Fir-White/FixRateAI` (id 170223860). Его приватная часть сохранена в GitVerse `MIRROR_GH_SSH_KEY`, существующие реквизиты GitVerse — в `MIRROR_GV_USERNAME`/`MIRROR_GV_TOKEN`. Личный GitHub OAuth-токен в GitVerse не передавался. Временный приватный файл ключа удалён после настройки; секреты не входят в Git, логи или отчёты. Проверка SSH-host сохраняется, данные host keys получаются через проверенный HTTPS GitHub API с ограниченными повторами.
