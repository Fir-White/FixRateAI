## Исходная сборка

- React/Vite, оболочка E3, семь разделов главного инженера, ролевые маршруты и выбор здания. Данные рабочего дня приходят из реальных нарядов. В системе есть календарь, версии плана, выпуск и назначение нарядов, регламенты, реестр, команда и отчётность.
- Исполнитель заполняет чек-лист, прикладывает фото, сохраняет и сдаёт отчёт. Очередь приёмки поддерживает основания решения, историю попыток и вспомогательный фотоанализ.
- Основной композер и контекстные переходы открывают общий серверный диалог. PostgreSQL хранит сообщения, предложения на подтверждение, выбранную модель и область пользователя, объекта и роли. Личный XLSX читается с листами и адресами ячеек. Реестр и каталог используют бизнес-импорт с предпросмотром.
- Командная ветка `dev` содержит CR‑17 с версионируемым исходным Excel и таблицей `source_revision_events`.

## Реализовано

1. **История действий.** `/assistant?view=actions` открывает до 25 записей на странице. Строка ведёт в сохранённый диалог. При переключении вкладок остаются текст, ожидающие вложения и контекст, а `chat` сохраняется в адресе. Открытие журнала и повтор чтения доступны при недоступной модели.
2. **Задания и отчёты исполнителя.** «Мой день», «Мои задания», «Оборудование» и «Мои отчёты» ведут к рабочим разделам. `/executor/reports` использует серверный `activeExecutionId` разрешённых нарядов. Детали, фото и история попыток открываются в задании. Календарь доступен из ближайших заданий, смены — из календаря.
3. **SQL-проверка установки и обновления.** Контракт проверяет 58 первичных ключей после 024 и таблицы диалогов, вложений, действий и выбора модели. Проверки ограничений, отрицательных операций и сохранности истории выполняются на отдельной БД.
4. **Регрессионные тесты.** Сценарии навигации, первой настройки, рабочего дня и выбора модели приведены к текущему E3. Тестовые уточнения переиспользованы из коммита `b6fd12f`.

## API, права и подтверждение

`GET /api/v1/assistant/actions?offset=0` читает существующие `assistant_actions` и `assistant_conversations` по текущим `site_id`, `user_id` и роли. Ответ с `Cache-Control: private, no-store` содержит тип операции, UUID цели при наличии, статус, даты и результат проверки. Та же проекция доступна через инструмент `assistant_action_history`. Контракты инструмента и критериев приёмки обновлены генераторами.

Просрочка предложения рассчитывается по сроку подтверждения. Запись о старте означает полученное подтверждение. «Выполнено» соответствует успешному ответу команды, проверка постусловия отображается отдельно. У неопределённого исхода нет автоматического повтора. Проекция использует ограниченный набор метаданных и безопасные сообщения об ошибках по коду ответа. При удалении диалога его личные записи удаляются вместе с ним, аудит сервера сохраняется.

Подтверждение проходит через `POST /assistant/actions/{identity}/confirm`. Сервер сверяет SHA, фактическую область, права и предусловия, прежде чем однократно зафиксировать допуск к выполнению. Права в новых маршрутах исполнителя проверяются существующей ролью и API заданий и вложений. Обновление использует установленную схему БД.

## Excel и Dynamic RAG

| Вход | Реализация и состояние |
| --- | --- |
| XLSX в диалоге | Личная область пользователя, объекта, роли и диалога. Сервер хранит исходное имя и сверяет размер и хеш при чтении. `attachment_read` читает выбранные листы и диапазоны. Формулы остаются данными |
| Excel для бизнес-данных | Реестр и каталог проходят предпросмотр и явный импорт в оборудовании или планировании. Актуальные статусы, сроки и расчёты идут из PostgreSQL |
| Постоянный источник знаний | В текущей сборке отсутствует. `dev` содержит транзакционные события ревизий CR‑17. FRAI‑173 охватывает потребитель, извлечение, поиск и проверку ACL и редакции. Клиенту требуется контракт списка, карточки, версии и цитаты |

Подбор регламентов для разбора инцидента уже существует в `backend/app/integration/incidents.py`. Он ранжирует допущенные регламенты по словам для конкретного обращения. Постоянные файлы и обновление их индекса требуют передачи ML03.

Приёмка постоянного XLSX требует сценария «загрузка → текущая версия → поиск и цитата → замена файла → поиск новой версии». Тест должен исключать старые фрагменты после замены, проверять повтор той же контрольной суммы, ошибку парсинга, отзыв доступа и чужой объект.

## Локальный запуск

Настройте `DATABASE_URL` для отдельной PostgreSQL и установите зависимости из [инструкции запуска](../service/runtime.md#установка-и-запуск).

```powershell
$env:PYTHONPATH = 'backend;.'
python -m app.manage migrate
python -m app.manage seed-demo
npm.cmd --prefix frontend run build
python scripts/start_backend.py --host 127.0.0.1 --port 8000
```

### Репетиция на TEST-объекте

1. Войти как `fixrate-demo-chief_engineer@example.test`. На «Рабочем дне» попросить подключённого помощника показать ближайшие работы и уточнить назначение по ID выбранного задания.
2. В «Планировании ТО» открыть период и проверить действующие сроки и загрузку. Выбрать учебный наряд с подготовленной доступностью, например из тестового сценария `test_assignment_preview_real_complete_crew_load_and_no_persistence`.
3. Выбрать бригаду через preview, затем подтвердить назначение. При подтверждении через помощника открыть журнал и сверить запись с текущим состоянием наряда.
4. Во втором браузерном профиле войти назначенным исполнителем. Открыть задание, начать работу, заполнить чек-лист, приложить учебные фото из `data/demo/demo-photo.png` и сдать отчёт. Из «Моих отчётов» открыть сохранённую попытку.
5. Открыть приёмку главным инженером. Проверить фото и чек-лист, дождаться доступного анализа, прочитать его ограничения, ввести основание и подтвердить решение. Для демонстрации возврата повторить шаг 4 и принять следующую попытку.

Для отдельной репетиции исполнения подготовлен наряд `runtime-order` и аккаунт `fixrate-demo-1@example.test`. Сквозной маршрут требует выбора реально доступной модели и репетиции на одном наборе данных.

## Эксплуатация и оставшиеся ворота

Сохранить тестовый объект с исходным Excel, подготовленными назначениями, учебными фото и отдельными аккаунтами двух ролей. Для выпуска зафиксировать проверенный SHA, повторить upgrade/backup/restore и принять сценарии на целевых устройствах. Ролевую проверку, результаты реального LLM/CV и испытания RAG учитывать по отдельным протоколам. [Оставшиеся зависимости](../architecture/fixrate-finalization-matrix.md)

После передачи CR‑17/ML03 подключить к текущему AI Workspace представление `/assistant?view=knowledge` и адрес выбранного источника. Использовать фактический контракт версии, ACL и состояния индекса для списка, карточки, листов и предпросмотра. Зарегистрировать чтение, поиск и разрешённые изменения в capability-каталоге. Проверить обновление индекса на `source-v1.xlsx` и `source-v2.xlsx` из TEST-фикстуры, затем провести сквозную репетицию двух ролей вместе с QA.
