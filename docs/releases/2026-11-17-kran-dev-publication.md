## 2. Что реализовано в AI-ассистенте

### 2.1. Выбор модели и стабильный контекст ответа

В интерфейсе чата появился каталог моделей Ollama/AI Tunnel с поиском, состояниями недоступности и ограниченным числом элементов DOM. Метаданные провайдеров читаются параллельно с ограничениями, кешируются отдельно от личного выбора. Просмотр каталога не загружает веса и не запускает генерацию.

Выбор сохраняется в PostgreSQL по пользователю, объекту и роли. Новая миграция **022** хранит настройки и снимок модели/deadline в turn. Запущенный ответ не переключается на другую модель при последующем изменении предпочтения. Конфликт ревизии даёт 409 и сохраняет введённые текст/файлы. Сервер закрепляет digest локальной модели, проверяет её доступные возможности и не отдаёт ключи браузеру/модели/истории. Открытие и закрытие выбора поддерживает клавиатуру, Escape и возврат фокуса.

Это реализованная интеграция конкретных провайдеров, не обещание готовых адаптеров любого бесплатного/платного API и не проверка качества каждой модели каталога.

### 2.2. Единый сохраняемый оркестратор

Вместо остановки на первом частном ответе используется один исполнитель с типизированными целями, зависимостями, неизменяемыми ограничениями и отдельным состоянием каждой цели. Миграция **023** добавляет workflow/resume lineage и привязку action к корневому поручению и фазе цели; прежние сообщения/действия остаются совместимыми с NULL в новых полях.

Путь поручения: исходное сообщение и principal → проверенный план целей → разрешённые предметные чтения/вычисления → конкретные предложения изменений → человеческие подтверждения → серверная запись → авторизованный readback → состояние отдельных целей. Завершённый ответ закрывает транспорт, а невыполненные цели остаются partial/blocked/awaiting_confirmation/uncertain, а не исчезают.

Предметные адаптеры ограничены своей ответственностью и набором инструментов. Backend проверяет объект/роль, реальные идентификаторы и ревизии, нормативный календарь/арифметику, источники и результат операции. Отдельный специалист не становится вторым привилегированным агентом. Неопределённая запись не воспроизводится автоматически при resume.

### 2.3. Исправления семантики, источников и доказательств

- Сохранены исходные запреты и требуемый вид результата при ремонте плана/параметров: запрос изменения не завершается одним чтением, установленный регламент не подменяется шаблоном операции, сотрудник не подменяется текущим профилем.
- Точный сотрудник разрешается по полному однозначному результату поиска; неоднозначность, чужой объект и конфликт явных IDs не превращаются в выдуманную идентичность.
- Явно запрошенный паспорт/первоисточник остаётся открытой зависимостью при отсутствии документа; модель не придумывает его содержание. Это консервативная защита, не доказательство полноты любых формулировок.
- Для типизированных staff/task команд используются разрешённые поля реальной схемы. Сохраняются не запрошенные пользователем значения; staff edit различает даты, membership/account flags и явный NULL.
- Фазы публикации/аналитики/подбора не закрывают весь workflow по одному промежуточному receipt; проверяется принадлежность receipt цели/пользователю и текущему состоянию.
- Ответы оборудования используют атомарные count/page/snapshot из одного SQL statement и ограниченные повторы чтений. Несогласованные страницы и обрезанная доставка остаются partial. Гарантия полного snapshot не распространяется автоматически на остальные списки.
- Calendar/history/workbook evidence опираются на реально прочитанные даты, принятые отчёты и ячейки; неизвестные нормы/единицы не заменяются нулём или догадкой модели.
- Истощение синхронного провайдера нормализуется в сохранённую ошибку; structured/text generation ограничены deadline. Бесконечное ожидание модели не считается работой над целью.

### 2.4. Подтверждения, приватные результаты и проверка записи

Изменения связаны с точным diff/payload hash, target, principal, ожидаемой ревизией и сроком согласия. Обычные серверные RBAC/CSRF и бизнес-правила остаются обязательными. Смена контекста, устаревшее согласие, повтор и потеря ответа проверяются отдельно.

Поддержанные записи проверяются свежим авторизованным чтением; реализован общий postcondition для **9 из 74** записывающих операций. Для остальных **65** нет основания считать произвольный ответ HTTP 200 доказанной бизнес-целью: они остаются unverified до соответствующей проверки.

Enrollment credential фильтруется до model payload, persistence и общих проекций; разрешённому администратору выдаётся защищённая ссылка с повторной проверкой доступа. Покрыты известные структурированные результаты, но очистка произвольного несвязанного legacy plaintext и полная DLP не реализованы.

### 2.5. Интерфейс ассистента

Реализованы отдельное отображение состояния поручения и ответа, статусы целей/этапов, самостоятельные подтверждения действий и продолжение сохранённой линии. Личная история/файлы и контекст роли/объекта не смешиваются. Большие старые ответы раскрываются через native details; серверные факты выводятся ограниченной текстовой грамматикой с сохранением значений и ссылок.

Прямые ссылки/история и selected files не доказывают сохранность **неотправленного** черновика после reload: этот дефект остаётся открытым. Полный навигационный UI gate и отдельные cold/explicit-open задержки также не закрыты.

## 3. Что реализовано для установки и эксплуатации

### 3.1. Отдельный Docker release-контур

Добавлены `deploy/compose.yaml`, multi-stage `deploy/Dockerfile`, Caddy и pinned `images.lock.json`/`requirements-core.lock`. Developer Compose сохранён. Целевой набор: PostgreSQL 18 → отдельный migrator → API и worker → frontend/HTTPS; Ollama подключается отдельно или явным профилем.

Core содержит solver/OR-Tools, RF и обязательные библиотеки без автоматической установки весов. Неподготовленный CLIP не объявляется работающим CV. Системные C++/OpenMP runtime закреплены, Python dependencies имеют точные версии; для всех **38** зависимостей разрешены Linux amd64/Python 3.12 wheels. Это resolver-проверка, не успешная сборка OCI.

API/worker используют UID 10001, постоянное файловое хранилище и health checks. API не дублирует optimizer/scheduler отдельного worker. Worker отслеживает heartbeat и остановившийся scheduler. БД/API/Ollama не публикуют host-порты; по умолчанию web доступен loopback. Для удалённого режима предусмотрены DNS/HTTPS/Secure cookies. Распределённая durable queue/lease recovery этим worker не реализована.

### 3.2. Однофайловые установщики

Реализованы шаблоны Windows `FixRateAI-Setup.ps1.in` и Ubuntu `fixrate-install.sh.in`, упаковщик `release_package.py` и встроенный bundle с manifest/контрольными суммами. Заказчику предполагается готовый PS1/bash с заранее собранными images; host Python/Node/PostgreSQL не требуются.

Действия: install, status, doctor, backup, restore, upgrade, verify. Есть проверка Docker/Compose/архитектуры/диска/порта, отдельное подтверждение системных prerequisites, закрытые ACL/права, криптографические инфраструктурные секреты и lock параллельных операций. Повтор той же версии сохраняет project/secrets/volumes/пользователей и не делает demo seed. Другой release требует явного upgrade.

Фактические embedded payload проверены PowerShell 5.1 и Git Bash. Поддержанные целевые платформы — Windows 11 x64 с Docker Desktop/WSL2 и Ubuntu 24.04 amd64. EXE, offline bundle, ARM и произвольные ОС не заявляются.

### 3.3. Первоначальный администратор и исправление транзакций

Новая миграция **024_installation_bootstrap.sql** добавляет installation singleton. `/api/setup` и форма `/setup` создают организацию, первое здание, администратора и членство атомарно, по одноразовому установочному секрету из закрытого файла. Секрет передаётся защищённым header, не JSON модели/истории. После успеха hash уничтожается; повтор получает 409. Любой существующий пользователь закрывает первоначальную регистрацию, включая upgrade заполненной схемы.

Конкурентные запросы сериализуются `SELECT FOR UPDATE`. При испытании обнаружен и исправлен реальный дефект: migrator оставлял `raw.autocommit=True` в pooled connection, поэтому последующие транзакции/блокировки не работали ожидаемым образом. `migrate` и `seed_demo` восстанавливают предыдущее состояние соединения; исключение при bootstrap откатывает все созданные строки.

Operator recovery — отдельная CLI-процедура с существующим admin, скрытым вводом нового пароля, явным подтверждением, отзывом сессий и audit. Обычная регистрация сотрудников и объектные роли не заменены публичной выдачей admin.

### 3.4. Backup, restore и upgrade

Backup останавливает consumers, сохраняет PostgreSQL custom dump, всё файловое хранилище, конфигурацию и прежний bundle, проверяет hashes, dump listing и безопасный tar. На Windows binary streams копируются через BaseStream, чтобы PowerShell 5.1 не испортил dump текстовым перенаправлением.

Restore требует подтверждения замены, проверяет полный backup, восстанавливает БД одной транзакцией и файлы в проверенный staging; traversal/symlink архивы отклоняются до удаления существующих файлов. Целевая инфраструктура/пароль БД не подменяются чужими из backup. При сбое consumers остаются остановленными. Единой атомарной транзакции PostgreSQL+filesystem нет.

Upgrade допускает только точные проверенные compatible_from версии и прежний major PostgreSQL; сначала создаётся backup, затем образы/миграции/health. Автоматический downgrade image не считается откатом данных. Allowlist пока пуст: прежней сертифицированной публичной версии нет. Native pg_dump/pg_restore в другую БД и byte-exact file restore выполнены; контейнерные wrappers ещё требуют исполнения.

### 3.5. CI и защищённые Releases

Новый workflow `release.yml` описывает push/PR main, dispatch и строгие semver tags: pinned Actions, backend/contracts/migrations, frontend, Docker build, фактический generated-installer smoke, Windows package verification и передачу проверенных images publisher без поздней пересборки.

Main создаёт CI-кандидаты; официальный tag требует SHA из main, owner enable flag и protected environment с независимым reviewer без self-review/admin bypass. Publisher проверяет OCI revision/architecture, digest, анонимное чтение registry, checksums загруженного draft и публичную загрузку после публикации; повтор существующего release не создаёт дубль. Параллельные публикации версии сериализованы.

Workflow и скрипты реализованы, но настоящие main/tag/registry испытания не выполнены. Этот push в kran_dev не является merge main, публичным Releases или production deployment. Существующий GitVerse sync может автоматически отзеркалить обновлённую ветку по своим правилам; вручную публикуется только GitHub kran_dev.

### 5.3. Доступные ресурсы тестирования

Последним решением снято общее требование «только локальная Ollama»: участник выбирает доступную локальную модель, бесплатный или платный API. В результатах нужны фактические provider/model, профиль, параметры/corpus/SHA и разделение разных сред. Исторические local-model протоколы не переписываются в API-прогоны.

Основные описания TEAM-карточек содержат новое правило. Во время последующей сверки выявлены остаточные старые local-only формулировки в отдельных чек-листах ML03/N01/Q01/Q02; запись через YouGile периодически теряет подтверждение, поэтому их полная синхронизация пока не заявляется завершённой. Новое правило в плане имеет приоритет, а открытая правка чек-листов не выдаётся за выполненную при публикации исходников.

Остаток реализации: `verify_agent_local.py`, `validate_record` в генераторе acceptance и поставочный Compose остаются специализированными локальными профилями. Валидатор текущего исторического ledger принимает positive_e2e только с pinned Ollama reference; универсальная регистрация положительных API-evidence ещё должна быть согласована/адаптирована в N01/N02/Q01. Новая организационная политика не означает, что этот машинный формат уже расширен или что все провайдеры реализованы. До этого допустимые API-испытания фиксируются отдельным явным протоколом, без ложного импорта в local-only ledger.
