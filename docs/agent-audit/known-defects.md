# Дефекты и минимальные воспроизведения

## AG-016 — ошибка чтения выдаётся за отсутствие данных (подтверждён, C4)

Повторение frozen 75a1fa9 на новой БД дало **1 failed/1157 passed, 835,95 с**, source_stable=true. A-equipment не прочитал данные: native grammar разрешала root name, предназначенный describe_tool, у обычного equipment_find; модель дважды отправила name="". Backend правильно отверг аргументы 422, но финальный текст объявил, что оборудование не найдено, и попросил пользователя повторить запрос вручную. Успешный первый round 1158/1158 не был достаточным доказательством.

Разделены обычный envelope и describe_tool с const tool; селекторы не удаляются ради успеха. Независимый set/const oracle проверяет именно изоляцию root-полей, не объявляется полным JSON Schema validator. Первоначальная попытка подключить отсутствующий jsonschema дала collection error, не продуктовый результат; новых зависимостей не устанавливалось. После исправления oracle **10 failed/7 passed** до продуктового фикса: пять структурных вариантов и пять настоящих HTTP-fault путей с вводящей в заблуждение модельной прозой.

All-failed read guard теперь различает 401/403, 404, 422, 5xx и не позволяет модели объявить реестр пустым. Настоящий ответ total=0 остаётся допустимым. Для однозначного списка текущего оборудования обязателен equipment_find даже при пустом router; названия/коды/total берутся из backend, страница явно помечается как страница. Текущий объект не расширяется до всех доступных зданий. Дополнительный фильтр/второе действие не поглощаются таким recognizer. Пять форм запроса, пять исключений и 31 запись против страницы 25 входят в регрессию.

## AG-017 — смена роли очищает даты трудоустройства (подтверждён, C4)

Отдельный native repro **5 failed/17,61 с**, agent-audit-staff-preservation-before.

Никаких миграций/переписывания прежних данных. Live rename/staff oracle теперь проверяет все остальные поля SQL-строки, а не только роль/название. Добавлен реальный assistant proposal/approval/replay с сохранением дат.

## AG-018 — чтение фото ложно объявляет запись показания (подтверждён, C4)

Дополнительный live-срез дал **1 failed/79 passed, 379,75 с**: фото Pressure 1.2 bar прочитано как число, маркировка потеряна, а текст сообщил «Эти данные добавлены как фиксированная запись». Actions пусты, fingerprint домена не изменён: это выдуманная запись в ответе, не фактическая мутация. Oracle усилен также на ложные фразы о сохранении/обновлении показаний.

Для однозначной read-only просьбы считать маркировку и показание с одного изображения добавлен VisiblePhotoReading: literal label, numeric text|null, visible unit|null. Данные приходят от настоящей vision inference; неизвестное не заменяется нулём, математическое выражение не становится измерением. Рендер фиксированно сообщает отсутствие записи/приёмки; эта ветка не планирует доменные действия. Явная просьба сохранить/назначить/изменить/опубликовать остаётся в общем workflow подтверждений. Parser/renderer/recognizer тесты отдельно от настоящих фото-эпизодов; оригинальные изображения заказчика не использовались.

### Продолжение AG-005 — двойное JSON-кодирование нестабильно даже с retry

После исправления AG-015 независимый запуск дал **1 failed/72 passed**: staff-role episode дважды вернул синтаксически неверный arguments_json, хотя до этого тот же сценарий проходил. Это не отсутствие сотрудника/прав и не исправлено одним хорошим повтором.

В локальном Ollama wire теперь используется структурированный объект аргументов, полученный из AgentStep schema; адаптер однократно сериализует его в прежнюю каноническую DTO. Публичная схема AgentStep, облачный strict transport, backend JSON Schema, ACL, preflight и approval не меняются. Ошибочные legacy строки не «чинятся» regex/eval и не исполняются: остаётся одна ограниченная inference-retry с безопасной диагностикой. Пять новых HTTP-fixture roundtrip проверяют quoted text, path/body/view/пустой объект, а canonical schema остаётся string. **33 passed/13,09 с** на parser/transport; реальное качество модели подтверждается отдельно live-прогоном.

## AG-015 — транспорт превращает PATCH omission в явные null (P0, исправлен)

Новый живой holdout переименования оборудования не создал предложение: `agent-audit-positive-holdout` — 1 failed/7 passed; дополнительная диагностика — 1 failed/13 passed. Модель прочитала revision=2, но три попытки equipment_edit получили 422 и итог ошибочно попросил пользователя узнать ревизию. Одного уточнения промпта оказалось недостаточно: точный INVALID_COMMAND указал value_error на уровне body.

Первопричина в `validate_arguments`: `jsonable_encoder(body)` материализовал все default=None. Минимальная валидная команда после первой проверки получила system_id/status/data_origin/properties=null, и вторая проверка в `propose` закономерно отвергла их как явный сброс обязательных полей. Это собственный дефект транспорта, не отсутствие доступа и не необходимость вручную сообщать revision.

Отдельные 5 PATCH-вариантов воспроизвели ошибку: **5 failed/6 passed**, `agent-audit-partial-command-before`. Исправление использует exclude_unset=True, сохраняя именно переданные поля на всех фазах. Допустимое явное очищение nullable-поля не теряется; явный null обязательного поля по-прежнему отклоняется. Схема API и валидация не ослаблены. Диагностика содержит только field/type, без input/ctx/значений body; trace различает validation/access/not_found/backend. Промпт v12 поясняет текущую revision и запрещает требовать техническую ревизию у пользователя. Живое переименование после исправления подготовило предложение и прошло подтверждение с независимой SQL-проверкой; окончательный совместный прогон записывается в журнале отдельно.

## AG-011…014 — происхождение прогнозов и неизвестные суммы (исправлены)

Независимый запуск старых strict-xfail через `--runxfail` дал **5 failed, 39 passed**: прежняя маркировка не являлась доказательством исправления.

- **AG-011:** `uncertainty.kind=unknown` с calibrated=true ошибочно допускал раннюю дату. Теперь неизвестность запрещает такое основание; 5 соседних границ проверяют fallback, не одобрение AI.
- **AG-012:** сохранённая алгоритмическая дата могла быть раньше срока снимка и служить ложным fallback. ALG02 обязан совпадать с замороженным обязательством после согласованного переноса выходных; расхождение диагностируется и использует срок снимка. Некорректный тип даты не обрушает решение.
- **AG-013:** bounded_ai сохранял придуманные моделью overdue/runtime_due_at_hours/elapsed_ms. Теперь это производные значения сервера и снимка, проверенные на 5 границах часового пояса. Результат модели не является источником текущей даты или измерения времени.
- **AG-014:** пустая последовательность операций проходила `all([])`, превращая неизвестные нормы/длительность в известный ноль. Пустой период с неизвестными исходными значениями сохраняет null; обоснованный пустой известный период остаётся 0.

Старые четыре ожидаемых бизнес-утверждения сохранены, сняты только xfail. Добавлено 25 независимых соседних проверок. Чистая регрессия: **157 passed, 1 xfailed / 3,45 с**; PostgreSQL/API: **210 passed, 1 xfailed / 12,03 с**, весь native pipeline. Дополнительная проверка сохранения фактической policy в SQL: **64 passed / 10,87 с**. Теги `maintenance-orchestrator-v1.1`, `bounded-ai-v1.1`, `calendar-rules-v3.1` отличают новые решения; старые записи не переписываются. Обнаруженный hardcode policy в source_snapshot заменён на действительную decision.policy_version.

## AG-002 — противоречивые агрегаты принимаются за полный анализ (P1)

Воспроизведены 10 независимых повреждений поверх настоящего PostgreSQL/API-ответа: общий счётчик, незавершённость, сумма сроков, сумма норм, число по датам, cardinality страницы, сумма операций оборудования, число дублей, неверная локальная дата и невалидная форма snapshot_id. Все 10 первоначально выдавали полный отчёт (`reports/agent-audit-provenance-before`, 10 failed). Это явный fault injection, не замена положительных данных заглушкой.

Первопричина: проверялись только complete и равенство fingerprint; внутренние арифметические/календарные инварианты не проверялись. Добавлен независимый evidence gate перед текстом: счётчики/категории, область доступа, время, полнота страниц, даты/нормы и детали. Кандидаты в бизнес-дубли не удаляются, множественные связи оборудования не суммируются как независимые задания. Исправление проходит отдельную регрессию.

Первая регрессия после исправления: 654 passed (`agent-audit-evidence-after`). Позднее добавлены проверка свежести часов, совпадение запрошенных фильтров и проверка формы подробных строк.

## AG-003 — молчаливое расширение аналитической области (P1)

Новый независимый набор из четырёх фактических work_orders: завтра, январь, февраль и приёмка. 10 failed / 1 passed (`agent-audit-scope-before`): игнорировались день/месяц/источник/состояние; запросы завершённых/отменённых перехватывал обработчик незавершённости. Неподдержанные/невалидные даты и отбор по оборудованию требуют уточнения вместо отчёта по всем. Классификация «просрочено/сегодня/будущее» не превращается в фильтр today. Первая регрессия: 73 passed (`agent-audit-scope-final`), затем добавлены смежные случаи.

## Ошибки тестового стенда, не дефекты продукта

Отсутствовавший Accept MCP (406); требование inference от раннего role guard; старый unit principal без timezone; ожидание пустого query без фактического default limit=25; сравнение эквивалентных Z/+00:00 как разных строк исправлены в oracle/fixture. Первоначальный 2-секундный solver budget допускал отсутствие incumbent: это не ложная невозможность. Все неуспешные протоколы сохранены; их не засчитывают как найденные продуктовые уязвимости.

Дополнительно: вопрос «какое сегодня число» допускает корректные день и месяц без обязательного года; это исправление oracle, не отказ от проверки серверной даты. Полный счётчик 31 заданий корректно выдан детерминированной аналитикой — требовать от неё inference было ошибкой стенда. Для fault-тестов теперь principal берётся из фактической записи сайта, включая timezone; перед **каждой** инъекцией проходит положительный контроль полного отчёта и после неё проверяется конкретная причина evidence gate. Это исключает вакуозный успех из-за иной ошибки доступа/часового пояса.

## AG-007 — ложное отсутствие оборудования без чтения (P1)

На объединённом прогоне `agent-audit-integrated` модель сообщила, что RT-ABSENT-999 отсутствует, с **пустой трассой**. Значение случайно совпало с fixture, но отсутствие не было доказано. Причина — route.tools=[] разрешал свободный ответ по вопросу о реальных данных.

Ошибка чтения даёт ограничение, а не пустой реестр; секреты/произвольные URL не запрашиваются. Пять форматов кода + backend 503 проверены на настоящем API с явно внесённой ошибкой маршрутизатора. Это не универсальное доказательство grounding всех свободных тем.

## AG-008 — календарь заданий и чужие регламенты вместо конфигураций актива (P1)

В `agent-audit-integrated-after` A-regulations назвал отсутствие регламента по пустому tasks_find при существующей опубликованной конфигурации. B-no-regulations привёл операцию другого насоса и попросил Excel identity вместо чтения service-configurations. Обе ошибки подтверждены реальной моделью, не scripted-ответом.

Для запроса регламентов конкретного кода grounding выбирает точное совпадение в разрешённом equipment_find, затем вызывает regulations_read с фактическим equipment_id. Счётчики опубликованных/неопубликованных конфигураций и уникальных операций, периодичность и действие выдаются из этого результата. Нет совпадения/несколько совпадений/ошибка — не повод угадывать связь. Будущая published-конфигурация явно показана с датой начала и не выдаётся за обязательную работу сегодня. Пять adjacent-cases (0/1/2 published, draft only, mixed) подтверждены при пустом календаре; связанные 76 проверок прошли.

## AG-009 — количество Excel выдано за неизвестную норму (P1)

## AG-010 — свободная hex36-строка попадает в trace без хеша (P2, подтверждён)
