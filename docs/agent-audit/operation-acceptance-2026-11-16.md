## Что проверяет положительный сценарий

Для каждой операции `positive_scenario` содержит понятную цель пользователя, исходную TEST-фикстуру, первое видимое действие в личном чате, способ подтверждения, независимое предметное постусловие и следующий шаг после успеха. Роль берётся из конкретной ячейки. Например:

| Операция | Проверяемый результат |
|---|---|
| `equipment_edit` | Изменено точное имя выбранного оборудования; остальные поля, другие карточки и прежняя история сохранены. |
| `task_assign` | После отдельного подтверждения сохранены проверенные сотрудники и время; до подтверждения назначения нет, повтор не создаёт дубль. |
| `report_submit` | Отчёт и свидетельства переданы инженеру; принятия работы ещё нет. |
| `report_review` | Независимый полномочный инженер принял или вернул точную попытку с историей; принятый факт появляется только при принятии. |
| `inventory_read` | Проверен реестр доступных объектов и оборудования, включая оборудование без заданий; пробелы сверены с данными. |
| `pattern_preview` | Даты воспроизведены штатным календарём; пять повторов в год не превращены в пятилетний интервал; заданий не создано. |
| `equipment_service_history` | Фактические отчёты и приёмка относятся к нужному оборудованию и периоду; неподтверждённая дата сдачи и неизвестное время не превращаются в полный исторический факт. |
| `workbook_readiness` | Проверены реальные исходные ячейки выбранных отправленных книг; количество не подменяет норматив, а неподтверждённые исходные числа не превращаются в рассчитанную численность. |
| `publication_publish` | Выпущен именно утверждённый актуальный diff, однократно; начатое/принятое и закрепления сохранены. |

Итог сверяется через независимое авторизованное чтение API, SQL в отдельной тестовой БД или hash файла. Допускается любая корректная последовательность разрешённых инструментов. Совпадение текста ответа, HTTP 200 или имя единственного инструмента не служит oracle. Независимые неисполненные пункты остаются pending/blocked; предложение изменения означает ожидание подтверждения, а не выполненную запись.

Для чтений и previews бизнес-состояние остаётся неизменным. Для изменений проверяются отсутствие записи до подтверждения конкретного payload, повторное применение, сохранность непрошенных полей и независимых данных. Секреты вводятся только в защищённые поля карточки, файлы поступают из личных вложений. После успеха повторное открытие ресурса/диалога должно показывать сохранённый результат.

## Виды доказательств

У каждой ячейки отдельные категории; прохождение одной не закрывает другую:

| Поле | Что можно доказать |
|---|---|
| `registered` | Операция и роль есть в зафиксированном capability manifest. |
| `reachability` | Реальный запуск достиг допустимой операции в нужном пользовательском сценарии. |
| `positive_e2e` | Настоящий локальный chat → tools → нужное подтверждение → проверенный результат и состояние данных. |
| `negative` | Проверена конкретная граница: запрет роли, чужой объект, конфликт, пустые/невалидные параметры. |
| `mocked` | Пройден тест с подменой модели/транспорта; не объявляется настоящим LLM E2E. |
| `api_domain` | Пройден бизнес-процесс API/БД/solver; способность свободного чата пройти его отдельно не доказана. |

`candidate_test_mentions` — только статические ссылки на тестовые функции, где встречается имя операции. Они могут вести к отрицательному, mock или неполному тесту. Экспорт не исполняет эти функции и не выводит из ссылки успешность или покрытие роли. Количество таких упоминаний не является метрикой качества.

## Источники требований и решения заказчика

Каждая спецификация содержит блок MVP, исходные PLN/AT/AN и зависимости D-01…D-09 по [MVP_SCOPE, §7 и §9](../MVP_SCOPE.md). Это продуктовая трассировка области, а не утверждение о полной реализации соответствующего требования одной операцией. Например, календарные операции относятся к MVP-05 и требуют подтверждения частот/политик D-03; создание деталей — к MVP-09 и ресурсу/единицам D-06; приёмка — к MVP-08 и полномочиям D-05.

Один и тот же блок MVP-11 добавлен всем операциям, поскольку здесь оценивается их доступность через ассистента. Подтверждение на синтетической фикстуре не утверждает реальные нормы, полномочия заказчика, полезность ML или готовность всего блока MVP. Неподдержанные продуктом операции будущего MVP не появляются в реестре как реализованные: этот реестр проверяет полноту **фактически зарегистрированного текущего API**.

## Воспроизведение и обновление

Экспорт и его unit-проверки работают офлайн, без БД, `.env`, каталога провайдера и генерации:

```powershell
python scripts/assistant_acceptance_matrix.py --write
python scripts/assistant_acceptance_matrix.py
python -m pytest tests/backend/test_assistant_acceptance_matrix.py -q
```

Для фактического прогона нужна отдельная БД с синтетическими пользователями/объектами, зафиксированный commit и hash начальных данных. Все генеративные испытания — исключительно установленная локальная Ollama. Внешние LLM и fallback запрещены независимо от ключей. Новые веса не скачиваются; предпочтение модели и прочие настройки работающей пользовательской версии не меняются.

Исполненный протокол можно импортировать отдельным артефактом, сохраняя исходный реестр обязательств:

```powershell
python scripts/assistant_acceptance_matrix.py --write --evidence var/local-run/executed-cells.json --output reports/local-run/acceptance-results.json
```

Вход — список записей с полями `operation`, `role`, `category`, `status`, `run_id`, точный 40-символьный `source_commit`, `fixture_sha256`, `artifact` и `test_node`. Для `positive_e2e=passed` дополнительно обязательны `provider=ollama`, фактический `model_ref` с digest, `mocked=false`, `goal_achieved=true`, `data_verified=true`, `no_unconfirmed_writes=true`. Это индекс протоколов: сами утверждения и oracle должны быть проверяемы в указанном артефакте, запись JSON не заменяет испытание. Все попытки сохраняются, включая неудачные; последняя определяет текущий статус ячейки. Другие роли и операции не наследуют успех.

## Выполненная проверка матрицы и остаток

При разработке выполнены **19 unit-проверок** генератора: полнота разрешённых пар, уникальность предметных постусловий, актуальность экспорта, остановка при новой операции без сценария, запрет внешней модели/cloud tag/mock/непроверенных данных для положительного E2E, независимость категорий и ролей, сохранение неудачных попыток. Первый запуск обнаружил устаревший экспорт после добавления тестовых ссылок: 17 passed / 1 failed; после регенерации 18 passed / 6,30 с. Обновлённый контракт со 173 операциями дополнительно проверен экспортом и тестами. Это не бизнес-E2E и не испытание LLM.

Обязательный остаток: выполнить и независимо сверить положительные сценарии всех нужных пар роль/операция, прикрепить протоколы и зафиксировать условия отказа/продолжения. Наличие 173 подробных сценариев и 708 зарегистрированных ячеек не означает промышленную готовность агента. 691 клетка остаётся not_run; прежние failed attempts не удаляются после нового PASS. Исторический PASS другой версии не закрывает приёмку финального источника.
