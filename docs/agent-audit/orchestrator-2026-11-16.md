## Исполнитель и состояния

`service.agent_turn` направляет каждое сообщение в один `orchestrator.run`. Прежние root-перехватчики task/inventory/production/workbook больше не завершают весь запрос по совпадению слов. Модель формирует типизированный план `GoalSpec`: конечная операция, область, точные пользовательские изменения и зависимости. Предметные специалисты — ограниченные сервером наборы инструментов. Права определяются актуальной сессией и API, не моделью.

Для известных предметных параметров `domain_adapters` разрешает точный инвентарный код, получает серверную ревизию и готовит вызов без дополнительного inference. Строгая существующая грамматика единственной полностью заданной команды остаётся защитой от неверных UUID/полей/экранированных имён. Она не перехватывает составные команды: независимые части сохраняются в общем плане.

Миграция **023** добавляет nullable workflow/resume-ссылку к turn и связь предложения с корневым поручением/пунктом. Уникальность `(workflow_root_turn_id, workflow_goal_id)` и блокировка корневого turn защищают от повторной карточки после сбоя между commit предложения и checkpoint. Данные старых переписок не переписываются. Отмена/права/CSRF/hash/revision/before snapshot остаются прежней границей исполнения.

`turn.status=completed` означает только окончание ответа. Цель отдельно бывает planned/running/completed/partial/blocked/awaiting_confirmation/uncertain/cancelled. Ответ модели и успешный вспомогательный поиск не завершают изменение. После подтверждения сервер проверяет receipt и авторизованное повторное чтение; неизвестное постусловие остаётся unverified. Потерянный dispatch не повторяется.

Продолжение передаёт `resume_turn_id` обычным транспортом сообщения. Сервер проверяет владельца/объект/роль, выбирает последний checkpoint этой линии и восстанавливает связи с уже сохранёнными действиями. Новый turn не повторяет старые изменения. GET чата только формирует представление workflow и не может затереть новый checkpoint исполнителя. Просроченный executing становится durable uncertain без повторной отправки.

## Факты и интерфейс

Календарные даты рассчитывает штатный `occurrence_pairs`; пять повторов в год не превращаются в пятилетний интервал. История привязана к конкретным отчётам и приёмке, часовому поясу и периоду. Изменяемая дата начала наряда не переносит прошлые попытки. Неизвестная/противоречивая дата явно делает доказательство частичным. Сохранённый регламент не является подтверждением производителя.

Проверенные снимки имеют источник, время, hash и scope. Они используются как контекст, а текущий результат требует нового авторизованного чтения. Межходовый кеш, способный подменять API после UI/MCP-записи, не включён без общего транзакционного сброса.

Техник или инженер первым действием отправляет поручение/файл. Затем видит пункты и незавершённые исходы, отдельно проверяет каждую карточку и подтверждает нужные изменения. После успеха состояние опирается на серверную проверку; после препятствия доступно продолжение. Черновик/вложения сохраняются, адрес чата и Back/Forward остаются прежними. Длительность подписана «Ответ завершён», а не «поручение выполнено». Новые виджеты ограничены 12 пунктами на turn; production/mobile/performance-приёмка фиксируется отдельно от unit.

## Испытания и ограничения доказательств

Единственная установленная модель на момент проверки — `qwen3.5:4b-q4_K_M`, pin `sha256:d8b0f5e9760cd1682034f292d7ef72ec46f432149be0df7574bf2d6e92e38c04`. 9B отсутствует. Генеративные проверки идут только через loopback Ollama, без pull/fallback/внешнего LLM и без записи пользовательских настроек. `verify_agent_local.py` устанавливает защиту Python-процессов/потомков, очищает внешние ключи, создаёт отдельную PostgreSQL и сверяет source/corpus/model provenance. Без `--live` реальный `/api/chat` запрещён; mock-транспорты проверяются отдельно.

Промежуточные результаты, не суммируемые из-за пересечений:

- 170 unit/grammar проверок предметных адаптеров, календаря, outcome и памяти — passed.
- Независимая HTTP/PostgreSQL проверка истории/core/security/outcomes — 70 passed, полный выбранный native pipeline exit0.
- Адаптация legacy chat/capability — 54 passed, выбранный native pipeline exit0, стабильный source/corpus на том срезе.
- Независимые explicit/staff/proposal/failed-read/scope — 65 passed; следующий artifact step обнаружил устаревший schema export. Это не полный pipeline pass.
- 38 UI unit проверок статусов, карточек и страницы — passed на промежуточном срезе; это не production browser/performance-приёмка.

Широкая exploratory регрессия на существующем audit Python 3.11/OR-Tools: 2347 passed, **98 failed**, 45 skipped, 1 xfailed. Все отказы сохранены и разбираются; часть — старые stubs/формулировки, часть — реальные регрессии, в том числе literal binding, staff metadata, файлы, предметные отчёты и planning workflows. Новые exploratory live-прогоны пока выявляют ошибки семантического плана; корректный календарь с непроверенной историей не засчитывается полной приёмкой. Приватные исходные протоколы не входят в Git.

Открыты: все положительные role×operation E2E; frozen-сравнение/повторы и SLA; полноценные runtime постусловия остальных изменений; автоматическая очередь/lease recovery; reconciliation uncertain; потоковые токены; покрытие RAG. Эти пункты не закрываются наличием новых классов, manifest или зелёным HTTP.

## Следующая контрольная точка: фазы и доказательства

После первого integration-коммита `e4d965d` исправлены две ошибки независимого security review: `_` в идентификаторе пункта больше не работает как SQL wildcard при выборе phase receipts; требования `manufacturer_document`/`user_decision` и вид доказательства проверяются на всех переходах, включая строгую привязку явной команды. Предложение действия не является доказательством сохранённых данных. Обычный разговор получает `answered/response_only`, не бизнес-успех.

Утверждение и публикация продолжаются только по принадлежащему этой линии успешному receipt и свежему совпадающему API-состоянию. Подтверждение промежуточной фазы возвращает цель в planned для следующего шага; сам receipt не завершает многофазное поручение. Испытаны настоящий CP-SAT и цепочка утверждения/выпуска, а также подмена receipt и сбой между commit и checkpoint.

Полная аналитика заданий объединяет summary/equipment/dates/duplicates одного scope/snapshot; прочитанные секции и неполнота сохраняются. Прочтение XLSX не завершает аналитическую цель, если подготовка объяснения прервалась. Проверенное имя оборудования может передать ID соседнему пункту лишь при точном упоминании кода в исходном запросе и названии цели, без подмены свежего API историческим ответом.
