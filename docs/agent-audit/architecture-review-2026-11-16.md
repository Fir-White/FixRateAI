# Архитектурный аудит исполнительного агента — 16.11.2026

## Вывод

Текущий агент предоставляет безопасный доступ к большому набору API, но не имеет единой модели пользовательского поручения и проверяемого условия его завершения. Поверх общего LLM-цикла накопились распознаватели формулировок и отдельные сценарии, которые могут перехватывать запрос и завершать ответ после выполнения только части задачи. Зарегистрированный endpoint означает техническую доступность операции, а не способность агента самостоятельно пройти весь пользовательский сценарий.

Целевое требование владельца: любое действие, доступное текущей роли в интерфейсе, можно поручить чату; агент собирает известные данные, уточняет только действительно недостающие пользовательские решения, готовит понятное подтверждение, выполняет разрешённое действие и проверяет результат. Смена пароля остаётся исключением. Это требование для текущей реализации в полном объёме **не доказано и местами прямо опровергается воспроизведениями**.

Проверена рабочая версия kran_dev поверх `13841cd` с ещё не опубликованным выбором модели (миграция 022). Исследованы runner, prompts, API/MCP transport, tool validation, read repair, предметные обработчики, evidence/grounding, память/файлы, adapters Ollama/AI Tunnel, подтверждение и отображение результата, схемы хранения и тестовые oracle. При этом аудите прикладная логика не переписывалась. Изменения предыдущей итерации выбора модели сохранены.

## Метод и границы

- Прочитаны последние 9 сохранённых turn локального preview: 8 completed и 1 OLLAMA_TIMEOUT. Это небольшая пользовательская история, не статистическая оценка качества.
- Выполнены 4 настоящих сообщения через авторизованный API на `http://localhost:8010` с выбранной `aitunnel/qwen3.5-9b`, в трёх отдельных проверочных диалогах. Вызовы к модели и backend не подменялись.
- Изменения оборудования **не подтверждались**. Создавались только проверочные чаты и предложения; после записи результатов удалены только эти чаты. Пользовательские диалоги и выбор модели сохранены. Подтверждение/публикация/планирование рабочих данных не запускались.
- Выполнены отдельные детерминированные пробы dispatch/history/schema-budget и расчёт фактической периодичности штатным календарным модулем, без записи в БД.
- Приватные исходные протоколы и исполняемые пробы: `var/agent-architecture-audit-20261116/`. Они не входят в Git. Чувствительная runtime-конфигурация/ключи в отчёт не включены.
- Предыдущие 835 backend/ML и 27 UI checks относятся к итерации выбора модели. Они не повторялись и не выдаются за успешную проверку найденных здесь проблем. Нынешние сообщения — целевые контрпримеры, а не случайная выборка для процента надёжности.

## Фактический путь сообщения

1. `integration/assistant.py` проверяет сессию, CSRF, владельца чата, scope, ключ повтора и ревизию выбранной модели; сохраняет turn и запускает `BackgroundTasks`.
2. `assistant/service.py` собирает каталог текущей роли, последние 12 turn, до 8 результатов действий и сведения о файлах. Решение включать историю принимает `needs_history` по регулярным выражениям.
3. До общего агента последовательно проверяются task analysis, inventory, production workflow и Excel readiness. Некоторые ветви сразу записывают completed и возвращают текст.
4. В общем пути LLM сначала выбирает до 8 инструментов. Полные схемы выбранных инструментов добавляются только в пределах 18000 символов.
5. LLM выдаёт собственный формат `AgentStep`: answer и до 3 calls. Cloud arguments — JSON внутри строки, Ollama использует специальный объектный адаптер. Native provider `tools/tool_calls` в этом пути не используется.
6. Сервер валидирует и выполняет чтения; изменяющий вызов сохраняет предложение. **После первого предложения цикл прекращается.**
7. Отдельная генерация final/conversation превращает текущие observations в текст. В ряде предметных ветвей текст формируется без неё.
8. Подтверждение проверяет неизменность предложения/исходного состояния и повторно вызывает API. UI обновляет карточку. Продолжение общего плана после approval автоматически не запускается.

## Находки и причины

### AR-01 — P0: нет единой проверки полноты поручения

Подтверждено кодом и двумя живыми примерами. В `service.py:316–337` task report имеет приоритет над inventory; найденный отчёт может немедленно завершить turn. В `service.py:470–487` найденный код оборудования и упоминание регламента ведут к `answer=regulation_report(...)`, даже если вопрос содержит историю, объяснение даты и проверку документов. Чистое выполнение чтения становится завершением пользовательской задачи.

Решение: до выбора executor получить явный список обязательных результатов: область, период, сущности, требуемые чтения/изменения/проверки. Предметный обработчик возвращает typed result для одного шага, а не завершает всю беседу. Completion gate закрывает поручение только после покрытия всех пунктов либо перечисляет конкретные неустранимые ограничения. Нельзя заменять цель шаблонным отчётом.

### AR-02 — P0: один write на ответ и отсутствие продолжения после approval

Подтверждено: `service.py:614–617` завершает цикл при первом proposal; выход из внутреннего цикла происходит ещё раньше. Схема AgentStep позволяет до трёх calls, но второй write не доходит до исполнения подготовки. `integration/assistant.py` после confirm возвращает только действие; `ActionCard.tsx` обновляет UI через onChanged, а следующая задача агента не возобновляется. Сохранённых целей и зависимостей шагов нет.

Решение: persisted workflow с шагами, зависимостями и состояниями `needs_input`, `reading`, `awaiting_confirmation`, `executing`, `verifying`, `blocked`, `completed`. Для двух независимых изменений — две проверяемые карточки/группа с явной семантикой подтверждения. Для зависимого процесса — продолжение после результата предыдущего шага с повторной авторизацией. Не обещать транзакционный rollback группы, пока его нет в предметном API. Повтор события approval не должен повторять запись.

### AR-03 — P1: память представлена текстом и эвристикой включения истории

Подтверждено отдельными вызовами `needs_history`:

- «В 14:00» после «На какое время назначить начало?» → false.
- «На следующую неделю» после «На какой период построить график?» → false.
- «Увеличь до двух часов» после сообщения о длительности операции → false.

История ограничена 12 turn/15000 символов, action results — 8 записями; текущие observations с инструментальными ответами не являются долговременным предметным состоянием. `production_workflow.py:173–220` подбирает прошлые успешные действия по имени инструмента; не во всех ветвях есть привязка к цели, выбранному периоду и конкретному черновику. Последнее — подтверждённый механизм и риск неверного выбора, но отдельная ошибочная публикация здесь не воспроизводилась.

Решение: хранить текущую цель, выбранные сущности и их ревизии, ожидаемый тип ответа, период, результаты шагов и ссылки на источники. Короткий ответ заполняет ожидаемое поле. Новая цель создаёт отдельный контекст выполнения. История нужна для языка, но не заменяет IDs и состояние процесса. Смена пользователя/роли/объекта инвалидирует применимость старого состояния.

### AR-04 — P0: свободный final способен сообщать неподтверждённую бизнес-логику

Подтверждено ответом о пятилетнем цикле при чтении только tasks_find. `finish_answer` формирует свободный текст по observations; `failed_read_report` срабатывает только когда все чтения провалились. Один успешный, но нерелевантный запрос не ограничивает последующие утверждения. Специальный строгий `evidence.py` защищает task analysis, но не все ответы агента. System prompt запрещает выдумывание, однако не является проверкой фактов.

Решение: расчёты, календарная семантика, допустимость назначения, нормы и агрегаты возвращаются предметными функциями с источником/областью/полнотой. Для ключевых утверждений final получает проверенные facts, а не только произвольные JSON. Непрочитанное или отсутствующее следует различать. Explain recurrence должен вызывать настоящий генератор, а проверка паспорта — существующий разрешённый источник документов; при отсутствии такого источника сообщать именно об этом. Общие знания нельзя выдавать за локальные регламенты.

### AR-05 — P1: LLM управляет низкоуровневым HTTP-контрактом

`AgentCall.tool` — обычная строка; `arguments_json` у cloud — строка с JSON. Проба с несуществующим инструментом и `wrong_id="not-a-uuid"` проходит AgentStep. Она будет отклонена позже tool/backend validation: защита работает, но модель уже потратила шаг. Ollama grammar задаёт имена read/write, но body/path/query остаются обобщёнными объектами. Ни один из проверенных describe-ответов не содержит outputSchema. Модель должна узнавать, где `id`, `task_id`, `equipmentId`, `equipment_id`, revision и preview token, из текста и примеров.

Решение: отделить API-адаптер от предметных инструментов. Обеспечить tool-specific аргументы и результаты; использовать native tool calling там, где контракт выбранного провайдера это подтверждает. Names/IDs разрешаются отдельным авторизованным resolver; revision и допустимые окна заполняет сервер. Существующий `assignment_prepare` — полезный образец такого предметного помощника. Переход на native tools сам по себе не решит память и выполнение составной цели.

### AR-06 — P1: большой каталог, отдельная маршрутизация и тихая потеря схем

Текущий manifest: 170 tools/74 writes. Главный инженер видит 160 tools/66 writes; каталог имён/названий — 16938 символов, assistant prompt — 10280, router prompt — 2914. Все input schemas этой роли суммарно 268817 символов; **весь этот объём одновременно не передаётся**, но выбор до восьми схем ограничен 18000 символов. Проба типового набора планирования включила 5 схем и молча пропустила `optimization_start`, `optimization_apply`, `publication_prepare`.

Router выбирает инструменты без аргументов; исполнитель заново решает, как их вызвать. Пустой route допускает direct_answer. Describe содержит название и input schema, но почти не описывает бизнес-предусловия и результат.

Решение: предметные группы инструментов и зависимости, общий типизированный план вместо двух независимых интерпретаций задачи. Выбор схем должен быть явным: если схема не поместилась, её требуется загрузить до вызова. Чтение сущностей и подготовка команды должны иметь компактные контракты. Не отправлять весь каталог в каждом шаге без необходимости.

### AR-07 — P1: распознаватели вмешиваются в смысл и период

Детерминированные пробы:

- «Измени ресурс установленной детали насоса НС-01 на 1000 моточасов» → `production_workflow.intent == materials`; эта ветка только читает ресурс и завершает ответ. Write не подготовлен.
- «Покажи нагрузку по всем заданиям на следующий календарный месяц» → task handler, но `analysis_scope.selectors == {}`. Относительный период с дополнительным словом пропущен, возможна сводка без ограничения периода.
- Bare inventory-code regex принимает слово «из-за» за инвентарный код в исследованной составной формулировке. В конкретном живом запросе до этой ветки выполнение не дошло из-за более раннего task handler.

Решение: единое semantic intent со строгими типами операции/области/дат, нормализация относительных периодов серверными часами и проверка полноты селекторов. Регулярные выражения оставить для форматов UUID/дат и строгих правил, а не для выбора пользовательского процесса. Неразрешённую неоднозначность явно уточнять, не расширять область молча.

### AR-08 — P1: общие лимиты без управления стоимостью выполнения задачи

AI Tunnel client устанавливает общий deadline при создании; default — 90 с на routing, все JSON rounds, ожидание read и final. Есть MAX_STEPS=12/MAX_TOOL_CALLS=20, до трёх calls за round выполняются последовательно. Поиск, который можно выполнить предметным resolver, требует нескольких inference. Финал делит бюджет с исполнителем; проверка «осталось меньше 12 с» не гарантирует успешный final. В живом повторе получен AITUNNEL_TIMEOUT за 90,229 с. Это факт отказа, а не доказательство отсутствия регламента.

Решение: явные бюджеты фаз, метрики inference/tool latency и reserve на завершение; независимые безопасные чтения выполнять параллельно после проверки зависимостей. Ошибки аргументов исправлять по схеме в ограниченных рамках; domain blockers не маскировать предложением уточнить произвольный период. Сохранённый план позволяет продолжить разрешённые чтения, а не начинать всё заново. Нельзя автоматически повторять write после потери ответа.

### AR-09 — P1: completed означает завершение ответа, а не достижение цели

Реальные частичные отчёты и одна карточка вместо двух имеют status=completed без error_code. Даже корректный отказ/уточнение обычно completed. Показатель «8 completed из 9» не является показателем успешности пользовательских задач. UI может показать «Выполнено за …» до выполнения предложенного изменения.

Решение: раздельно хранить завершение генерации, достижение цели, полноту фактов и состояние каждого действия. Бизнес-успех требует проверенного постусловия; недостающий пункт оставляет цель partial/blocked. Отказ по роли — отдельный корректный исход, не write success и не transport failure.

### AR-10 — P1/P2: после подтверждения нет предметного отчёта и автоматической сверки цели

Backend повторно проверяет данные и права, выполняет один API command и сохраняет status/result — полезная основа. Однако общий confirm не имеет спецификации ожидаемого пользовательского постусловия. ActionCard в основном показывает поля команды и раскрываемый JSON результата. Имена сотрудников/оборудования не разрешаются единообразно для всех операций, часть UUID остаётся в карточке. Нового понятного ответа о результате шага/следующем шаге не создаётся автоматически.

Решение: перед подтверждением — предметный diff «что/где/было/станет/последствия», после — чтение целевого ресурса или проверка явного transactional receipt, итог понятным языком и продвижение workflow. Expected revision/hash/API keys остаются техническими сведениями; секреты — только защищёнными полями. Для uncertain нужны предметные read-only reconciliation, а не повтор записи.

### AR-11 — P2: выполнение внутри веб-процесса неустойчиво к перезапуску и нагрузке

`BackgroundTasks` и process-local semaphore(2) не являются устойчивой очередью. Утрата процесса приводит к interrupted при последующем чтении; автоматического безопасного восстановления плана нет. При заполнении слотов возвращается 429. AI Tunnel/Ollama вызываются с stream=False; прогресс показывает этапы, а не готовые фрагменты ответа. Структурированная tool trace уже есть, но нет единого goal outcome, времени каждой inference, token usage и сохраняемого плана, связывающего ошибку с потерянным пунктом поручения.

Решение: очередь/worker с persisted job и lease, сохранение checkpoints, stop и авторизованное продолжение. Read можно безопасно восстановить; write — по ключу/receipt/reconciliation. Трассировать routing, доступные/загруженные схемы, фазы, model_ref, usage, причины отказа и postconditions без секретов и скрытых рассуждений. Streaming улучшает воспринимаемую задержку, но не исправляет семантику.

### AR-12 — P1: проверки границ API не измеряют выполнение поручений

`test_assistant_capabilities.py` доказывает покрытие маршрутов и ряд прав/файловых сценариев. `test_agent_redteam_matrix.py` исполняет корпус с `llm_called=False`: schema refs, invalid_root, invalid_query, forbidden_role, foreign_conversation. Эти проверки нужны и сохраняются. Но 628 таких случаев не означают 628 успешно выполненных поручений LLM. Live suites есть, отдельно opt-in, используют существенно меньший набор; часть oracle проверяет слова/числа в тексте. Они не контролируют всю полноту свободного ответа и все positive writes каждой роли. Текущие четыре контрпримера проходят мимо прежнего критерия «зелёного транспорта».

Решение: acceptance matrix «роль × операция × состояние × формулировка». Для каждого поддержанного действия — настоящий chat→proposal→human confirm→API→проверка БД/ресурса, запрет записи до confirm, replay/lost response и сохранение непрошенных полей. Для языка — перефразировки, короткие продолжения, смена цели, несколько пунктов и относительные периоды. Успех определяет независимое предметное постусловие, а не имя tool или наличие одного слова в ответе. Критичные даты/арифметика проверяются детерминированно.

## Что сохранять при исправлении

Не ослаблять серверные схемы, RBAC/ownership/site/role, CSRF, optimistic revisions, проверку before snapshot, hash предложения, защищённые поля, разделение предложения и исполнения, at-most-once dispatch и uncertain после потери ответа. Сохранить общий API и MCP как транспорт, строгую аналитику на PostgreSQL, проверку полноты/единиц и серверное время. Нынешние дефекты не являются основанием дать модели SQL, shell, произвольный URL или право самой подтверждать изменения.

Ни RAG по всем документам, ни дополнительное обучение модели не заменяют исполнительный workflow. Документные источники нужны для конкретных вопросов о паспортах/регламентах; утверждения о календаре сначала должны опираться на существующий генератор.

## Последовательность исправления

| Этап | Конкретная работа | Проверяемый результат |
|---|---|---|
| 1 — достоверность | Закрепить четыре воспроизведения и короткие history/period/dispatch случаи; убрать завершение всей задачи из частных readers; связать календарное объяснение со штатным генератором | Частичный ответ не становится полной задачей; НС-01 не превращается в пятилетний цикл |
| 2 — единый исполнитель | Модель цели/области/шагов, persisted state, resolver сущностей/дат, заполнение технических токенов сервером, условия завершения | Любое поддержанное одиночное действие имеет единый жизненный цикл; краткое уточнение не теряет цель |
| 3 — подтверждение и несколько действий | Группы независимых карточек, зависимости, continuation после approval, postcondition/read receipt и uncertain reconciliation | Два изменения дают два явных результата; повтор не дублирует запись; зависимые шаги исполняются в правильном порядке |
| 4 — инструменты и бюджет | Предметные адаптеры поверх всего API, input/output types, проверенный provider tool transport, инструментальные группы, фазовые бюджеты и trace | Модель выбирает действие и смысловые значения; контракты/ревизии не угадываются; схема не теряется молча |
| 5 — приёмка ролей | Сопоставить каждую фактически доступную UI-операцию всех 6 ролей с positive e2e и запретами | Список неподдержанного явный; готовность измеряется достижением пользовательской цели |
| 6 — эксплуатация | Устойчивая очередь, recovery/stop, streaming и понятные business result cards | Рестарт/нагрузка/потеря ответа не превращаются в необходимость вручную начинать задачу заново |

Первые доказательные сценарии для нового исполнителя: назначить одного человека на ближайшее подходящее ТО; изменить конкретное поле оборудования; получить полный реестр и регламенты с заданным периодом; подготовить два изменения; сохранить и передать отчёт исполнителя с фото; принять/вернуть отчёт инженером. Затем расширить тот же механизм на остальные операции, а не добавлять распознаватели отдельных фраз.

Сроки и готовность всех 66 write главного инженера этим аудитом не оцениваются. Перед демонстрацией заказчику нужен согласованный перечень сценариев с реальными положительными доказательствами и понятным перечнем ограничений.
