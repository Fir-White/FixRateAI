# API, сессии и полномочия

Назначение: граница HTTP и проверка доступа. Код: [FastAPI](../../backend/app/main.py), [DTO](../../backend/app/schemas/maintenance.py), [авторизация](../../backend/app/security). Актуальная спецификация маршрутов доступна в `/docs` и `/openapi.json` запущенного backend.

Строгие REST-модели: [maintenance_api.py](../../backend/app/schemas/maintenance_api.py), [исходные примеры](../../backend/examples/maintenance_api_examples.json). Они описывают также целевые структуры, не все из которых имеют отдельный HTTP endpoint. Фактически доступные маршруты определяет OpenAPI. Неизвестные поля отклоняются, идентификаторы генерирует сервер; исходная норма не преобразуется в минуты без подтверждённого основания.

Канонические DTO: [maintenance.py](../../backend/app/schemas/maintenance.py),
их документальная копия [maintenance_contracts.py](../architecture/contracts/maintenance_contracts.py)
и [JSON Schema](../architecture/contracts/maintenance.schema.json). Все три обновляются совместно.
`maintenance-0.1` — единый развиваемый контракт текущей dev; новые календарные
варианты добавлены вместе со всеми потребителями. Прежние сохранённые снимки
сохраняют исходные поля и хеши. Версия вычисления теперь `calendar-rules-v2`.

Фактический HTTP-контракт предоставляет OpenAPI `/openapi.json`. Browser UI
использует CamelCase-проекции `/api/v1/maintenance/ui`; команды и настройки —
snake_case DTO. Это явная граница сериализации, а не два независимых расчёта.
Frontend не вычисляет нормативные даты или пригодность бригады повторно.

## Предметные структуры

| Структура | Правило |
|---|---|
| `CalendarPattern` | Общая периодичность обслуживания и смен: день, неделя, месяц, календарный квартал, год, число раз за год, конкретные даты; ISO-чётность и исключения |
| `RecurrenceRule` | `calendar_pattern` с общими настройками; `calendar_interval` для отсчёта от выполнения/совместимости; `explicit_dates` для сохранённых годовых списков; `runtime` хранит порог наработки, не угадывает календарную дату |
| `OperationVersion` | Численность, исходная норма и единица, отдельная длительность, допуски, инструкция и чек-лист одной версии |
| `ForecastSnapshot` | Один объект/оборудование/привязка/версия, отсечка принятой истории, snapshot ID и SHA-256 |
| `ForecastResult` | Одинаковая структура для алгоритма и AI; исходная дата, версия, состояние, неопределённость, причина и elapsed time |
| `OrchestrationDecision` | Ссылки на оба результата, версия политики, выбранная дата либо `needs_input/manual_review`, обоснование |
| `AssignmentCommand` | Только предложенные исполнители и точный интервал, причина и ожидаемая ревизия; не факт назначения |
| `Assignment` | Подтверждённое назначение и снимки допусков, сохранённые BE05 |
| `ErrorResponse` | `schema_version`, `error={code,message,details,request_id}` и совместимое строковое `detail`; входные значения и пароли не попадают в ошибку |

Все даты — местные календарные даты объекта, timestamps — aware ISO 8601.
Интервалы `[start,end)`. Нормативный день не превращается в дату следующей полуночи
в интерфейсе. Рабочие роли: `admin/dispatcher/engineer/executor`.

## Оборудование, правила и работа

| Метод / путь после `/api/v1/maintenance` | Поведение |
|---|---|
| GET `/management/catalog` | Доступные системы, типы и допуски |
| POST `/management/systems`, `/management/equipment-types`, `/management/skills` | Справочники; глобальные типы создаёт администратор |
| GET/POST `/equipment` | Список с пагинацией / создание; scope задаёт сессия |
| GET/PATCH/DELETE `/equipment/{id}` | Чтение / изменение с ревизией / вывод из эксплуатации; история не удаляется |
| GET/POST `/equipment/{id}/service-configurations` | Чтение / создание настраиваемого обслуживания |
| PUT `/equipment/{id}/service-configurations/{binding_id}` | Новая версия с выбранной даты; действующие задания не переписываются |
| POST `/tasks/{id}/cancel` | Диспетчер отменяет не начатое задание с причиной, освобождает назначения, сохраняет историю |

Управление оборудованием, обслуживанием, сменами и бригадами доступно
администратору/диспетчеру; инженер читает настройки и выполняет приёмку.
Создание заданий, назначение и отмена требуют роли диспетчера.
Мутации требуют CSRF. Новые API не принимают роль или произвольный объект от клиента.

[команда](../../frontend/src/pages/WorkforceSettingsPage.tsx),

## PostgreSQL и ошибки

Единственная физическая схема — миграции 001–008 и отражаемый ORM.
Не использовать `create_all()` или вторую таблицу сессий из исходной ветки.
Уникальные ключи, транзакционные блокировки, ревизии и снимки проверяются сервисами.
При отказе транзакции не возвращается успех.

401 — нет сессии; 403 — доступ/CSRF; 404 — отсутствует или скрыт ресурс;
409 — ревизия/состояние/ограничение; 422 — неверный ввод; 503 — БД недоступна.
`X-Request-ID` связывает запрос и структурированную ошибку. Пригодный регламент
остаётся доступным при отказе AI. `unavailable` не обозначается успешным прогнозом.


## Дополнения управления

POST management/calendar-pattern/preview возвращает даты шаблона за year/month без записи. POST management/staff/{user_id}/qualifications/{skill_id}/revoke принимает expected_revision, сохраняет отзыв и аудит, конфликтует с действующей будущей бронью. Изменение существующего допуска через PUT требует его текущую ревизию.

ServiceConfiguration.checklist содержит объекты text/answer_kind/unit/required/visual_verifiability/photo_required; типы boolean/number/text сохраняются в замороженном снимке. При создании привязки operation_id позволяет использовать существующую операцию той же системы; её code совпадает, параметры/название/чек-лист сохраняются в отдельной версии. Отсутствие operation_id создаёт новую операцию. PATCH equipment принимает частичные изменения и expected_revision; properties сохраняются.

## Проекции UI и команды выполнения

`/docs` и `/openapi.json` формируются настоящим сервером. Раздел `ui` — явные camelCase проекции для SPA; он не выдаётся за полный REST контракт из проектной документации. Канонические DTO ML остаются snake_case `maintenance-0.1`.

| Метод и путь | Поведение |
|---|---|
| `GET /api/health` | Готовность подключения к БД |
| `GET /api/v1/maintenance/ui/equipment[/{id}]` | Реестр или `{equipment,history}` |
| `GET …/ui/tasks[/{id}]` | Список либо `{task,execution,review,decision}` |
| `GET …/ui/calendar?year=…&month=…` | Сохранённые вхождения выбранного месяца |
| `GET …/ui/calendar/preview?year=…&month=…` | Диспетчер/инженер: read-only расчёт ALG02 из PostgreSQL, даты и диагностика по привязкам; без записи плана |
| `GET …/ui/tasks/{id}/assignment-context` | Диспетчер: серверные условия и границы подбора ALG03 |
| `POST …/tasks/{id}/assignment-preview` | `{expected_revision,start_local,end_local,crew_id?}`; диспетчер, CSRF; рекомендация состава/времени, диагностика и каноническая команда без сохранения |
| `POST …/tasks/{id}/assign` | `AssignmentCommand` + `crew_id?`; диспетчер, CSRF; повторная проверка под блокировками, сохранение полного состава/времени/снимков/ревизии/аудита одной транзакцией |
| `POST …/calendar/generate` | Диспетчер, CSRF; `{year,month,preview_token,idempotency_key}` → оба прогноза, решение, draft-задания и предложения бригад. Атомарная запись, повтор без дублирования |
| `GET …/ui/comparisons[/{run_id}]` | Интегрированные сохранённые сравнения |
| `GET …/ui/quality` | Задания на приёмке или доработке |
| `POST …/tasks/{id}/start` | `{expected_revision}`; новая попытка из назначенного задания или доработки |
| `PUT …/tasks/{id}/report` | `{expected_revision,narrative,answers:{item_uuid:value}}`; запись своего черновика |
| `POST …/tasks/{id}/photos` | Multipart: `expected_revision,checklist_item_id,phase,view_key,file` |
| `GET …/photos/{id}/content` | Авторизованное чтение файла; короткий путь `…/photos/{id}` также работает |
| `POST …/tasks/{id}/submit` | `{expected_revision}`; проверка чек-листа/пар фото, заморозка |
| `POST …/tasks/{id}/review` | `expected_revision,execution_id,verdict,reason`, необязательные `reviewed_ai_result_id,additional_evidence_refs` |
| `POST …/tasks/{id}/forecast` | `{expected_revision}`; построение/сохранение общего снимка и результатов |
| `POST …/tasks/{id}/photo-review` | `{expected_revision,comparability_confirmed:false}`; ML/CV для текущей submitted-попытки |

Все многоточия в таблице означают `/api/v1/maintenance`. Изменяющие запросы после входа требуют `X-CSRF-Token`. Frontend читает его из отдельной `fixrate_csrf` cookie. Изменения ревизии клиента не принимаются: backend блокирует строку задания и проверяет `expected_revision`, затем увеличивает ревизию сам.

Коды HTTP: 401 — нет активной сессии; 403 — роль/CSRF/собственная приёмка; 404 — ресурс не найден или скрыт областью доступа; 409 — состояние, ревизия или конфликт ограничений; 422 — неполные/неверные данные; 503 — отказ БД. Runtime возвращает канонический ErrorResponse с error.code/message/details/request_id и совместимым строковым detail. X-Request-ID позволяет сопоставить ошибку с запросом; секреты и исходные значения ввода в неё не включаются.

Чтение не создаёт demo записи. Неподдерживаемые маршруты возвращают 404; они не заменяются фиктивными успешными endpoints. Исторические SQL-прогнозы без `comparison_snapshot.ui` сохраняются в БД, но не отображаются как полноценные сравнения нового формата: необходим явный backfill после получения недостающих полей.


## Транзакции и защита команд

Сессия — случайная opaque cookie `fixrate_session`, HttpOnly, SameSite=Lax, срок 8 часов. В БД хранится SHA-256 токена, а не его исходное значение; пароль — PBKDF2-SHA256 с солью и 600000 итераций. Заголовки роли/пользователя не являются удостоверением личности. Отзыв членства действует на существующую сессию.

| Роль API | Доступ в текущем runtime |
|---|---|
| admin | Чтение реестра, заданий и сравнений; не приёмка и не выполнение за исполнителя |
| dispatcher | Реестр, календарь, задания, подбор работников/бригад, запуск/чтение прогнозов |
| engineer | Реестр, календарь, задания, прогнозы, очередь, фотоанализ и решение о приёмке |
| executor | Только назначенные задания; связанное оборудование/собственная история/календарь; изменение своего текущего черновика |

005 принимает новые канонические роли. Старые значения сохраняются: `executive → admin`, `chief_engineer → engineer`, `engineer → engineer`, `technician → executor`. Диспетчер создаётся с ролью `dispatcher`; начальник инженерной службы не становится диспетчером по неявному предположению.

Все обращения ограничены объектом активной сессии. Для исполнителя дополнительно проверяется действующее назначение. Инженер не может принимать собственный отчёт или задание, в котором он был исполнителем. Фото проходят те же проверки. Файлы не публикуются отдельной незащищённой статикой; отдача использует `private, no-store` и `nosniff`.

Сдача, решение и аудит фиксируются одной транзакцией. Файловая запись удаляется при неуспешной транзакции загрузки; UUID пути создаёт сервер. Процессный crash между записью файла и commit может оставить бесхозный файл — сборщик такого мусора пока не реализован. Заморозка отчёта обеспечивается HTTP сервисом; прямой SQL-доступ администратора БД не ограничен отдельными immutable-триггерами.
