# Автоматическое размещение черновиков

[Общая модель](draft-plans.md) · [План](../PLAN.md) · [Проверки](verification.md) · [Производительность](performance.md).

Для подготовленного варианта теперь доступно отдельное [утверждение и первичная публикация](publication.md). Применение результата оптимизации всё ещё создаёт только новую версию черновика. Замена уже опубликованного состава и полный Planning Agent остаются последующим объёмом.

В сохранённой версии каталожного плана появился блок «Автоматическое размещение и сравнение». Пользователь запускает расчёт, сравнивает базовое размещение по ближайшему сроку с балансировкой CP-SAT, просматривает бригады и применяет один вариант с причиной. Применение создаёт следующую версию черновика. Публикация, резервирование людей и создание нарядов этим действием не выполняются.

## Вход и ограничения

Вход — сохранённые обязанности/сегменты, подтверждённые решения строк, нормы/бригады/делимость, окна и зависимости. Часы, активы, IDs и состав операций не изменяются. Число частей задаётся в ручном редакторе до расчёта: оптимизатор пока не выбирает разбиение самостоятельно. CONTINUOUS_WORK размещается соседними частями одной бригады; партии сохраняют привязки активов.

Снимок ресурсов включает доступность, отсутствие, глобальную занятость сотрудников, допуски и занятость оборудования. Неизвестные ресурсы не становятся свободными автоматически. Полезная ёмкость требует подтверждённой policy; 24 часа в тестах — синтетический ввод, не универсальная норма или заключение о допустимом режиме труда. Полные нормы отдыха, дополнительные сервисные окна и материалы остаются за пределами этого этапа.

По умолчанию размещения сохраняются. Флаг перепланирования позволяет перемещать только незакреплённые части; закреплённые время и бригада неизменны. Новые начала выбираются по местной сетке 15/30/60 минут и границам доступности. Новая длительность округляется вверх до целой минуты без изменения нормативных чел.-часов. Учитываются часовой пояс, перенос ночного события на следующие сутки и запас до начала. Прежние допустимые размещения включаются отдельными кандидатами с точными датами.

Оба варианта проходят общий `draft_validator`; native solver не обходит его. Отвергнутый вариант не выдаётся для применения. Частичное допустимое размещение можно сохранить как неполный черновик; оно не считается полностью обеспеченным графиком.

## Алгоритмы и метрики

Baseline `earliest-due-first-v1` воспроизводимо размещает сначала закрепления, затем работы по сроку с первой подходящей бригадой. OR-Tools CP-SAT использует булевы варианты начала, целый состав бригады, optional intervals/NoOverlap, ограничения дней, окон, допусков, зависимостей и ёмкости. Дробные «исполнители» из деления часов на смену не назначаются.

Цель `coverage-then-segments-then-weighted-balance-v1`: сначала максимум полностью размещённых корневых работ, затем максимум сегментов, затем взвешенные снижение дневного пика, разброса загрузки людей, изменений и более раннее выполнение. Первые два приоритета имеют ограниченные доминирующие коэффициенты. Веса последнего уровня задаются в UI.

Метрики: покрытие, нормативные часы, неразмещённые части, пик часов/дневной полезной ёмкости, использование людей, разброс относительной загрузки и переназначения. Нагрузка ёмкости использует зарезервированное время присутствия и может превышать нормативные часы после округления. Отношения при неполных ресурсах возвращаются `null`. `unfilled_slots` — места в бригадах неразмещённых частей, а не штатная численность здания.

`OPTIMAL` относится **только** к конечной модели кандидатов, а не всем минутам/разбиениям/технологиям. `FEASIBLE` не доказывает оптимальность. Если полный охват недостижим в полностью рассмотренной модели, `coverage_status=INFEASIBLE`; при ограниченном поиске — UNKNOWN. Полный проверенный график имеет покрытие FEASIBLE независимо от доказательства оптимальности. Нехватка данных, отсутствие решения до таймаута и противоречивые закрепления различаются диагностикой. [Официальные статусы CP-SAT](https://developers.google.com/optimization/cp/cp_solver).

## Фоновый процесс и бюджеты

Миграция 016 добавляет `draft_optimization_runs`: исходную revision, автора, параметры/fingerprint, приватный снимок, состояние/lease, два варианта и применённую revision/kind. Путь состояния: queued → running → succeeded/failed либо cancel_requested → cancelled. Отмена очереди сразу терминальна; отмена работающего расчёта имеет приоритет над поступившим результатом.

Очередь хранится в PostgreSQL. Координатор держит один глобальный advisory slot и запускает отдельный spawn-процесс: только JSON и канал отмены, без ORM-сессии/реквизитов БД. После потери владельца работа получает WORKER_LOST, а не успех; запрошенная отмена завершается отменой. Shutdown ограничен, зависший процесс завершается принудительно. `OPTIMIZATION_WORKER=false` отключает запуск (503), сохраняя ручной режим.

Лимиты: 1–30 секунд плюс ограниченный запас запуска/IPC, один CPU worker CP-SAT; до 500 сегментов, 512 кандидатов на группу, 20000 кандидатов и 200000 переменных выбора; снимок до 24 МиБ. Незавершённых расчётов: один на черновик, два на объект, 16 глобально. Усечение модели явно снимает доказательство оптимальности/невозможности, исходные работы не удаляются. История/размещения — по 25; diagnostics и примеры validator — первые 25 с полными счётчиками причин. Снимки ресурсов и чужие задания клиенту не выдаются.

Зависимости закреплены в `requirements-solver.txt`, включённом в основной requirements и Docker build. Подтверждённые runtime: native Python 3.11 и контейнер Python 3.12; версии установлены отдельно без обновления существующих ML-пакетов.

## API и применение

`POST /api/v1/maintenance/draft-plans/{id}/optimization-runs`: expected_revision, actor-bound idempotency_key, options. Повтор возвращает тот же run ID; другой запрос с тем же ключом — 409. GET того же пути выдаёт историю без тяжёлых результатов.

Префикс `/api/v1/maintenance/optimization-runs/{run_id}`:

| Маршрут | Назначение |
|---|---|
| GET | Состояние и компактное сравнение, private/no-store |
| POST /cancel | Идемпотентный запрос отмены |
| GET /placements?kind=baseline\|optimized&offset= | Страница частей и имён работников своего объекта |
| POST /apply | Выбранный kind, expected_revision, причина; новая версия |

Чтение доступно читателям каталога; запуск/отмена/применение — chief_engineer/dispatcher/admin с членством и CSRF. Это не даёт admin право публикации. Применение сериализовано с правками источника, проверяет базовую revision, актуальность источника, нынешний fingerprint ресурсов и свежий validator. Изменения дают 409. Повтор применения того же kind возвращает созданную версию; другой kind отклоняется.

Контракты: `schemas/optimization.py`, `contracts/optimization.schema.json`, `frontend/src/shared/api/optimization.ts`. Модуль UI ленивый; открытие/прогрев не запускают расчёт. Polling выбранного run останавливается в скрытой вкладке и не имеет параллельных запросов. Поля сохраняются при ошибке; контекст изолирован существующей оболочкой.

## Границы и следующий этап

Продвинуты PLN-05/09/16/22 для черновика одного объекта с подготовленными строками; весь P0 и полное подтверждение каталога не закрыты. Остаются совместный сценарий нескольких зданий, активный портфель/after-completion, автоматическое разбиение, undo, дополнительные ограничения, Approval Gateway и атомарная публикация. Следующий этап — мост к действующим планам и проверяемое предложение/diff с явным утверждением, затем Planning Agent поверх тех же команд. LLM не заменяет constraint solver.
