## Методика и границы

Пути вида `reports/verification/...` обозначают локальные доказательства, исключённые из Git, а не обязательные файлы чистого clone. Они перенесены из `docs/verification` без изменения содержимого. Выбранные иллюстрации находятся в `docs/assets`; датированные результаты ниже сохраняют исходные условия и ограничения. Подробный снимок прежней редакции: `reports/documentation/2026-11-02-dev-alignment/verification-before.txt`.

Тест считается выполненным после фактического запуска в изолированной среде с указанием версии, времени/seed, команды и результата. Пропуск не равен успеху, DTO fixture не заменяет HTTP/БД, fake classifier не доказывает inference или качество. Ошибка транзакции не должна оставлять частичное состояние. Команды полного runner находятся в [runtime](runtime.md).

`backend/tests/test_roles_contracts.py` — исходная in-memory спецификация политик/DTO, часть её проектных routes не является действующим HTTP API. `test_transactions.py` проверяет lifecycle на SQLite, не совместимость PostgreSQL DDL. Реальное API/БД/файлы проверяют runtime/management/assignment_save/planning tests. Vitest использует explicit demo/mocks; Playwright — собранную SPA и настоящий backend. Семантику документов сверять с [backend](backend.md), [планированием](planning.md) и [ML/CV](ml.md).

## Порядок проверки

1. Отдельная тестовая среда, версии, время, timezone и seed; рабочая БД не используется.
2. DTO/schema/fixtures/диаграммы и чистые unit-тесты.
3. SQL на пустой БД и upgrade заполненной 004 до 008, повтор мигратора/seed и сохранность истории.
4. Настоящие PostgreSQL/HTTP: роли, CSRF, site scope, переходы, locks/revision и атомарность.
5. TypeScript/сборка/UI, затем Playwright на собранной SPA и настоящем backend.
6. Отдельно реальный RF/CLIP inference; mocks проверяют протокол, не качество модели. Backup/restore и проверка качества на заказчике требуют собственных доказательств.

Непройденный или пропущенный обязательный критерий блокирует соответствующий этап демонстрации; исключение оформляется явно с причиной, владельцем и сроком, а не считается успехом. Порядок этапов: preflight → контракты → чистый backend → SQL/upgrade → PostgreSQL/API/RBAC → UI E2E → отдельный реальный model profile → restore/репетиция.

Минимальный воспроизводимый набор: Site A `Asia/Yekaterinburg` и чужой Site B; неизменённый Excel и отдельный synthetic_demo; два работника, полный/неполный/неквалифицированный/занятый состав; разные инженер и автор отчёта; фиксированные часы для полуночи/просрочки. Исторические имена qa_* — обозначения тестовых ролей, не существующие рабочие аккаунты. Канонические [DTO-примеры](../architecture/contracts/examples.json) и [предметные fixtures](../domain/examples/maintenance_cases.json) сохраняются в одном экземпляре.

## Доступ, настройки и эксплуатационные критерии

Регистрация создаёт pending-заявку без клиентского выбора роли. Нужны проверки login/logout/CSRF, отзыва роли на активной сессии, всех role×route/site scope, последнего администратора, CRUD/циклов оборудования, employment bounds, ночных смен/DST, прав на допуски/бригады и ревизий. Проверяются реальные HTTP/БД и веб-формы, а не только скрытие кнопки.

Повтор генерации использует planning_runs/idempotency_key; остальные команды защищены state/revision/locks/UNIQUE, универсальный HTTP Idempotency-Key не реализован. Требуется отдельно проверить неизвестный сетевой исход и конфликт ключа/payload. Seed не заменяет утверждённый customer-график и не сбрасывает существующие пароли/историю. Demo UI содержит также фиктивные записи с customer-бейджем для проверки отображения; это не история заказчика.

Backup/restore всего контура БД+фото+модели, эксплуатационная репетиция, качество ML на реальном заказчике и ресурсные SLA не доказаны одним прогоном test runner. Эти пункты остаются в [плане](../PLAN.md).

### Проверки входа

[login.spec.ts](../../frontend/e2e/login.spec.ts) содержит тринадцать сценариев с mock API: адаптивность, клавиатура, показ пароля, ошибки/pending, ID объекта, статичная помощь, безопасный возврат, бренд/автоматические паузы, переход с первого физического нажатия, disabled-повтор без зависшего feedback, прокрутка/фокус короткого экрана, стабильная геометрия при классической полосе прокрутки, семантика/однократное появление hero-текста, общий мобильный ритм и mobile Canvas/viewport. Компоновка проверяется в том числе на 1920×1080, 1440×900, 1366×768, 1024×768, 768×1024, 430×932, 412×915, 390×844, 375×812, 375×667, 360×800 и 320×568. Координаты регрессий фиксируются до `pointerdown`, чтобы повторное наведение автоматизации не скрывало сдвиг цели. Их успех не подтверждает серверную сессию. Скриншоты сохраняются в `frontend/test-results`, а не сравниваются с эталонными пикселями. UI-тесты форм, общей оболочки, геометрии, canvas renderer и lifecycle движения находятся рядом с кодом в `frontend/src/pages` и `frontend/src/features/auth`. [RegistrationPage.test.tsx](../../frontend/src/pages/RegistrationPage.test.tsx) проверяет запрет отправки без подтверждения и при несовпадении, фокус/описание ошибки и исправление, независимое раскрытие обоих паролей с клавиатуры, блокировку формы во время запроса и сохранение данных при серверной ошибке. Успешная заявка должна отправлять прежний payload без подтверждения и без роли. ## 02.11.2026: мобильная Aurora, viewport и производительность

### Причины и исправление viewport

Baseline (`reports/verification/2026-11-02-mobile-aurora-viewport/baseline.json`) снят до изменений вместе с исходниками и снимками. Подтверждённые причины полосы: `body min-height:100vh` при auth/page `100svh`, отдельные фоновые поверхности и абсолютная сцена `clamp(700px,100svh,940px)`, заканчивавшаяся раньше длинной регистрации. В четырёх baseline-сценариях регистрации с ошибками документ имел высоту около 1016–1020 px, а сцена — 800–932 px; непокрытая область достигала 88–216 px.

Для логотипа воспроизведён другой механизм: при reload Chrome восстанавливал `scrollY=98`; документный верх бренда оставался 28 px, а видимый становился −70 px. Это воспроизводимый сценарий, а не доказательство точной причины каждого пикселя исходного Android-снимка. Исправлены свежая мобильная navigate/reload entry и восстановление прежней browser policy на pagehide/unmount; ручная прокрутка, resize, клавиатура и SPA/POP не получают постоянного сброса scroll.

Текущая мобильная сцена — fixed `100lvh`, page/panel/body minimum — `100dvh`, с `100vh` fallback и auth-scoped фоном html/body. Формы остаются в нормальном потоке. Разделение размеров соответствует назначению [large/dynamic viewport units](https://web.dev/blog/viewport-units). Клавиатура в Chrome по умолчанию меняет Visual Viewport, поэтому одна замена `vh` на `dvh` не является проверкой клавиатуры: [модель Chrome](https://developer.chrome.com/blog/viewport-resize-behavior/). `viewport-fit=cover` и safe-area сохраняются; область Android gesture navigation зависит также от [режима edge-to-edge браузера](https://developer.chrome.com/docs/css-ui/edge-to-edge).

Browser review (`reports/verification/2026-11-02-mobile-aurora-viewport/browser-review.json`) проверяет Login/Register на 360×800, 390×844, 412×915 и 430×932: верх страницы, низ длинной формы/ошибок, сокращение и увеличение viewport, фокус и CTA при приближённой клавиатуре, reload, переходы и отсутствие горизонтального scroll. Исходный baseline 360 px захватил незавершённый intro-transform; отдельная нормализация (`reports/verification/2026-11-02-mobile-aurora-viewport/settled-layout-normalization.json`) явно обозначена как browser-only восстановление старого CSS, без выдачи его за повторный запуск всей старой версии. Desktop сравнивается с отдельными baseline и эталонными path-фазами.

### Профиль, renderer и границы геометрии

Числовые настройки и поведение описаны в [web](web.md#геометрия-пауза-и-производительность), причина выбора — в [ADR mobile Canvas](../decisions/2026-11-02--mobile-aurora-canvas.md). У desktop остаётся прежний SVG, у mobile — общий phaseclock и Canvas вместо покадрового SVG blur. Пользователь сначала сообщил о сильных задержках при мобильном SVG, затем после Canvas-обновления на своём телефоне ответил: «Стало заметно плавнее». Это качественный отзыв с реального устройства; автоматической ADB-проверки Android не было, ADB в окружении не найден.

[Геометрические тесты](../../frontend/src/features/auth/ribbonGeometry.test.ts) проверяют мобильный p8-бюджет, дополнительный x-бюджет, отражённую S-ручку, фиксированные концы и C1-стыки. Интервальный Bernstein/Hölder/de Casteljau сертификат даёт зазор центральных линий >15 world px и положительные x-интервалы без петель. [Desktop fixture](../../frontend/src/features/auth/fixtures/desktop-ribbon-paths.json) содержит 11 независимо захваченных фаз до переработки; default desktop paths совпадают точно. Canvas использует эти же мобильные кубические кривые, один путь для всех световых слоёв и один существующий loop.

Отдельная модельная выборка (`reports/verification/2026-11-02-mobile-aurora-viewport/geometry-profile-comparison.json`) воспроизводится скриптом (`reports/verification/2026-11-02-mobile-aurora-viewport/compare-geometry-profiles.cjs`) из корня worktree. Обеим версиям подаются одинаковые фазы 0–600 с с шагом 0,25 с, по шести параметрам кривой каждой ленты. Отклонение относительно собственного t0 исключает статичный мобильный y-offset. Peak ratio mobile/desktop — 1,440 и 1,460, RMS ratio — 1,325 и 1,278. Это не измерение видимого crop телефона или FPS, а проверка усиления формы отдельно от скорости ×1,9.

В живом Canvas-прогоне (`reports/verification/2026-11-02-mobile-aurora-viewport/live-canvas.json`) на 390×844/DPR3 наблюдались 47,878 с движения: по 1380 actual Bézier draws каждой ленты, изменённые сериализованные first/last-кривые при неподвижных концах и четыре разных PNG. Reduced-motion замораживал bitmap и геометрию; продолжение и синтетический hidden/visible probe прошли без большого скачка (максимальное измеренное изменение control после resume — 0,873 world px). Pointer/touch не меняли замороженную геометрию. Промежуточный счётчик уникальных кривых исключён: QA сохранил объекты по ссылке; raw sampling сохранён, доказательство строится на отдельно сериализованных first/last, счётчиках draw и снимках. Этот прогон со скриншотами не используется как performance-замер.

### Сравнение производительности

SVG stress (`reports/verification/2026-11-02-mobile-aurora-viewport/svg-stress.json`) и Canvas stress (`reports/verification/2026-11-02-mobile-aurora-viewport/canvas-stress.json`): Chrome headless, 390×844, deviceScaleFactor 3, CPU throttle ×4, примерно 10 с без screenshot/video/getImageData и параллельных тестов/сборки. Числа — CDP main-thread duration на одном компьютере, не FPS или время GPU Android.

| Метрика за ~10 с | Мобильный SVG | Мобильный Canvas |
|---|---|---|
| TaskDuration | 2,3563 с | 1,1481 с |
| ScriptDuration | 0,4960 с | 0,3603 с |
| LayoutDuration | 0,0966 с | 0 с |
| RecalcStyleDuration | 0,4069 с | 0 с |
| Максимум pending Aurora rAF | 1 | 1 |

Нулевой Paint в Canvas trace означает отсутствие соответствующих SVG/DOM Paint events в этом trace, а не отсутствие работы GPU. rAF cadence headless изменился (p95 14,4→16,8 мс), поэтому из этих проб не выводится физический FPS или процент ускорения телефона. Bitmap Canvas — 488×1055 при указанном viewport/DPR, в пределах общего raster-cap. Ранний Canvas-прогон с хвостом E2E сохранён как `canvas-stress-contaminated.json` и исключён из сравнения; baseline прежнего статичного mobile также не выдаётся за baseline производительности динамической анимации.

Отдельный desktop-контроль (`reports/verification/2026-11-02-mobile-aurora-viewport/after-performance.json`) дал Task 0,4738 с и Script 0,1428 с за ~10 с против 0,5930/0,1727 с прежней пробы. Это одиночные измерения с ограничениями cadence, не доказательство общего ускорения desktop. Точные source hashes, DPR, условия и сырые интервалы находятся в JSON. Пользовательское подтверждение Android и эти числовые пробы учитываются раздельно.

Lifecycle audit (`reports/verification/2026-11-02-mobile-aurora-viewport/lifecycle.json`) выполнил 16 unmount/remount и mobile/desktop смен: после каждого unmount не оставались Aurora rAF, ResizeObserver, IntersectionObserver и отслеживаемые Aurora listeners, после remount максимум pending rAF оставался 1. JS heap в инструментированном контексте вырос примерно с 5,0 до 7,1 MB; это диагностическая запись с warm-up, а не гарантия отсутствия любых JS/GPU-утечек. GPU-память Android не измерялась.
