# Проверки и доказательства

## Методика и границы

Тест считается выполненным после фактического запуска в изолированной среде с указанием версии, времени/seed, команды и результата. Пропуск не равен успеху, DTO fixture не заменяет HTTP/БД, fake classifier не доказывает inference или качество. Ошибка транзакции не должна оставлять частичное состояние. Команды полного runner находятся в [runtime](runtime.md).

`tests/backend/test_roles_contracts.py` — исходная in-memory спецификация политик/DTO, часть её проектных routes не является действующим HTTP API. `test_transactions.py` проверяет lifecycle на SQLite, не совместимость PostgreSQL DDL. Реальное API/БД/файлы проверяют runtime/management/assignment_save/planning tests. Vitest использует explicit demo/mocks; Playwright — собранную SPA и настоящий backend. Семантику документов сверять с [backend](backend.md), [планированием](planning.md) и [ML/CV](ml.md).

## Порядок проверки

1. Отдельная тестовая среда, версии, время, timezone и seed; рабочая БД не используется.
2. DTO/schema/fixtures/диаграммы и чистые unit-тесты.
3. SQL на пустой БД и upgrade заполненной 004 до 008, повтор мигратора/seed и сохранность истории.
4. Настоящие PostgreSQL/HTTP: роли, CSRF, site scope, переходы, locks/revision и атомарность.
5. TypeScript/сборка/UI, затем Playwright на собранной SPA и настоящем backend.
6. Отдельно реальный RF/CLIP inference; mocks проверяют протокол, не качество модели. Backup/restore и проверка качества на заказчике требуют собственных доказательств.

Правило приёмки исходного P0: зафиксировать среду/версии/время/timezone/seed, проверить успех и предусмотренный отказ, сохранить HTTP/БД/лог/скриншот/hash, повторить без дублей и переписывания истории. Непройденный или пропущенный обязательный критерий блокирует соответствующий этап демонстрации; исключение оформляется явно с причиной, владельцем и сроком, а не считается успехом. Порядок этапов: preflight → контракты → чистый backend → SQL/upgrade → PostgreSQL/API/RBAC → UI E2E → отдельный реальный model profile → restore/репетиция.

Минимальный воспроизводимый набор: Site A `Asia/Yekaterinburg` и чужой Site B; неизменённый Excel и отдельный synthetic_demo; два работника, полный/неполный/неквалифицированный/занятый состав; разные инженер и автор отчёта; фиксированные часы для полуночи/просрочки. Исторические имена qa_* — обозначения тестовых ролей, не существующие рабочие аккаунты. Канонические [DTO-примеры](../../contracts/examples/maintenance.json) и [предметные fixtures](../../tests/fixtures/domain/maintenance_cases.json) сохраняются в одном экземпляре.

## Доступ, настройки и эксплуатационные критерии

Регистрация создаёт pending-заявку без клиентского выбора роли. Нужны проверки login/logout/CSRF, отзыва роли на активной сессии, всех role×route/site scope, последнего администратора, CRUD/циклов оборудования, employment bounds, ночных смен/DST, прав на допуски/бригады и ревизий. Проверяются реальные HTTP/БД и веб-формы, а не только скрытие кнопки.

Повтор генерации использует planning_runs/idempotency_key; остальные команды защищены state/revision/locks/UNIQUE, универсальный HTTP Idempotency-Key не реализован. Требуется отдельно проверить неизвестный сетевой исход и конфликт ключа/payload. Seed не заменяет утверждённый customer-график и не сбрасывает существующие пароли/историю. Demo UI содержит также фиктивные записи с customer-бейджем для проверки отображения; это не история заказчика.

Backup/restore всего контура БД+фото+модели, эксплуатационная репетиция, качество ML на реальном заказчике и ресурсные SLA не доказаны одним прогоном test runner. Эти пункты остаются в [плане](../PLAN.md).

### Проверки входа

[login.spec.ts](../../tests/web/e2e/login.spec.ts) проверяет компоновку на десяти размерах окна, клавиатуру, видимость пароля, ошибки/ожидание, ID объекта, помощь, возврат на маршрут, неподвижный бренд и паузу CSS-анимаций. Все пять сценариев подменяют API; их успех не подтверждает серверную сессию. В полном runner скриншоты сохраняются в `reports/verification/<run-id>/playwright` и не сравниваются с эталонными пикселями. Отдельный Playwright без `--output` использует свой стандартный `frontend/test-results`; для сохранения структуры передавайте новый каталог внутри reports. UI-тесты страницы, геометрии и управления движением находятся в `tests/web/unit/pages` и `tests/web/unit/features/auth`.

Настоящий вход, возврат на защищённый маршрут, полномочия и выход четырёх ролей проверяет [roles.spec.ts](../../tests/web/e2e/roles.spec.ts), регистрацию и выдачу роли с дальнейшим производственным процессом — [settings.spec.ts](../../tests/web/e2e/settings.spec.ts). После изменения видимой ссылки на входе сценарий регистрации должен искать «Регистрация». Полный `scripts/verify.py --browser` собирает рабочую SPA и запускает оба вида проверок на отдельной временной PostgreSQL; запуск Playwright без `FIXRATE_BASE_URL` с пропущенными сценариями не считается проверкой приложения. Настоящий CLIP проверяется тем же runner при `FIXRATE_REQUIRE_CLIP=1` и заранее подготовленном локальном cache; отдельного списка Python-зависимостей для этого нет.

## SQL QA отдельно от полного runtime

> Этот QA проверяет исходную схему 001–004. Лог run_2026-10-30.log — исторический результат источника. Полный dev стенд с 005, HTTP и браузером: [scripts/verify.py](../../scripts/verify.py).


SQL-комплект включает контрактный тест развёртывания ER-модели ТО (миграции
`database/migrations/001–004`) и лог фактического прогона.

### Состав

| Файл | Назначение |
| --- | --- |
| [test_maintenance_schema.sql](../../tests/sql/test_maintenance_schema.sql) | Проверка таблиц, ключей, истории прогнозов, обязательных связей и отказов при некорректных данных. Выполняется в транзакции с `ROLLBACK`. |
| [verify_schema.ps1](../../scripts/verify_schema.ps1) | Поднимает одноразовый кластер PostgreSQL во временном каталоге, применяет миграции, прогоняет тесты `tests/sql/001–004` и `test_maintenance_schema.sql`, затем удаляет кластер. |
| [run_2026-10-30.log](../../logs/sql/archive/run_2026-10-30.log) | Фактический прогон: миграции `001–004` на чистой базе и все тесты, итог `ALL CHECKS PASSED`. |

### Запуск

```powershell
powershell -ExecutionPolicy Bypass -File scripts/verify_schema.ps1
```

Параметры: `-PgBin` (каталог `bin` PostgreSQL), `-Port`, `-Database`, `-LogPath`.
По умолчанию PgBin у этого исходного PowerShell runner — PostgreSQL 18; для установленной 16 передайте `-PgBin`. Используется порт `55433` и временный кластер в `%TEMP%\opencode`.

Скрипт не обращается к рабочей БД проекта: база создаётся с нуля и удаляется
после прогона. Код возврата `0` означает, что все проверки прошли.

### Что проверяет `test_maintenance_schema.sql`

1. Все 35 таблиц TL02, колонки миграций `002`/`004`, 35 первичных ключей,
   составной FK `fk_work_orders_entry_rule` (`NOT VALID`), уникальные индексы
   вхождений и 5 audit-триггеров.
2. Полную цепочку фикстур: участок → правило → привязка → план → вхождение →
   наряд → отчёт → приёмка → доказательства → прогнозы → решение.
3. Сохранение истории: обновление правила пишет audit-снимки `before`/`after`,
   строки прогнозов и решений не теряются.
4. Обязательные связи: наряд без вхождения/правила, инцидентный наряд без
   отчёта, вхождение с неизвестной привязкой, несовпадение правила наряда и
   вхождения, кросс-участковые ссылки.
5. Негативные случаи: недопустимые статусы, диапазоны, дубли бизнес-ключей,
   повторная приёмка, удаление истории, на которую ссылаются.
