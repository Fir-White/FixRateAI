# Работы, сегменты и версии черновика плана

[Подготовка каталога](catalog-decisions.md) · [План](../PLAN.md) · [Проверки](verification.md).

## Работа на сайте

«Работы + реестр оборудования» → «Каталоги регламентов СВиК» → сохранённый каталог → «Черновики планов этого каталога». Выберите подготовленные строки, горизонт и основание дат, посмотрите результат и явно сохраните черновик. Неподтверждённые нормы и смыслы не заменяются нулями или тестовыми значениями.

У версии есть общий список корневых работ и сегментов. Годовой обзор и месячный фильтр читают один и тот же набор; месяцы не хранят отдельные копии работ. Сводка различает обязательства по месяцу срока и фактическое размещение часов по дням/месяцам. Неразмещённые часы не распределяются по дням произвольно.

В работе доступны источник, решение инженера, норматив и сегменты. Сегмент можно разделить с точным сохранением суммы, разместить по местным часам объекта с полным составом бригады, закрепить или явно разблокировать с причиной. Каждая запись создаёт новую версию. История позволяет открыть прежнюю версию для чтения; обратное применение/undo пока не реализовано. Эти размещения **не резервируют** людей в рабочем графике и не создают наряды.

## Общая модель и хранение

`WorkOccurrence` содержит идентичность обязанности, объект/оборудование, нормативные часы, минимальную бригаду, допустимые интервалы, делимость, требования к допускам, включённые операции и происхождение до SHA файла/строки/ячеек/версии решения. `WorkSegment` содержит часть объёма, конкретные активы, интервал, целые ID сотрудников, закрепление и зависимости от сегментов.

Миграция 015 добавляет `planning_draft_versions`: draft ID, линейную revision/parent_revision, горизонт, автора/время/причину, снимки источника и ресурсов, обязанности, сегменты, проверку и компактную сводку месяцев. Версии через API не обновляются и не удаляются. Частные снимки ресурсов позволяют воспроизвести проверку на прежних фактах, не запрашивая сегодняшние смены. Они не выдаются через обзор/списки, в том числе не раскрывают чужие задания и объекты.

Существующие `schedule_plans`/`schedule_entries` предназначены для действующего месячного графика и требуют активных maintenance-rule/binding. Сценарий до утверждения источников может охватывать год и ещё не иметь этих привязок. Поэтому отдельное хранение черновиков не заменяет старые планы, правила, исполнения и назначения; публикационный мост будет отдельной работой.

Обязанности имеют воспроизводимые UUID внутри источника: строка, исходное событие, слот, смысл и подтверждённые активы. Изменение нормы не теряет идентичность того же события. Повторный preview одинаковых входов даёт одинаковый результат. Создание защищено actor/site-bound fingerprint и idempotency key; повтор возвращает прежнюю первую версию, другой запрос с тем же ключом получает 409. Это не токен утверждения.

Редактирование требует `expected_revision`. Порядок блокировок совпадает с каталогом: права/членство, затем advisory lock объекта. Два писателя одной версии получают один успех и один 409. Source digest повторно проверяется под блокировкой; изменение решения/оборудования требует нового расчёта. История остаётся доступной. Разбиение сохраняет ID старого сегмента за последней частью, поэтому прежние зависимости от его завершения не превращаются в зависимости от первой части.

## Правила генерации

| Вход | Результат |
|---|---|
| Исходный январь, `FIXED_EXECUTION` | Отдельные подтверждённые отмеченные события; несовместимое с частотой число выполнений блокируется |
| Исходный январь, `ALLOWED_WINDOW` | Одна обязанность на весь подтверждённый набор дней; промежутки без отметок не заполняются автоматически |
| `CONTINUOUS_WORK` | Одна обязанность; размещённые части должны быть смежными и с одной бригадой |
| `EQUIPMENT_BATCH` | Пакет подтверждённых активов; при делимости и норме на единицу — отдельные части реальных единиц, без умножения по ячейкам |
| `included_in` | Входит в выбранного родителя, не создаёт вторую обязанность или повторные часы; требования к допускам объединяются |
| `по необходимости` | Без реального события автоматическая регулярная обязанность не создаётся |
| Два события в сутки | Требуются подтверждённые day/night и границы слотов; ночной слот может закончиться на следующую дату |

Другие месяцы рассчитываются только по подтверждённому `CalendarPattern` и опорной дате. Используется существующая реализация семи типов календаря: day/week/month/quarter/year/yearly_count/dates, включая короткие месяцы, ISO-недели и явную политику переноса выходных. Паттерн задаёт обязательные сроки, `allowed_lead_days` — начало окна до срока; это относится и к периодическим окнам/пакетам/непрерывным работам. Январская полоса на остальные месяцы не копируется.

Для конкретных дат нужно отдельно подтвердить нормализованную частоту `dates`. Нельзя заменить обязательное ежемесячное обслуживание двумя произвольными датами, оставив частоту «раз в месяц». 4/5-летний цикл требует соответствующего интервала и якоря. Для `source_january` не берутся даты другого года; для `dates` используется режим подтверждённого правила. Прежний `after_accepted_completion` в активном календаре не меняется; адаптер этих действующих привязок к новой общей модели ещё не подключён.

Календарное происхождение явно различается: январские события ссылаются на свои ячейки, события из правила — на строку нормы и версию решения, без ссылки на январскую ячейку как на февральскую дату. Время хранится aware, сроки — date-only. Местный ввод преобразует backend по timezone объекта; DST gap/fold не угадывается.

## Валидатор

Один чистый `scheduling/draft_validator.py` используется сохранением и read-only проверкой; будущий solver должен вызывать его же. Проверяются:

- точная сумма человеко-часов частей, покрытие активов, объём каждой единицы партии, минимум сегмента и неделимость;
- допустимое окно/слот и горизонт, достаточная длительность и полный одновременный состав;
- действующая роль/доступ сотрудника, доступность, отпуск/отсутствие, реальные занятые интервалы на всех объектах;
- обязательные допуски каждого члена бригады, подтверждение и срок действия;
- пересечения людей/оборудования в сценарии и действующая занятость оборудования;
- зависимости, отсутствие циклов, технологическая непрерывность и закрепления;
- подтверждённая полезная ёмкость отдельно от длины смены; неизвестные данные остаются неизвестными.

Политика ёмкости: присутствие за день × заданные полезные часы / 24; существующее занятое время вычитается консервативно как занятое продуктивное время. Размещение занимает весь указанный интервал, даже если он длиннее нормы. Сводка показывает отдельно нормативные часы и занятые часы присутствия. Общая свободная ёмкость объекта не доказывает пригодность каждой бригады — это проверяется для размещения. Параметр nullable; без подтверждения/источника статус остаётся неполным. Универсальная 24-часовая продуктивность не вводится.

Статусы `valid` / `incomplete` / `invalid` описывают **проверенные ограничения на снимке**. Это не `OPTIMAL`, не результат solver и не разрешение публикации. Все DTO сохраняют `ready_for_real_plan=false`. Изменение с hard-нарушением отвергается без новой версии; неполный черновик можно сохранять. При конфликте введённые поля остаются в форме.

`POST /validate` получает свежие ресурсы и проверяет source digest. Изменение источника помечает старый вариант `SOURCE_STALE`, сохраняя прежние часы/историю. Факт доступности при проверке не является резервом: будущая публикация обязана под глобальными блокировками повторить проверку и атомарно создать назначения.

## API, доступ и бюджеты

База `/api/v1/maintenance/draft-plans`. Контракты `schemas/draft_plans.py`, экспорт `contracts/draft-plans.schema.json`.

| Маршрут | Назначение |
|---|---|
| `GET /source-choices/{import_id}` | Поиск подготовленных строк, 25 за раз |
| `POST /preview` | Read-only генерация; счётчики, замечания, первые 25 работ |
| `POST` | Явное сохранение новой версии 1 по проверенному fingerprint |
| `GET ?import_id=` | Последние версии сценариев каталога, по 25 |
| `GET /choices/{workers\|skills}` | Справочник выбора, по 25, сотрудники только своего объекта |
| `GET /{id}?revision=` | Метаданные, сводка месяцев и сохранённый результат проверки |
| `GET /{id}/versions` | История, по 25 |
| `GET /{id}/occurrences?revision=&period=YYYY-MM&q=&offset=` | Общие работы с фильтром года/месяца, по 25 |
| `GET /{id}/occurrences/{root}/segments` | Одна работа, до 25 частей и локальные имена выбранных сотрудников |
| `POST /{id}/segments` | Замена частей работы/указанных сегментов с сохранением остальных и новой revision |
| `POST /{id}/placements` | Местный интервал одного сегмента и бригада через тот же edit/validator |
| `POST /{id}/validate?revision=` | Свежая read-only проверка без изменения версии |

Черновики меняют chief_engineer/dispatcher/admin. Это не выдаёт admin права публикации; её маршрута пока нет. Чтение наследует права каталога: director/chief/engineer/dispatcher/admin, executor недоступен. Сайт и членство проверяются сервером; UI отдельно различает права импорта/подтверждения каталога и подготовки плана. При смене объекта/роли редактор источника перемонтируется, не сохраняя данные предыдущего контекста.

Пределы: горизонт до 366 дней, до 1000 строк источника, 5000 корневых работ, 10000 сегментов, 100 зависимостей на часть и 100000 на сценарий. Ресурсы — до 500 сотрудников и 100000 интервалов; превышение требует сократить расчёт, данные не обрезаются до ложного успеха. Ресурсы и глобальная занятость читаются пакетно; завершённая работа до горизонта исключается в SQL. Preview/validate — явные расчёты, не выполняются при фоновом прогреве.

Обзор читает сохранённую сводку месяцев, не весь JSON источника/работ/сегментов. SQL выдаёт только страницу работ/частей/истории. Отчёт содержит первые 25 примеров и полный счётчик причин; большие списки/подневный обзор имеют страницы по 25. Модули планирования и сложного календарного редактора загружаются лениво; scoped cache и read-only POST сохраняют общий бюджет UI. Проверка 1000 работ ограничивает список десятью SELECT, обзор — восемью с HTTP-аутентификацией и ответом менее 200 КБ.

ИИ подключается к тем же проверенным командам после готовности этих границ.
