# GitHub и синхронизация GitVerse

## Привязка автора к аккаунтам, проверка 17.11.2026

Один и тот же commit `892b23a` на GitHub имеет `author.login=krangras`, а в GitVerse API — `author=null` и `committer=null`. Имя/email внутри Git-объекта сохранены: `krangras <218948672+krangras@users.noreply.github.com>`. То же отсутствие связи GitVerse подтверждено для `e9dd52e`. Следовательно, перенос SHA работает, но GitVerse не связывает эту авторскую идентичность с профилем. Это следствие ранее выбранного GitHub noreply, а не потеря автора при новой синхронизации.

Существующий GitVerse-токен ограничен правами репозитория: `/user` и `/user/emails` возвращают 403. GitHub CLI также не имеет доступа к личному списку email. Поэтому фактические подтверждённые адреса аккаунтов не устанавливаются догадкой и локальный `user.email` не изменяется. Для будущих коммитов адрес должен связываться с обоими профилями; практический путь — общий подтверждённый email. [Управление адресами GitVerse](https://gitverse.ru/docs/gitverse/account-profile/guides/emails). Реальный email попадёт в новые commit objects, если выбрать его авторским. Изменение настройки само по себе не исправляет опубликованные commit objects. Новой переписи истории/force push в рамках настройки sync не выполнялось; восстановление связи старых SHA через профиль требует отдельной проверки возможностей GitVerse.

## Действующая автоматизация, 17.11.2026

[Полный протокол](../releases/2026-11-17-git-host-sync-automation.md) заменяет прежнюю схему обратной передачи только через GitHub cron. У GitHub и GitVerse теперь отдельные push-workflow; оба читают общий проверенный код из GitHub main. Резервные расписания независимы: GitHub `2-59/5`, GitVerse `7,22,37,52` минут каждого часа. Для GitVerse настроены собственные mirror-секреты и отдельный GitHub deploy key с явного согласия владельца.

Переносятся все ветки/теги. Временные сбои и неопределённый исход push восстанавливаются максимум тремя новыми циклами чтения/планирования; слепого повторения записи нет. Действительные конфликты истории/тегов и постоянные отказы доступа сохраняют ошибку и обе версии. Удаление только на одной стороне по прежней политике восстанавливается со второй. Старой ветке без нового workflow требуется наследование текущего dev для event-доставки; до этого её изменения подбирает резервный опрос. Issues/PR и приложение не развёртываются.

31 тест настоящих локальных bare-репозиториев прошёл. Реальные события и финальные SHA проверяются отдельно в [журнале](verification.md#17112026--независимая-автосинхронизация-github-и-gitverse). Ниже сохранено историческое описание миграции и первоначальной схемы; актуальные условия изложены в этом разделе.

## Восстановление после временных HTTP-ошибок, 17.11.2026

В [Actions 43829871430](https://github.com/Fir-White/FixRateAI/actions/runs/43829871430) синхронизация завершилась ошибкой `RPC failed; HTTP 403 ... expected flush after ref listing` до планирования обновлений. GitHub в этом шаге используется через SSH, GitVerse — через HTTPS; старый отчёт не различал initial inventory и fetch. Причина отказа на стороне HTTP-сервиса по этому сообщению не установлена. Последующие три запуска, включая [44000302572](https://github.com/Fir-White/FixRateAI/actions/runs/44000302572), прошли с неизменёнными секретами; последний подтвердил `up_to_date / refs_equal=true`. Постоянная непригодность токена этим инцидентом не доказана, секреты не ротировались.

`scripts/sync_git_hosts.py` теперь повторяет только безопасные чтения (`inventory`, `fetch`, `verify_refs`): максимум три попытки, ожидания 2 и 5 секунд. Повторяются распознанные транспортные отказы и временные HTTP 408/429/5xx. Для GitVerse отдельно обработана точная сигнатура RPC/403/expected-flush; произвольный HTTP 403, явный отказ аутентификации, SSH permissions и ошибки сертификатов сразу остаются ошибками.

Отчёт содержит `retries` и, при окончательном отказе удалённой операции, `failed_operation` с хостом, этапом, числом попыток и обезличенным сообщением. URL userinfo и token/query-параметры маскируются. Git-команда имеет timeout 120 секунд. Постоянный отказ после исчерпания попыток сохраняет `status=failed` и ненулевой exit; он не объявляется успешным.

Записи `push` не повторяются автоматически: таймаут мог наступить после фактического изменения remote. Следующий запуск заново читает refs и принимает решение по текущим SHA. По-прежнему применяются атомарные non-force pushes; расхождения истории и разные теги не перезаписываются, удаление отсутствующих веток не распространяется.

Проверка: **24 passed** на настоящих временных bare-репозиториях. Кроме прежних случаев проверены временный отказ inventory/fetch/verification, исчерпание попыток, постоянные auth/TLS-отказы, отсутствие секретов в отчёте, другие транспортные ошибки и потерянный ответ уже успешного push с последующим чтением текущих refs. Никаких внешних тестовых веток/тегов для этого не создаётся. Реальное подтверждение Actions после публикации изменения фиксируется отдельно в журнале проверок.

Workflow продолжает брать исполняемый скрипт из `dev`; отдельное изменение default branch `main`, состава секретов, прав токена и SSH host verification не требуется.

После публикации исправления `2d08801` настоящий [Actions 44004147452](https://github.com/Fir-White/FixRateAI/actions/runs/44004147452) перенёс `dev` GitHub → GitVerse и завершился success. Отдельно подтверждено совпадение всех четырёх веток и отсутствие тегов; детали и ограничения — в [журнале](verification.md#17112026--устойчивость-github--gitverse-sync).

## Работа и синхронизация

origin указывает на GitHub, gitverse — на GitVerse. Workflow [Sync GitHub and GitVerse](https://github.com/krangras/FixRateAI/actions/workflows/gitverse-sync.yml) синхронизирует все ветки и теги в обе стороны, сохраняя SHA коммитов. Обычный push в любой из репозиториев становится видимым на втором хостинге после успешного запуска синхронизации.

GitHub → GitVerse: запуск при push в ветку с workflow. GitVerse → GitHub: автоматическая проверка по расписанию `*/5 * * * *` на default branch `dev`, также доступна кнопка Run workflow. GitVerse webhook и внешний постоянно работающий сервер не требуются. Это плановый опрос, а не мгновенная доставка события: GitHub может задерживать или пропускать плановые запуски при нагрузке; после 60 дней отсутствия активности в публичном репозитории расписание может отключиться. Ограничения описаны в [GitHub Actions: schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Исполняемая логика — [scripts/sync_git_hosts.py](../../scripts/sync_git_hosts.py). Временный bare-репозиторий получает только Git-объекты и refs; содержимое импортируемых веток не исполняется. Управляющий скрипт всегда загружается из GitHub `dev`. Проверки истории определяют, какая сторона содержит более новый совместимый коммит. Новые ветки и теги копируются; совпадающие refs не обновляются. Повторный запуск не создаёт коммитов, поэтому взаимная отправка не образует бесконечного цикла.

Если одноимённую ветку независимо изменили на обоих хостингах, обе истории сохраняются, workflow получает статус failed и показывает имена/SHА конфликтующих refs в Summary. Независимые безопасные обновления при этом переносятся. Различающиеся одноимённые теги также считаются конфликтом. Для разрешения нужно объединить ветку обычным merge либо вручную определить корректное имя тега, затем повторить workflow. Автоматического merge, force push и удаления refs нет. Отправка на каждый хостинг атомарна; при конкурирующем несовместимом push Git отвергает обновление. Двухсторонняя транзакция между хостингами отсутствует: если один push прошёл, а второй не прошёл, следующий запуск повторяет сравнение без перезаписи истории.

Удаление ветки только на одном хостинге приводит к её восстановлению со второго. Намеренное удаление нужно делать на обоих хостингах при временно отключённом workflow. Автосинхронизация переносит историю репозитория, не Issues/PR/пользователей и не локальные незакоммиченные файлы. Рабочие папки разработчиков автоматически не обновляются; публикация сайта/перезапуск приложения в этот workflow не входят.

## Доступ

GitHub Actions сохраняет минимальные `contents: read`. Для GitVerse используются существующие repository secrets `GITVERSE_USERNAME` и `GITVERSE_TOKEN`. Для записи в GitHub добавлен отдельный write deploy key «GitVerse bidirectional mirror», ограниченный репозиторием `krangras/FixRateAI`; приватная часть хранится в Actions secret `GH_MIRROR_SSH_KEY`. Личный GitHub-токен в workflow не сохраняется. Такой ключ позволяет переносить также коммиты с изменениями workflow; встроенный read-only GITHUB_TOKEN используется только для чтения метаданных GitHub. Описание прав — [GitHub deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys).

Оба хостинга и пользователи, имеющие право писать в их ветки, являются доверенными источниками кода. Добавление write-доступа на GitVerse означает возможность перенести эти коммиты на GitHub. Изменения GitHub `dev`, включая workflows, должны проверяться как изменения управляющего кода автоматизации.

Значения секретов не помещаются в URL, исходники и документацию. Временные key/askpass/known_hosts создаются с правами только для runner и удаляются при завершении. Host keys GitHub получаются через его HTTPS API; SSH StrictHostKeyChecking включён. Локальные приватные файлы подготовки находятся в игнорируемом `var/git-sync`; это не исходники.

Для ротации GitVerse-доступа обновить Secrets в Settings → Secrets and variables → Actions. Для GitHub-ключа создать новую пару, заменить deploy key в Settings → Deploy keys и `GH_MIRROR_SSH_KEY`, затем запустить workflow вручную. Для отзыва удалить deploy key и секрет. Не присылать ключи/токены в чат и не добавлять их в .env.example.

[GitVerse: токены](https://gitverse.ru/docs/collaborative/authentification/tokens/), [GitHub: секреты Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

Другие разработчики должны использовать собственный подтверждённый email.

Предыдущая настройка использовала GitVerse noreply, который GitHub не связал с аккаунтом. Имя отправителя push не заменяет email автора в объекте commit. Настройка нового email исправляет последующие коммиты; ранее опубликованные объекты этим не изменяются. GitHub объясняет привязку в [инструкции email автора](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address). На этом этапе прежние SHA сохранялись; позднее владелец отдельно разрешил исправление опубликованной истории, описанное ниже.

## Исправление опубликованного авторства, 06.11.2026

По отдельному разрешению владельца GitHub и GitVerse получили одинаковую переписанную историю 14 веток, включая появившуюся feat/ml-work. Исправлены 79 авторских и 77 committer-email со старого GitVerse noreply на `218948672+krangras@users.noreply.github.com`. Связанные SHA 170 коммитов изменились; файлы, сообщения, даты, порядок родителей и сведения остальных авторов проверены и сохранены. У четырёх изменённых подписанных коммитов удалены ставшие недействительными подписи; оригиналы находятся в локальной резервной копии.

Перед заменой синхронизация была приостановлена. Обновления выполнялись атомарно для каждого хостинга с точными force-with-lease по сохранённым SHA. После отправки проверено совпадение всех веток обеих площадок и чистота трёх локальных рабочих копий. GitHub API подтвердил 61 связанный с krangras коммит из 116 коммитов dev; проверенный коммит frontend_polished также связан с аккаунтом. Это проверка авторства, не новый прогон приложения.

Локальная резервная копия, снимки refs и карта old-SHA → new-SHA хранятся в игнорируемом `var/git-author-fix`. Старые SHA в реестрах происхождения и датированных протоколах обозначают исходную историю до исправления авторства. Для проверки содержимого сохранены прежние trees и карта соответствия; эти исторические ссылки не подменяются новыми якобы исходными идентификаторами.

Коллегам после этой согласованной переписи нужно выполнить fetch и сверить свои ветки с новой историей. Перед переносом собственных незапушенных коммитов сохранить их отдельно и перенести через cherry-pick/rebase на новую базу; не вливать старую историю обратно обычным merge. Правило обычной синхронизации по-прежнему запрещает force push: текущая операция — однократное согласованное исключение.
