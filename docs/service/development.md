# Разработка, контракты и интеграция

Назначение: передача изменений между областями проекта, развитие общих контрактов и обновление интегрированного `dev`. Запуск приложения описан в [runtime](runtime.md), проверка результата — в [verification](verification.md).

## Структура репозитория

Размещение определяется назначением файла. Это единственная карта каталогов проекта; команды запуска находятся в [runtime](runtime.md).

```text
README.md                   краткое назначение проекта и вход в документацию
backend/                    backend
frontend/                   SPA, её конфиги и Node-зависимости
ml_service/                 ML/CV
.env                        рабочие локальные параметры; не включается в Git
.env.example                шаблон; настоящий .env остаётся локальным в корне
requirements.txt            единственный список Python-зависимостей backend/ML/CV/тестов
contracts/                  экспорт JSON Schema и примеры DTO/API
database/migrations/        неизменяемая применённая SQL-цепочка
database/seeds/             исходный явный seed SQL
database/schema/            машинный каталог базовой модели
data/customer/              исходный Excel
data/demo/                  сохраняемые demo-ресурсы
data/models/                RF-модель и её manifest
data/provenance/            исходные ветки, SHA и карта адаптации
tests/backend/              Python-тесты backend и HTTP/PostgreSQL
tests/ml/                   Python-тесты ML/CV и их pytest fixtures
tests/web/unit/             UI unit-тесты с зеркалом структуры frontend/src
tests/web/e2e/              браузерные сценарии SPA/API
tests/web/setup.ts          общая настройка UI-тестов
tests/web/tsconfig.json     проверка TypeScript всех UI/E2E-тестов
tests/fixtures/             общие scheduling/domain fixtures
tests/sql/                  исходные SQL assertion и полный schema QA
scripts/                    проверки, экспорт ER и подготовка CLIP
docs/                       описание проекта, ADR и docs/assets с иллюстрациями
logs/                       журналы runtime, SQL и verification
reports/                    результаты, метрики, screenshots и audits
var/                        локальная БД, PID, фото и private backup
```

Новые проверки получают один run-id: `reports/verification/<run-id>` и `logs/verification/<run-id>`. `results.json` ссылается на логи относительными путями. `archive` содержит выбранные исторические доказательства в Git; `local-history` — перенесённые локальные материалы. Новые журналы и результаты игнорируются Git. Исторические команды/статусы/время не переписываются под новое расположение.

SQL migrations/seed, Excel, модель и изображения сохраняют исходное содержимое. BRANCH-реестры меняют только текущие destinations; source SHA/blob/source_path сохраняются. [TXT охвата и точная карта переносов](../../reports/audits/REVIEWED_FILES.txt) — снимок проверки, не отдельное описание архитектуры.

Все тесты и тестовые входы собраны в корневом tests; в компонентах тестовых копий нет. Единственный pytest.ini находится в корне. Vite/Vitest и Playwright используют tests/web, frontend/package.json сохраняет команды npm. Проверка TypeScript включает перенесённые UI-тесты и E2E; Node-зависимости остаются в frontend/node_modules без второго комплекта установки. Скрипты в scripts являются точками запуска проверок и экспорта, их результаты сохраняются в reports/logs.

Рабочий env-файл находится только в корневом .env и исключён из Git; локальный runtime.env перенесён без изменения значений. CLI и uvicorn читают этот файл, Vite использует корень как envDir и передаёт в клиент только VITE_* параметры. Общий шаблон .env.example и единственный requirements.txt также находятся в корне. Папка config и шесть вспомогательных Python manifests удалены. Конфиги frontend остаются рядом со сборкой; при переносе тестов обновлены только необходимые пути и разрешение модулей.

Изменяемое состояние var сохраняет своё рабочее расположение. [Состав var, назначение файлов и исключения для открытых журналов PostgreSQL](runtime.md#что-хранится-в-var) описаны в runtime; HF cache остаётся локальным ресурсом окружения.

Добавляя файл, выбирайте существующую категорию. Пример DTO относится к contracts, тестовый вход — к fixtures, результат измерения — к reports, журнал — к logs. Python-скрипт не размещается в docs; диаграмма с её редактируемым исходником и экспортом допустима в docs/assets. Повторные README, копии контрактов и пустые каталоги не создаются.

## Изменение общего контракта

1. Аналитика уточняет смысл, единицу и происхождение поля; интеграция фиксирует хранение и версию. Для UI/алгоритмов допустимы явно синтетические fixtures. Ввод оператором внутренней конфигурации не требует передачи этой обычной операции другому участнику.
2. Имя, статус или единица меняются одним комплектом: [единственный runtime DTO](../../backend/app/schemas/maintenance.py), [экспорт JSON Schema](../../contracts/maintenance.schema.json), примеры, SQL/DTO mapping и потребители. `schemas/management.py` описывает реальные команды управления, `maintenance_api.py` содержит также проектные структуры; их нельзя принимать за автоматически зарегистрированные маршруты.
3. Для канонической схемы выполнить `.venv/Scripts/python.exe -B scripts/validate_artifacts.py --write-schema`, проверить diff схемы, затем обычный валидатор. Старые сохранённые JSON/hash не пересчитывать ради нового имени; совместимость/преобразование решаются явно. Смена комментария сама по себе не требует новой миграции.
4. Изменение хранения оформляется следующей SQL-миграцией, уже применённые SQL не редактируются. Чистые вычисления передают DTO/fixtures, backend сохраняет результат с проверками/блокировками, UI отображает серверный результат и корректно обрабатывает 409/422/unavailable.
5. Проверить затронутые границы и сквозной путь на одной сборке. Тест контракта или чистого алгоритма не заменяет HTTP/PostgreSQL; fixture не подтверждает inference. Точный порядок и оставшиеся критерии P0 находятся в [verification](verification.md#критерии-p0-01p0-23).
6. Обновить соответствующий раздел этого комплекта, индекс и план по изменившемуся поведению. Дефект сохраняет владельца до проверки исправления; архитектурный документ сам по себе не закрывает реализационный критерий передачи.

Итоговый статус учёта и точные source blob находятся в BRANCH JSON выше; их нельзя заменять одной лишь отметкой о просмотре ветки.

1. Проверьте текущую ветку, `git status --short`, remotes и чужие незакоммиченные изменения. Не применяйте перенос поверх чужой работы; при необходимости используйте отдельный worktree существующей согласованной ветки. Не сбрасывайте и не чистите рабочее дерево.
2. Выполните `git fetch origin`, зафиксируйте новый SHA источника. В существующем реестре найдите **последнюю полностью учтённую версию**, а не только последний просмотренный tip. Сохраните refs исходных локальных веток для заключительной проверки.
3. Получите разницу **старый учтённый SHA → новый SHA**. Не копируйте очередную ветку целиком и не применяйте её отставание от `main` как удаление компонентов. Проверьте доступность старого объекта через `git cat-file -e OLD_SHA`; при переписанной/недоступной истории восстановите зафиксированную версию для сравнения и документируйте факт, не угадывайте по дате коммита.
4. Прочитайте карту данной ветки. Сопоставьте новые/переименованные/удалённые пути с их нынешними назначениями в `dev`; для `db/tests` используйте `tests/sql`, для P0 — `docs/service/verification.md`, для frontend mocks — только demo transport. Удаление файла в источнике не разрешает автоматически удалить его адаптированную реализацию.
5. Сначала обновите схемы/миграции и DTO, затем сервисы, ML и UI по зависимостям. Изучите tests и документацию вместе с кодом. Не редактируйте уже применённые SQL 001–008: добавляйте следующую миграцию. Сохраняйте работу ранее перенесённых компонентов.
6. Применяйте выбранные hunks вручную либо обычным `git apply` после `--check`; пути и контексты адаптируйте по карте. Не используйте `--3way`, merge, rebase, cherry-pick или `git pull`, запускающий слияние. Не разрешайте конфликты выбором «вся новая ветка».
7. Выполните связанные проверки и `scripts/verify.py --browser` для критических изменений. Для схемы проверьте новую БД и upgrade с данными. Для UI/API проверьте настоящий transport, для ML — реальные origin/hash/границы/отказы; демо fixtures не заменяют такую проверку.
8. Обновите соответствующий узел в `docs/service`, архитектуру/план при изменении возможностей, существующую карту файлов и доказательства проверки. Только после переноса всех нужных изменений и проверок замените учтённый SHA. При частичном переносе сохраните прежний полностью интегрированный SHA и отдельные `reviewed_sha` / `pending_paths` с конкретными исключениями — нельзя помечать tip полностью интегрированным.
9. Создайте обычный commit только в `dev`, указав источник и SHA в сообщении. Сравните refs всех исходных локальных веток с начальным снимком; убедитесь, что новые коммиты не имеют нескольких родителей. Push/PR выполняются только в отдельно разрешённом процессе.

Пример подготовки разницы (подставьте реальные SHA из реестра и нового снимка):

```powershell
git diff --name-status OLD_SHA NEW_SHA
git diff --binary --output=.git/kran-update.patch OLD_SHA NEW_SHA -- backend/app/db database
# Сначала адаптируйте патч к нынешним путям/контрактам.
git apply --check .git/kran-update.patch
git apply .git/kran-update.patch
git diff --check
```

Эти команды не обещают автоматическое применение: например, следующий `maintenance.ts` из frontend источника содержит mock transport, тогда как в `dev` тот же путь является production fetch. Его функциональные изменения следует разделить между demo transport, типами и API.
