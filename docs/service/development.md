Тесты размещены в tests/backend, tests/ml и tests/web; pytest.ini, Vitest и Playwright настроены на эти каталоги. Конфиги и Node-зависимости веб-сборки находятся в frontend. Демонстрационный режим приложения использует frontend/src/shared/mocks.

Результаты запусков сохраняются в reports, журналы — в logs. Рабочие данные стенда находятся в [var](runtime.md#что-хранится-в-var), параметры — в .env. Git исключает локальную среду, кеши, журналы и отчёты запусков; три сохранённых ML-эксперимента версионируются вместе с описанием результатов.

## Изменение общего контракта

1. Согласовать потребителей и формат обмена: календарь → прогнозы → решение → задание → назначение → выполнение → приёмка.
2. Обновить [DTO](../../backend/app/schemas/maintenance.py), [JSON Schema](../../contracts/maintenance.schema.json), примеры, SQL/DTO mapping и потребителей. Реальные команды управления описаны в schemas/management.py; зарегистрированные HTTP-маршруты — в [backend](backend.md).
3. Обновить экспорт через `scripts/validate_artifacts.py --write-schema` и проверить diff. Изменение хранения оформляется следующей SQL-миграцией.
4. Проверить затронутые границы: HTTP/PostgreSQL, UI и обработку 409/422/unavailable. Для схемы нужны новая БД и upgrade с данными; для AI — origin, hash и отказы провайдера.
5. Обновить описание поведения и состояние работы в [плане](../PLAN.md). Критерии передачи — в [P0](verification.md#критерии-p0-01p0-23).

## Происхождение интеграции и обновление источников

[BRANCH_SOURCES](../../data/provenance/BRANCH_SOURCES.json) и [BRANCH_FILE_MAP](../../data/provenance/BRANCH_FILE_MAP.json) хранят версии источников, соответствие файлов и учтённые адаптации.

| Источник | Область |
|---|---|
| main | Предметная модель, контракты и архитектурные материалы |
| kran_dev | SQL, ORM и репозитории |

| new_backend | Настройки обслуживания, сотрудники, роли и регистрация |

| feat/ml-demo-cases-eval | Пакетный CLIP, прогрев RF, обработка качества фото и CLI для локальных пар |

При обновлении источника сравнивают последний учтённый SHA с новым tip, адаптируют изменённые пути по карте и проверяют затронутые сценарии. Принятые SQL 001–008 сохраняются; изменения схемы получают следующую миграцию. После проверки обновляют учтённый SHA и соответствие файлов в реестрах.

## Настройка демо-доступа
