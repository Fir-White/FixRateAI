# Backend: HTTP, доступ и выполнение

Назначение: граница HTTP и проверка доступа. Код: [FastAPI](../../backend/app/main.py), [DTO](../../backend/app/schemas/maintenance.py), [авторизация](../../backend/app/security). Актуальная спецификация маршрутов доступна в `/docs` и `/openapi.json` запущенного backend.

Строгие REST-модели: [maintenance_api.py](../../backend/app/schemas/maintenance_api.py), [исходные примеры](../../contracts/examples/maintenance_api.json). Они описывают также целевые структуры, не все из которых имеют отдельный HTTP endpoint. Фактически доступные маршруты определяет OpenAPI. Неизвестные поля отклоняются, идентификаторы генерирует сервер; исходная норма не преобразуется в минуты без подтверждённого основания.

Канонические DTO определены только в [maintenance.py](../../backend/app/schemas/maintenance.py). [JSON Schema](../../contracts/maintenance.schema.json) экспортируется из этих же классов, [примеры](../../contracts/examples/maintenance.json) проверяются ими. Документная Python-копия удалена; изменения моделей, экспорта и потребителей проверяются совместно.
`maintenance-0.1` — единый развиваемый контракт текущей dev; новые календарные
варианты добавлены вместе со всеми потребителями. Прежние сохранённые снимки
сохраняют исходные поля и хеши. Версия вычисления теперь `calendar-rules-v2`.

Browser UI использует camelCase-проекции в пространстве `/api/v1/maintenance/ui/*`; команды и настройки —
snake_case DTO. Это явная граница сериализации, а не два независимых расчёта.
Frontend не вычисляет нормативные даты или пригодность бригады повторно.

## Устойчивость HTTP и файлов

Все `/api/` маршруты применяют same-origin политику: чужой Origin и `null` получают 403; запросы без Origin допускаются для CLI с обычной авторизацией. CORS_ORIGINS настраивает CORS middleware, но не отменяет эту проверку: SPA работает с того же адреса или через Vite proxy. CSRF остаётся обязательным для команд. Cookie Secure задаётся только явным true/false.

Ошибки API возвращают канонический ErrorResponse и X-Request-ID. Неожиданная ошибка — 500/INTERNAL_ERROR без текста исключения; журнал содержит только ID и класс ошибки. Конфликт БД — 409, недоступность БД — 503. SQLAlchemy скрывает параметры SQL. Штатный launcher отключает access log с query string; пароли, cookie, DSN и содержимое файлов не журналируются приложением. Исходные исключения провайдеров ML также не сохраняются.

Загрузка сверяет MIME multipart, расширение и декодированное содержимое JPEG/PNG; WebP сохранён как ранее поддерживаемый формат. Пределы: 10 МиБ и 20 млн пикселей; пустые, повреждённые файлы и имена с разделителями пути отклоняются 422. UUID имени генерирует сервер, байты остаются в приватном хранилище. Отказ записи — 503/PHOTO_STORAGE_UNAVAILABLE без изменения задания/метаданных; отказ транзакции удаляет созданный файл. Относительный PHOTO_STORAGE_ROOT разрешается от корня репозитория, размещение внутри публичной frontend/dist запрещено.

Перед фотоанализом повторно проверяются формат, размер и SHA-256 сохранённого файла. Повреждение — 422/PHOTO_CONTENT_INVALID до вызова AI. Ожидание ограничено PHOTO_REVIEW_TIMEOUT_SECONDS (по умолчанию 20); одновременно допускается не более двух провайдеров. TIMEOUT/PROVIDER_ERROR/PROVIDER_BUSY/INVALID_RESPONSE сохраняются как failed, с пустыми результатами и без model_ref. Таймаут прекращает ожидание, но не вычисление: зависшие daemon-потоки занимают два слота до возврата, последующие запросы получают PROVIDER_BUSY; для принудительной отмены нужен отдельный процесс/сервис. Эти потоки не получают DB session и не могут позднее записать результат.

Прогнозирование имеет отдельный ограниченный пул и fallback к подтверждённому регламенту; обе ForecastResult и объяснение решения сохраняются. Отсутствие модели не заменяется успешным ML-ответом. Фотоанализ не принимает работу автоматически. [Аудит семи backend-задач](verification.md#04112026-аудит-backend-и-устранение-блокеров), [запуск](runtime.md).

Детальный [контракт двух ML endpoints](ml.md#контракт-интеграции-backend-и-ml) фиксирует роли/команды, модель/feature/prompt версии, конфигурацию таймаутов, общий лимит пакета фото и последовательность вызовов. Исполняемые профили с реальными весами и без них описаны в [запуске](runtime.md#запуск-с-двумя-ml-инструментами).

## Предметные структуры

| Структура | Правило |
|---|---|
| `CalendarPattern` | Общая периодичность обслуживания и смен: день, неделя, месяц, календарный квартал, год, число раз за год, конкретные даты; ISO-чётность и исключения |
| `RecurrenceRule` | `calendar_pattern` с общими настройками; `calendar_interval` для отсчёта от выполнения/совместимости; `explicit_dates` для сохранённых годовых списков; `runtime` хранит порог наработки, не угадывает календарную дату |
| `OperationVersion` | Численность, исходная норма и единица, отдельная длительность, допуски, инструкция и чек-лист одной версии |
| `ForecastSnapshot` | Один объект/оборудование/привязка/версия, отсечка принятой истории, snapshot ID и SHA-256 |
| `ForecastResult` | Одинаковая структура для алгоритма и AI; исходная дата, версия, состояние, неопределённость, причина и elapsed time |
| `OrchestrationDecision` | Ссылки на оба результата, версия политики, выбранная дата либо `needs_input/manual_review`, обоснование |
| `AssignmentCommand` | Только предложенные исполнители и точный интервал, причина и ожидаемая ревизия; не факт назначения |
| `Assignment` | Подтверждённое назначение и снимки допусков, сохранённые BE05 |
| `ErrorResponse` | `schema_version`, `error={code,message,details,request_id}` и совместимое строковое `detail`; входные значения и пароли не попадают в ошибку |

Все даты — местные календарные даты объекта, timestamps — aware ISO 8601.
Интервалы `[start,end)`. Нормативный день не превращается в дату следующей полуночи
в интерфейсе. Рабочие роли: `admin/dispatcher/engineer/executor`.

## Хранение и ошибки HTTP

Физическая схема задаётся миграциями 001–008 и отражаемым ORM.
Не использовать `create_all()` или вторую таблицу сессий из исходной ветки.
Уникальные ключи, транзакционные блокировки, ревизии и снимки проверяются сервисами.
При отказе транзакции не возвращается успех.

401 — нет сессии; 403 — доступ/CSRF; 404 — отсутствует или скрыт ресурс;
409 — ревизия/состояние/ограничение; 422 — неверный ввод; 503 — БД недоступна.
Обработанные HTTP-, validation- и SQL-ошибки имеют описанный выше `ErrorResponse`.
Backend создаёт новый UUID для каждого запроса: `X-Request-ID` в ответе совпадает с
`error.request_id`; присланный клиентом ID не используется. Пригодный регламент
остаётся доступным при отказе AI. `unavailable` не обозначается успешным прогнозом.


## Дополнения управления

POST management/calendar-pattern/preview возвращает даты шаблона за year/month без записи. POST management/staff/{user_id}/qualifications/{skill_id}/revoke принимает expected_revision, сохраняет отзыв и аудит, конфликтует с действующей будущей бронью. Изменение существующего допуска через PUT требует его текущую ревизию.

ServiceConfiguration.checklist содержит объекты text/answer_kind/unit/required/visual_verifiability/photo_required; типы boolean/number/text сохраняются в замороженном снимке. При создании привязки operation_id позволяет использовать существующую операцию той же системы; её code совпадает, параметры/название/чек-лист сохраняются в отдельной версии. Отсутствие operation_id создаёт новую операцию. PATCH equipment принимает частичные изменения и expected_revision; properties сохраняются.

### Ресурс `maintenance_jobs`

`POST /api/v1/maintenance_jobs` (также `/api/v1/maintenance/jobs`) создаёт задание
из `schedule_entry_id` и связанного `equipment_id`. Backend проверяет объект, систему,
регламент и `rule_equipment`, поэтому чужое оборудование или регламент не могут быть
подставлены. Начальный статус — `planned`; повторное создание для той же регламентной
даты отклоняется.

`GET` списка/задания возвращает статусы `planned/assigned/in_progress/submitted/accepted/rework`.
`PATCH /api/v1/maintenance_jobs/{id}` или `POST /api/v1/maintenance_jobs/{id}/transitions` принимает
`expected_revision`, `status` и `reason` для решения инженера. Переходы используют
те же команды старта, сдачи и приёмки, что и основной API. Подтверждение состава
и интервала выполняется через `POST …/tasks/{id}/assign`. При устаревшей ревизии
сервер возвращает `409`, включая повтор запроса назначения.
`GET /api/v1/maintenance_jobs/{id}/history` возвращает события из транзакционного `audit_events`.

OpenAPI задаёт уникальные operationId для каждого метода и алиаса maintenance_jobs; оба варианта URL публикуют эквивалентные схемы параметров, тела и ответов. Проверка — [test_openapi_contract.py](../../tests/backend/test_openapi_contract.py), HTTP /openapi.json без PostgreSQL lifespan.

### Доступные действия в карточке

`allowedActions` вычисляется сервером для текущего пользователя и последней попытки. Это подсказка интерфейсу: команда всё равно заново проверяет права, состояние и ревизию.

| Значение | Когда включается |
|---|---|
| `forecast` | Роль dispatcher/engineer; успешность расчёта зависит от пригодности исходных данных |
| `cancel` | Диспетчер, SQL-статус draft/clarification/assigned, попыток ещё нет |
| `start` | Назначенный исполнитель, assigned/rework и сохранённый чек-лист |
| `edit_report`, `upload_photo`, `submit` | Автор последнего draft-отчёта, задание in_progress |
| `photo_review` | Инженер, задание in_review и последняя попытка submitted |
| `review` | Те же условия, инженер не автор отчёта и никогда не входил ни в одно назначение этого задания, включая закрытые |

### Ответы, сдача и фактическое время

`answers` в HTTP-команде — словарь `item_uuid → строка или null`, не массив канонических ответов и не JSON boolean. Для boolean допустимы `done`, `not_done`, `not_applicable`, null; обязательный boolean при сдаче должен быть именно `done`. Для number непустая строка должна разбираться как конечный Decimal; единица берётся из снимка пункта, отдельного объекта `work_readings` команда не создаёт. Неизвестный UUID пункта отклоняется. Переданные ответы обновляются, отсутствующие ключи не удаляют прежние ответы.

`submit` проверяет обязательные ответы и наличие before/after одного `view_key` у каждого `photoRequired` пункта, затем замораживает попытку. API фиксирует время загрузки, но не принимает достоверное время съёмки: наличие пары не доказывает хронологию съёмки и реального выполнения. Другие участники бригады не редактируют черновик автора.

`start` проверяет назначенного исполнителя, состояние, ревизию и чек-лист, блокирует работников и создаёт новую попытку. Текущий маршрут не повторяет весь подбор BE05 и не сверяет момент фактического старта с сохранённым плановым интервалом. Проверка полного состава/доступности/допусков относится к сохранению назначения; она не является ограничителем часов фактического выполнения.

Проекция задания различает `isOverdue` (deadline уже прошёл, статус не completed/cancelled) и `deadlineBreached` (`completed_at > regulatory_deadline_at`). Второй флаг вычисляется по времени submit, в том числе до приёмки; принятие не превращает поздний факт в своевременный. `overdue_since`, автоматическая эскалация и отдельная резолюция для поздней приёмки пока отсутствуют: инженер использует обычный review с reason.

Чтение не создаёт demo записи. Неподдерживаемые маршруты возвращают 404; они не заменяются фиктивными успешными endpoints. Исторические SQL-прогнозы без `comparison_snapshot.ui` сохраняются в БД, но не отображаются как полноценные сравнения нового формата: необходим явный backfill после получения недостающих полей.


## Транзакции и защита команд

Сессия — случайная opaque cookie `fixrate_session`, HttpOnly, SameSite=Lax, срок 8 часов; `COOKIE_SECURE=true` включает Secure. В БД хранятся SHA-256 session/CSRF token, а не исходные значения. Пароль — PBKDF2-HMAC-SHA256 с солью и 600000 итераций. При каждом запросе заново проверяются срок сессии, активность пользователя/объекта/членства и текущая роль. Заголовки роли/пользователя не являются удостоверением личности. Login/register проверяют переданный Origin, изменяющие запросы активной сессии — CSRF.

| Роль API | Доступ в текущем runtime |
|---|---|
| admin | Чтение реестра, заданий и сравнений; не приёмка и не выполнение за исполнителя |
| dispatcher | Реестр, календарь, задания, подбор работников/бригад, запуск/чтение прогнозов |
| engineer | Реестр, календарь, задания, прогнозы, очередь, фотоанализ и решение о приёмке |
| executor | Только назначенные задания; связанное оборудование/собственная история/календарь; изменение своего текущего черновика |

005 принимает новые канонические роли. Старые значения сохраняются: `executive → admin`, `chief_engineer → engineer`, `engineer → engineer`, `technician → executor`. Диспетчер создаётся с ролью `dispatcher`; начальник инженерной службы не становится диспетчером по неявному предположению.

Все обращения ограничены объектом активной сессии. Для исполнителя дополнительно проверяется действующее назначение. Инженер не может принимать собственный отчёт или задание, в котором он был исполнителем. Фото проходят те же проверки. Файлы не публикуются отдельной незащищённой статикой; отдача использует `private, no-store` и `nosniff`.

Сдача, решение и аудит фиксируются одной транзакцией. Файловая запись удаляется при неуспешной транзакции загрузки; UUID пути создаёт сервер. Процессный crash между записью файла и commit может оставить бесхозный файл — сборщик такого мусора пока не реализован. Заморозка отчёта обеспечивается HTTP сервисом; прямой SQL-доступ администратора БД не ограничен отдельными immutable-триггерами.

## Границы фактической реализации

- HTTP-маршруты реализованы в `backend/app/main.py`, `backend/app/integration/management.py` и `backend/app/integration/maintenance_api.py`; последний модуль регистрирует действующий maintenance API. DTO находятся в `backend/app/schemas/maintenance.py`, `maintenance_api.py` и `management.py`. Наличие DTO-класса само по себе не означает отдельный endpoint; список проверяется по зарегистрированным маршрутам/OpenAPI.
- `start` создаёт попытку и фиксирует `started_at`. `submit` фиксирует `completed_at` задания и `submitted_at` отчёта. Именно `completed_at` затем используется как `performed_at` принятой истории. Отдельного ввода произвольной фактической даты/времени выполнения текущий HTTP не предоставляет.
- Принятый факт — проекция `acceptance_reviews(decision=accepted)` и связанных работ; отдельной физической таблицы ServiceEvent нет. В снимке прогноза review ID становится `service_event_id`. Чтение наработки из `work_readings` в этот снимок пока не подключено: `runtime_reading`/`runtime_hours` возвращаются null.
- Приёмка требует текущую submitted-попытку, правильную ревизию и непустой reason. `reviewed_ai_result_id` и `additional_evidence_refs` API принимает как необязательные поля; нынешняя веб-форма передаёт reason без этих полей. Проверки обязательности дополнительных доказательств в зависимости от AI-статуса нет. Архитектурное требование учитывать ограничения AI сохраняется в ADR.
- Фотоанализ проверяет сохранённый размер/SHA-256 перед вызовом AI. Download остаётся авторизованной выдачей файла; отдельного автоматического аудита всего хранилища и сборщика бесхозных файлов нет.

## Локальный vision-провайдер

POST /api/v1/maintenance/tasks/{task_id}/photo-review сохраняет прежние права, expected_revision и ограничение на отправленную замороженную попытку. PHOTO_REVIEW_PROVIDER=ollama включает локальный Qwen3.5 через ограниченный адаптер. Ответ items[].assessment содержит общий VisualAssessment, beforePhotoId/afterPhotoId фиксируют выбранную пару. canonical/UI и версия модели сохраняются в ai_quality_checks.findings. SQL-миграции для добавления необязательных JSON-полей не требуется.

При недоступности возвращается структурированный unavailable/LOCAL_VISION_UNAVAILABLE, при неверном ответе/таймауте — failed с кодом; успешной подмены CLIP нет. Неполная конфигурация — HTTP503/LOCAL_VISION_CONFIGURATION_INVALID. HTTP200 фотоанализа не означает приёмку, её endpoint не вызывается автоматически.
