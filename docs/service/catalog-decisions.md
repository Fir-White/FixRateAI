# Уточнение каталога СВиК перед планированием

[Источник и импорт](catalog-imports.md) · [Разрывы v1.1](planning-v1.1-gap.md) · [Проверки](verification.md).

Следующим этапом добавлены [работы, сегменты и версии черновика плана](draft-plans.md). В решении строки появились отдельные подтверждения календарного паттерна/опорной даты и требований к допускам. Они не заполняются автоматически. В списке частот есть `dates`; календарное правило обязано соответствовать явно подтверждённой частоте.

## Результат этапа

В сохранённом каталоге откройте операцию. В панели доступны смысл январских отметок, год, события внутри отметки, явная периодичность, оборудование текущего здания, нормы и правила разделения. Исходные ячейки показаны отдельно. Решение можно сохранить неполным; главный инженер может явно подтвердить полную строку. Обязанности, сегменты, наряды и назначения при этом не создаются.

Пять вариантов смысла: `UNKNOWN`, `FIXED_EXECUTION`, `ALLOWED_WINDOW`, `CONTINUOUS_WORK`, `EQUIPMENT_BATCH`. Значения исходника и подсказки парсера не подтверждаются автоматически. Количество определяется выбранными ID оборудования, максимум 100 на строку; отметки не превращаются в количество активов. Сохраняются год именно исходного января и пояснение инженера. Остальные месяцы не достраиваются.

Нормы положительные, с явной единицей `person_hour` / `elapsed_hour`, базой `per_asset` / `whole_binding`, численностью бригады и ссылкой на методику. На одно выполнение:

- `person_hour`: человеко-часы = норма × количество, если норма на единицу; длительность одной бригады = человеко-часы / численность.
- `elapsed_hour`: длительность одной бригады = норма × количество, если норма на единицу; человеко-часы = длительность × численность.
- Для нормы на весь комплекс множитель количества равен 1.

Параллельное выполнение разными бригадами, сменные ограничения и реальные сегменты рассчитываются следующим этапом. Здесь подтверждаются возможность разделения, минимальный сегмент и пояснение ограничений; минимальный сегмент не может превышать рассчитанную длительность. Длина смены и продуктивная ёмкость людей не подменяются нормативом строки; универсальная 24-часовая продуктивная ёмкость не утверждается.

`included_in` ссылается на самостоятельную подтверждённую строку того же каталога с совпадающими оборудованием, годом/событиями и правилами разделения. Вложенные цепочки и самоссылки блокируются. Собственная положительная норма запрещена: самостоятельный дополнительный объём равен нулю, часы учтены у родителя. Изменение версии родителя требует нового подтверждения дочернего решения.

## Хранение, подтверждение и права

Миграция 014 добавляет `catalog_operation_decisions`. Каждая команда создаёт запись с версией, автором, временем, причиной, полным решением, снимком ревизий/названий оборудования и версией родителя. Прежние решения и `regulation_catalog_imports` не переписываются. История — по 25 строк. Повторный импорт прежнего файла открывает прежний import ID и сохраняет решения.

Черновик редактируют главный инженер и admin; **подтверждает только главный инженер**. Управленческие роли читают в пределах объекта, executor не получает каталог. Это подтверждение исходных данных, отдельно от будущего утверждения плана. При записи повторно проверяются активность пользователя, членство и роль. Сохраняется порядок блокировок пользователей/членства, затем общий advisory lock каталога объекта, совместимый с изменением оборудования.

Обязательный `expected_revision` сравнивается с последней версией. Из двух одновременных записей проходит одна; вторая получает 409 без изменения истории. После ошибки форма сохраняет введённые значения. Явная загрузка актуальной версии заменяет локальные поля; автоматические focus-запросы не пересоздают редактор. Повтор команды после потерянного ответа также не создаёт дубликат той же версии.

Подтверждение с незаполненными полями получает 422. После изменения ревизии/статуса оборудования готовность снимается; история подтверждения сохраняется. Для повторного подтверждения создаётся новая версия. Выбор несуществующего или чужого оборудования отклоняется. Изменение родителя аналогично снимает готовность дочерней строки.

`prepared` означает подтверждённые входные данные строки без блокирующих уточнений. Это **не готовый реальный план**: `ready_for_real_plan` остаётся `false`. Исходные DTO по-прежнему отражают исходник с неизвестными нормами; прогресс решений отдаётся отдельно. Будущий генератор и публикация обязаны заново проверить права, зависимости и версии.

## API и производительность

База: `/api/v1/maintenance/catalog-imports/{id}`.

| Метод и путь | Назначение |
|---|---|
| `GET /preparation` | Счётчики и компактные статусы максимум 1000 исходных строк, без сетки и полных решений |
| `GET /binding-options?q=&offset=` | Поиск активного оборудования объекта в SQL, максимум 25 записей и общее количество |
| `GET /operations/{row}/decision` | Последнее решение, текущие привязки, расчёт и уточнения; версия 0 до первой записи |
| `POST /operations/{row}/decision` | `expected_revision`, `confirm`, непустая `reason`, `decision`; атомарная новая версия и audit |
| `GET /operations/{row}/decision/history?offset=` | До 25 прежних решений со снимками оборудования, автором и версией родителя |

Контракты: `backend/app/schemas/catalog_decisions.py`, экспорт включён в `contracts/catalog.schema.json`. Ответы приватные, `no-store`; frontend cache изолирован по пользователю/объекту/роли, успешная запись инвалидирует чтения. Редактор получает свежую базу при открытии/явном обновлении. Остальные чтения используют общий scoped cache. В DOM не более 25 операций, 25 вариантов оборудования и 25 версий истории; сырые ячейки загружаются только для одной строки.

Последние версии и имена авторов получаются одним запросом с JOIN; привязанное оборудование — ещё одним запросом. Проверка 500 строк с 500 решениями ограничивает HTTP-чтение прогресса десятью SELECT с аутентификацией. XLSX/BYTEA и 31 ячейка каждой операции в этот запрос не попадают. Начальный JS остаётся под бюджетом 150 КиБ gzip.

## Следующая работа

Этап продвигает PLN-24/25/26, но не закрывает весь новый P0. Пока нет группового предпросмотра/применения решений, подтверждённого пула с количеством без явных ID и подтверждения источника целиком. Не реализованы общие `WorkOccurrence`/сегменты, версии годового/месячного плана, валидатор, solver и Planning Agent. Перед подключением решений к действующим регламентам требуется устранить наследование старого ограничения бригады по короткому коду `1.4`, сохранив его для прежнего регламента. Новый редактор изолирован от прежнего DTO и старые ограничения не меняет.

Нормы и значения смысла настоящей книги заказчика не придуманы и массово не подтверждены. Автоматические записи проверяются на сгенерированной fixture в отдельной БД.
