# Общие черновики из регламентов и Excel

Инженер, диспетчер или администратор открывает **Планирование ТО → Общий состав обязательств**, выбирает период и источники, рассчитывает состав, затем нажимает **Проверить общий черновик** и сохраняет его с названием и основанием. Следующий шаг — проверить условия доступа и полезного времени, реальные смены и распределить работы. Руководитель видит сохранённые планы без команд изменения; техник получает работу через действующие задания.

Ссылка `/planning?mode=requirements&portfolio=<id>&portfolio_revision=<n>&portfolio_view=work|schedule|load|publish` восстанавливает сохранённый план, версию и этап. Старый маршрут Excel сохраняется. Поиск состава и страница списка не ограничивают сохраняемый объём. Переключение представлений сохраняет поля; обновление страницы восстанавливает сохранённую версию. Историческая версия доступна для чтения.

## Источник и версии

Общий черновик использует существующую `planning_draft_versions` и общий редактор/валидатор/очередь baseline и CP-SAT. Миграция **018** разрешает `import_id=NULL` только для `kind=portfolio` и соответствующей сводки; каталожный черновик продолжает требовать реальный import ID. Миграция не переписывает строки и снимки прежних версий.

Вход `PortfolioInput`: `kind=portfolio`, полный `RequirementsRequest` без поиска/состояния/смещений страниц, `policy` v2. Границы дневного/ночного события совпадают с просмотренным каталогом. Ёмкость и доступ остаются неизвестными до явного подтверждения; их изменение создаёт новую версию. Вложенные условия каталога фиксируют его исходную интерпретацию, верхний `policy` определяет размещение общего состава.

Сервер сохраняет все выбранные требования и факты источников, включая историю и уже выданные/принятые события. В новые `WorkOccurrence` попадают только требования `new`; спорные источники, неизвестные нормы, неоднозначное сопоставление и отсутствие новых работ блокируют сохранение. Сохранение не доверяет экранной сумме: сервер повторяет расчёт и сверяет actor-bound SHA. Повтор с тем же ключом возвращает ту же версию; иное содержимое получает 409.

Регламентная работа содержит реальные `binding_id`, `rule_id`, `regulation_id`, исходную дату, основание календаря/принятого выполнения, норматив и подтверждённую минимальную длительность. Она не получает фиктивные import ID, Excel-строки или ячейки. Делимость регламентной работы не предполагается. Часы остаются трудоёмкостью; длительность проверяется отдельно при ручном размещении и в решателе. Каталожные работы сохраняют прежнюю сериализацию, UUID и provenance.

Редактор, изменение условий, проверка и применение расчёта повторно проверяют актуальность регламентов, оборудования, истории и выданных обязательств. CAS и блокировка объекта защищают версии от конкурирующих изменений. Доступность, допуски и глобальная занятость читаются через прежний общий механизм; применение дополнительно сверяет снимок ресурсов. Старые версии сохраняют прежние часы и проверку.

## API и границы

| Действие | API |
|---|---|
| Проверить общий черновик | `POST /api/v1/maintenance/portfolio-plans/preview` |
| Сохранить версию 1 | `POST /api/v1/maintenance/portfolio-plans` |
| Список последних общих версий | `GET /api/v1/maintenance/portfolio-plans?offset=0` |
| Обзор, работы, сегменты, история, условия, проверка, размещение и расчёт | Существующие `/draft-plans/{id}/…` и `/optimization-runs/{id}/…` |

Списки и работы выдаются по 25, генерация ограничена 5000 корневых работ / 10000 сегментов, снимок — 24 МиБ. Контракт экспортирован в `contracts/portfolio.schema.json`. Приватные снимки не выдаются через списки и обзор. Кеш интерфейса изолирован контекстом пользователя/объекта/роли и инвалидируется после записи.

Общий черновик подключён к [Approval Gateway](publication.md): сохранённая процедура регламента + дополнения по безопасности/примечаниям → неизменяемое предложение → утверждение главным инженером → отдельный первичный выпуск. Задания регламентного источника используют реальные правила, привязки и ID чек-листов, без копирования регламентов. Смешанный план создаёт конечные процедуры только для каталожных корней. Сервер повторно проверяет источник, принятый факт, существующие события, revision и ресурсы под общими блокировками. Выдача через старый месячный генератор тоже учитывается. Прежний выпуск из Excel сохранён.

Добавлены [undo последнего собственного изменения и нагрузка выбранной версии](draft-history-load.md). Несколько объектов/файлов, изменение действующего графика с diff, Planning Agent, экспорт версии и дополнительные кадровые/технологические ограничения остаются отдельными пунктами ТЗ. Тестовые источники не подтверждают фактические нормы заказчика.
