# Производительность: требования к дальнейшей разработке

Плавность входит в готовность функции вместе с корректностью и доступностью. Эти правила применяются к новым страницам, изменениям существующих экранов, API и общим компонентам. Оптимизация подтверждается production-сборкой и воспроизводимым замером. Скорость сети, объём данных и устройство фиксируются вместе с результатами; абсолютная мгновенная загрузка на любом устройстве не является проверяемым обещанием.

## Бюджеты и проверяемые ограничения

| Область | Требование |
|---|---|
| Обычный ввод и тёплая навигация | Ориентир до 100 мс до видимого отклика на эталонном компьютере без CPU throttling. При CPU ×4 замеряется отдельно; задержку загрузки данных показывать честно. |
| Прокрутка | Нативная; без регулярных задач основного потока дольше 50 мс в установившейся прокрутке. Ориентир кадра — 16,7 мс при 60 Гц; сохранять p95 интервалов кадров и частоту экрана. |
| Начальная загрузка | Начальный JS со всеми статическими импортами до 150 КиБ gzip; Vite build останавливается при превышении. Код остальных страниц — отдельными модулями. Рост бюджета требует объяснения и замера. |
| Большие реестры | Ограниченный DOM: пагинация или виртуализация. Реестр оборудования и наряды — по 25 записей. Поиск должен находить записи за пределами текущей страницы. |
| Чтение SQL | Число SELECT не растёт пропорционально строкам списка. Тестировать малый и увеличенный набор. Для оборудования/реестра — до 20 SELECT вместе с HTTP-аутентификацией, для сохранённого месячного календаря — до 10. |
| Кеш | Дедупликация параллельных чтений; отдельная память для пользователя/объекта/роли. Сброс после мутаций, при смене контекста и выходе. Кеш не хранится в localStorage и не содержит паролей/токенов. |

Временные ориентиры проверяются профилированием, а не нестабильными миллисекундными assertion в jsdom. Детерминированные бюджеты SQL, DOM и повторных запросов проверяются автоматическими тестами. Если временной ориентир не достигнут, указывают фактическое значение и оставшуюся причину; успешный функциональный тест не подтверждает FPS.

## Правила реализации

1. Сохранять оболочку и фон между маршрутами. Suspense должен заменять содержимое страницы, оставляя навигацию доступной. Уже подготовленный модуль отображать синхронно, без повторного suspension; выбор типа компонента фиксировать на время mount, чтобы завершение загрузки не сбрасывало черновик. Модули и разрешённые данные подготавливать по намерению пользователя: hover, keyboard focus, pointer down. После готовности активной страницы разрешённые модули последовательно прогреваются в idle. Фоновый прогрев ограничивает параллелизм; он не запускает команды изменения данных, AI-расчёты или загрузку фотографий.
2. Использовать общий `useApiQuery` и `readQueries` для разделяемых чтений. Составной запрос должен переиспользовать уже выполняющийся запрос зависимости. Ключ включает все параметры ответа; контекст пользователя/объекта/роли изолируется провайдером. Сохранять защиту от ответа, начатого до мутации, и не показывать данные предыдущего объекта даже на один кадр. Периодическое чтение статуса AI останавливать в скрытой вкладке; после возврата возобновлять без дублирования запросов.
3. Не создавать Intl-форматтер на каждую строку/ячейку или каждый рендер. Применять `dateTimeFormatter`, заранее подготовленные словари и индексы; избегать вложенных линейных поисков и копирования растущих массивов в цикле. Поиск в большом реестре отделять от срочного отображения введённого текста.
4. Прокрутку оставлять браузеру. Не добавлять scroll hijacking, React setState на каждый кадр прокрутки или непассивные wheel/touchmove на область страницы. Исключения для границ модальных панелей проверять на мыши, touch и нативных select/number/range. Использовать CSS overscroll-behavior там, где это решает задачу.
5. Декоративная графика не должна конкурировать с вводом: bounded raster, Web Worker/OffscreenCanvas при поддержке, fallback, один цикл, остановка в скрытой вкладке и reduced motion. Не выполнять чтение layout в каждом кадре. После смены размеров и открытия панелей фон сохраняет координаты. Не добавлять backdrop blur к крупным движущимся поверхностям без отдельного профиля.
6. Панели и диалоги: анимировать opacity/transform, сохранять фокус и inert, проверять computed display с Tailwind Preflight. Скрытая разметка не должна становиться доступной клавиатуре. Portal помогает отделить панель от размытия и wheel-обработчиков родителя.
7. Списковые API готовят связанные строки пакетно, с фильтрацией по объекту и разрешённым идентификаторам. `Views.prefetch` — снимок в пределах одного read-only запроса; не вызывать перед записью или блокировкой строк. Нельзя применять его кеш к командам, проверке revision, транзакционным блокировкам или валидации после записи. Предпочитать ограничение периода/сортировки/количества строк в SQL.
8. Не ускорять страницу удалением прав, проверок срока, истории, фотофиксации или подменой неизвестных норм. AI и расчётные операции могут занимать время: показывать их фактическое состояние, сохранять отзывчивость остального интерфейса, не запускать их при прогреве ссылок.

## Как проверять изменения

Использовать одинаковые Chrome, viewport, набор данных и CPU rate до/после. Сначала закончить сборку и остальные нагрузочные проверки; параллельные тесты и Docker build искажают профиль.

1. Проверить свежий вход и первый переход в каждый разрешённый раздел, затем повторить обход. Разделять загрузку модуля, API и React/layout/paint; заголовок над индикатором загрузки не означает готовность данных.
2. Проверить desktop 1440×900 и mobile 390×900, normal CPU и ×4. Выполнить нативную прокрутку длинной страницы и панели, открыть уведомления, вводить поиск и менять вкладки.
3. Проверить Back/Forward, смену объекта/роли, обновление после записи, ошибки API, фокус клавиатуры и reduced motion. Рабочие записи пользователя не использовать для автоматических мутаций: API подменяется fixtures либо применяется отдельная тестовая БД.
4. Сохранить метрики в `reports`, команду и основные результаты — в `docs/service/verification.md`. Не коммитить cookies, пароли, трассы с персональными данными или private runtime.

Детерминированные проверки:

```powershell
python scripts/verify.py --pytest-target tests/backend/test_read_performance.py tests/backend/test_registry.py tests/backend/test_runtime_integration.py
$env:FIXRATE_BASE_URL='http://127.0.0.1:8000'
node frontend/node_modules/@playwright/test/cli.js test --config frontend/playwright.config.ts tests/web/e2e/performance.spec.ts tests/web/e2e/notifications.spec.ts tests/web/e2e/workspace.spec.ts
```

Первой команде нужны локальные PostgreSQL binaries; альтернативный Docker runner обязан создавать отдельные тестовые БД и private photo storage. Браузерные performance-сценарии работают с mock API: 1000 единиц оборудования, полный поиск, не более 25 строк DOM, повторное чтение из кеша, Worker и fallback. Это проверка поведения production SPA, не end-to-end проверка настоящих бизнес-операций.

## Изменения 13.11.2026

На рабочем локальном наборе (5 единиц оборудования, 93 календарных записи месяца, 124 наряда) отдельный процесс с реальным PostgreSQL показал:

| Проекция | SELECT до → после | Время до → после, мс |
|---|---|---|
| Оборудование | 429 → 9 | 850 → 191 |
| Реестр | 48 → 8 | 83 → 44 |
| Месячный календарь | 205 → 3 | 349 → 96 |

Замеры исключают HTTP-аутентификацию и не являются p95 SLA. Основной JS: 689 → 381 КБ без сжатия, новая сборка — около 122 КБ gzip. Фон растеризуется в Worker, при отсутствии поддержки или ошибке используется основной поток. Удалён backdrop blur фиксированной верхней панели, переиспользуются Intl-форматтеры, реестр ограничивает DOM, прогрев составного запроса обслуживания переиспользует список оборудования.
