## 5. Ожидаемый итоговый результат демонстрации

После прохождения всех трех сценариев система находится в следующем консистентном состоянии:
1. **Заявка №1 (`task-501`, манометр `eq-item-991`):** Успешно закрыта (`status = completed`, `is_overdue = false`), в базе сохранены оба прогноза (`Алгоритм` и `ML`), подтвержденный фотоотчёт «До/После» (`1.15 -> 3.2 бар`), запись в истории обслуживания и обновленный показатель SLA (+1.0 н-ч) на дашборде Главного руководителя.
2. **Заявка №2 (`task-502`, счетчики `eq-item-994`):** Защищена от закрытия по бракованному фото — находится в статусе `returned` («На доработке у Техника») с зафиксированным вердиктом CV-модуля `rejected` (`low_quality_blur_and_glare`).
3. **Заявка №3 (`task-503`, щит АВР `eq-item-995`):** Защищена от назначения неквалифицированного персонала — осталась в статусе `created` (`assignee_id = NULL`, `resource_deficit = true`) без нарушения правил безопасности.

## 6. Чек-лист соответствия критериям приёмки задачи `FX26-AN07`

- **QA может пройти сценарий строго по документу (шаг за шагом):** Все шаги содержат конкретные ID оборудования (`eq-item-991`, `eq-item-994`, `eq-item-995`), точные имена файлов из папки фикстур (`case_01_before.jpg`, `case_01_after.jpg`, `neg_01_after_blurry_glare.jpg`), вводимые числа и нажимаемые кнопки.
- **Ожидания не зависят от ручных исправлений в БД:** Все переходы статусов (`created` -> `assigned` -> `in_progress` -> `on_review` -> `completed` / `returned`), блокировки и расчёты SLA происходят исключительно через действия пользователей в интерфейсе (UI) и штатную работу сервисов.
- **Указаны действия для всех 4 ролей системы:** В сценариях задействованы Главный инженер (инициализация регламентного контура и контроль дефицита), Инженер (планирование с AI-оркестратором, назначение и приёмка), Техник (полевое выполнение и загрузка фотоотчётов) и Главный руководитель (проверка истории ТО и аналитики SLA в режиме `Read-Only`).
