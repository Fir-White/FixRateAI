## Применение в существующем контракте

Объект `setting` каждого пункта соответствует `ChecklistSetting` в backend/app/schemas/management.py: boolean/number/text, обязательность, единица, визуальная проверяемость, требование пары фото. Для выбранного профиля массив `items.map(item => item.setting)` можно передать в поле checklist новой версии обслуживания. Метаданные происхождения не являются полями HTTP-запроса.

Для 1.1 числовые поля давления и температуры оставлены необязательными: в привязке может быть только манометр или только термометр. Протокол результатов и читаемая фотофиксация обязательны в черновике. После выбора оборудования следует утвердить нужные параметры, единицы и обязательность; отсутствие датчика не должно заставлять исполнителя выдумывать число.

Для 1.4 источник требует двух работников. Чек-лист не заменяет проверку назначения бригады. Текстовый номер акта не является загруженным или проверенным документом: полноценное хранение актов и контроль обязательных доказательств остаются отдельной интеграционной работой. Действующее ограничение визуального анализа кодов 1.5/1.6 также отмечено в аудите; шаблон не означает его исправления.

Перед изменением опубликованного обслуживания создаётся новая версия с выбранной даты. Отправленные попытки и уже созданные задания сохраняют свои снимки чек-листа; новые пункты не добавляются в старые отчёты задним числом.

## Проверка

Из корня: `python -B scripts/validate_checklist_catalog.py`, затем `python -B scripts/validate_artifacts.py`. Проверяются шесть операций, уникальность пунктов, происхождение и хеши, диапазоны строк, статус черновика и совместимость каждого setting с действующим DTO. Это проверка извлечения, не утверждение технологического регламента или факт выполнения работ.
