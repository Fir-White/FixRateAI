# Оптимизация графики авторизации — 01.11.2026

Проверена ветка `feature/frontend-kran`, HEAD `2948458`, с существовавшими незакоммиченными изменениями. Исходный замер выполнен на реальном рабочем дереве перед оптимизацией, а не на чистом HEAD. Результаты предыдущего [Organic Aurora Flow 3.0](../2026-11-01-aurora-flow-3/README.md) остаются историческим прогоном и не выдаются за новую проверку.

## Что изменилось

- Очищаются небольшие прямоугольники прежних частиц вместо полного canvas на каждом кадре. Очистка выполняется в целых пикселях backing store до новой отрисовки; пересечения частиц, resize и смена плотности экрана учитываются.
- Пока частицы скрыты при узком окне или небольшой высоте, их прозрачный canvas занимает 1×1 пиксель и не перерисовывается. Sprite и видимое полотно создаются по необходимости.
- Для проверки перекрытия с лентами сегменты и их границы рассчитываются при обновлении геометрии; точная функция затухания сохранена. Цели детерминированного шума кэшируются с ограничением на 64 seed.
- Сохранён один `requestAnimationFrame`: геометрия и все слои свечения обновляются в среднем 30 раз в секунду, существующие мелкие частицы — в среднем 60. Время движения и коэффициент скорости ×1,3 сохранены. При resize во время паузы отрисовывается последняя показанная фаза.
- Оригинальные SVG, композиция, цвета, форма лент, подключение к авторизации и API не менялись. Пауза, reduced-motion, статичная мобильная сцена и отсутствие реакции на указатель сохранены. Новые библиотеки не устанавливались.

Экспериментальный первый вариант сохранял исходную частоту частиц и пиксельное совпадение. Финальный вариант ограничивает только их временное обновление: на экранах с частотой выше 60 Гц промежуточные кадры частиц могут отличаться. Это осознанный компромисс в пользу производительности; частота движения самих лент не менялась.

## Производительность

Windows, Node 24.21.0, Chrome 156.0.8078.79 headless, Ryzen 5 7535HS, DPR 1; frontend Vite на `127.0.0.1:5174`, запросы `/api/` отвечают локальным fixture 401. Прогоны до и после выполнены последовательно одним [скриптом](scripts/performance.mjs), без параллельных браузерных проверок. CDP `TaskDuration` и `ScriptDuration` относятся к главному потоку страницы, а не к суммарному использованию CPU/GPU всей системы.

| Сценарий | Длительность main-thread tasks до → после | JavaScript до → после | p95 интервала rAF до → после | Интервалы rAF >25 мс до → после |
|---|---|---|---|---|
| 1440×900, 30 с | 3,877 → 1,987 с (−48,7%) | 1,330 → 0,501 с (−62,3%) | 7,1 → 7,1 мс | 1 → 0 |
| 1920×1080, 12 с | 1,370 → 0,773 с (−43,6%) | 0,472 → 0,198 с (−58,1%) | 7,1 → 7,1 мс | 0 → 0 |
| 1440×900, CPU ×4, 12 с | 7,132 → 3,982 с (−44,2%) | 2,464 → 1,098 с (−55,4%) | 7,1 → 7,1 мс | 5 → 0 |

Доля времени main-thread tasks при 1440×900 составила примерно 12,9% → 6,6% длительности обычного прогона и 59,4% → 33,2% при искусственном CPU ×4. Это одиночные локальные измерения; сравнение больших выбросов не считается гарантией их отсутствия. Исходный максимум rAF в первом 30-секундном прогоне составил 161,8 мс, финальный — 13,8 мс; на CPU ×4 — 48,7 → 14 мс. rAF cadence около 144 Гц в этой среде не равен измерению фактически показанных кадров на физическом дисплее.

Сырые данные: [до](baseline-performance.json), [пиксельно-идентичный промежуточный вариант](candidate-performance.json), [финал](candidate2-performance.json). Независимая 31-секундная browser review дала p95 rAF 7,1 мс, максимум 14 мс и 0 интервалов >25 мс; она включает создание скриншотов/чтение пикселей и не подменяет benchmark — [данные](browser-review.json).

Отдельная CDP трассировка active/paused по 8 с с CPU ×4: [до](before-trace.json), [промежуточный вариант](after-trace.json), [финал](final-trace.json). В одном таком прогоне на активной странице зарегистрировано 39 → 6 событий `MinorGC`; в паузе `FireAnimationFrame`, `Paint`, `Layout` и `PrePaint` не зарегистрированы. Продолжительности trace-событий включают вложенные события и могут перекрываться; их суммы нельзя складывать. Трассировка создаёт накладные расходы и не измеряет полное GPU raster time.

В реальном Canvas при 1920×1080/DPR1 за 901 одинаковый кадр сумма площадей прямоугольников `clearRect` составила 1 420 696 800 → 566 100 backing pixels для пиксельно-идентичного промежуточного варианта (0,03985% исходного); количество вызовов 901 → 9000. В первой записи статистика включала финальную очистку при уничтожении renderer: она исключена из итоговых чисел, а воспроизводимый скрипт отключает подсчёт перед `destroy`. Прямоугольники могут перекрываться: это объём заданных областей очистки, не измерение затрат GPU. В отдельной эмуляции 144 Гц ограничение частиц до 60 Гц уменьшило число и суммарную площадь этих малых очисток до 41,67% промежуточного варианта — [измерения перекрытий](renderer-crossover.json), [144 Гц](temporal-144hz.json).

## Внешний вид и корректность

Независимый Visual QA проверил login↔register, сохранение DOM сцены и паузы, статичный логотип, обе независимые кривые с закреплёнными концами, отсутствие реакции на мышь, reduced-motion, паузу/resize/resume и Space в интерактивных элементах. Проверены 1920×1080, 1440×900, 1366×768, 1024×768 и 390×844; горизонтального скролла нет — [протокол](browser-review.json), примеры [desktop](scene-1440x900.png) и [mobile](scene-390x844.png).

- При контролируемых 60 Гц все 9 PNG baseline/финал совпали побайтно, как и SVG paths/логотип — [хеши](visual-comparison.json).
- Все 34 полных RGBA-снимка canvas при DPR 1 и 1,5 совпали побайтно, включая соседние кадры и resize→pause→resume — [сравнение](candidate2-canvas-comparison.json), [архив данных](canvas-evidence.zip).
- Функции видимости сравнены в 24 050 фактических точках за 120 с, включая 1100 частичных и 4887 полностью скрытых попаданий, и в 4608 точках около границ: отличий нет — [сравнение](visibility-comparison.json). Canvas промежуточного варианта также сопоставлен с исходным в четырёх сочетаниях viewport/DPR, включая частичные перекрытия — [данные](renderer-crossover.json).
- При искусственном 144-Гц такте за 1440 кадров/10 с обновлено 600 кадров частиц и 300 кадров лент; на кадрах обновления canvas совпадает с промежуточным renderer. Между обновлениями частиц ожидаемы отличия: максимальное наблюдаемое смещение 0,1471 CSS px, максимальная разница alpha до 10/255 в четырёх проверенных сценариях. Пауза и первый кадр после возобновления совпали — [данные](temporal-144hz.json). Физический экран 144 Гц и GPU других компьютеров не исследовались.

## Повторение

Из `frontend` запустить `npm.cmd run dev -- --host 127.0.0.1 --port 5174 --strictPort`. Из корня worktree:

```powershell
node docs/verification/2026-11-01-auth-graphics-performance/scripts/performance.mjs review
node docs/verification/2026-11-01-auth-graphics-performance/scripts/trace.mjs review
$env:FIXRATE_BASE_URL = 'http://127.0.0.1:5174'
node docs/verification/2026-11-01-auth-graphics-performance/scripts/review.cjs
```

Для воспроизведения сравнений старых исходников распаковать `baseline-source.zip` и `candidate-source.zip` в каталог `scripts`, затем запустить `visibility-compare.mjs`, `renderer-crossover.cjs` и `compare-144hz.cjs` из этого каталога. `canvas-evidence.zip` содержит исходные `baseline-canvas` и `candidate2-canvas`; их можно распаковать в `scripts` и сравнить через `canvas-compare.cjs baseline candidate2`. Новые выводы скриптов помещаются в `scripts` и не перезаписывают приведённые выше исторические JSON.

GPU других устройств, общее энергопотребление и фактически показанный FPS не измерены. Данный прогон подтверждает уменьшение работы в проверенном Chrome, а не гарантирует мгновенную работу на любом компьютере.
