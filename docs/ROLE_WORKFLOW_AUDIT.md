# Проверка ролей, навигации и переходов в dev

Дата: 31 октября 2026 года. Проверено фактическое приложение на основе `f94f4e9`, а не только таблицы контрактов. Основные правила экранов взяты из `docs/ui/screen-map.md` и `docs/architecture/system_architecture.md`. Ниже отдельно указаны действующие HTTP-возможности и ещё не реализованная часть проектной схемы.

## Экраны

| Раздел | Администратор | Диспетчер | Инженер | Исполнитель |
|---|---|---|---|---|
| Панель диспетчера | Обзор | Обзор | Нет | Нет |
| Реестр и карточка оборудования | Объект | Объект | Объект | Оборудование назначенных заданий |
| Календарь | Нет | Объект | Объект | Вхождения назначенных заданий |
| Очередь и карточка задания `/tasks` | Нет | Объект | Объект | Вместо этого `/executor/tasks` |
| Сравнения прогнозов | Нет | Чтение и запуск | Чтение и запуск | Нет |
| Кабинет исполнителя | Нет | Нет | Нет | Назначенные задания |
| Приёмка | Нет | Нет | Да, запрет собственной приёмки | Нет |

Администратор не заменяет диспетчера, инженера или исполнителя. Его панель получает сводные данные через чтение задач/сравнений API в своём объекте; это не даёт ему права выполнять работы, запускать прогнозы или принимать отчёты. HTTP-чтение задач разрешено всем известным ролям с областью объекта/назначения, как в исходном QA-контракте; набор отдельных экранов уже этого API.

Права экранов и ссылки используют общую `SECTION_ROLES`. Сам API независимо проверяет сессию, актуальную роль, объект, назначение, CSRF, ревизию и состояние. Подмена клиентской роли не даёт доступа.

## Рабочие переходы

| Исходное состояние UI | Действие и исполнитель | Результат |
|---|---|---|
| `assigned` | Назначенный исполнитель начинает работу; нужен чек-лист | `in_progress`, новая попытка №1 |
| `in_progress` | Автор текущего черновика сохраняет ответы/загружает фото | То же состояние, новая ревизия |
| `in_progress` | Автор сдаёт полный отчёт с обязательными ответами и парами фото одного ракурса | `submitted`, попытка заморожена |
| `submitted` | Инженер анализирует фото | Состояние задания не меняется |
| `submitted` | Другой инженер отклоняет с причиной | `rework_required`, старая попытка и решение сохранены |
| `rework_required` | Назначенный исполнитель начинает следующую попытку | `in_progress`, новый ID и номер отчёта |
| `submitted` | Другой инженер принимает с причиной | `accepted`, принятая история оборудования |
| `accepted` / `cancelled` | Начало, изменение отчёта, сдача, повторная приёмка | Отказ, данные не меняются |

Ревизия проверяется при каждой команде. Неактуальная ревизия, неподходящее состояние или попытка дают 409; неверная роль/собственная приёмка — 403; чужой объект или отсутствующее активное назначение — 404. Неполный отчёт — 422. Второй участник бригады может читать текущий отчёт, но не изменять черновик его автора.

Ответ карточки и команд содержит `allowedActions`: `start`, `edit_report`, `upload_photo`, `submit`, `forecast`, `photo_review`, `review`. Сервер вычисляет их для текущего пользователя/назначения/попытки/состояния. Интерфейс использует этот ответ для доступности действий; серверные проверки команд остаются обязательными. Разрешение `submit` означает право сдавать, а комплектность отчёта проверяется при сдаче.

## Исправления

1. Календарь исполнителя открывает `/executor/tasks/{id}`, а не закрытый `/tasks/{id}`.
2. У диспетчера убраны ссылки на приёмку из очереди, карточки задания и AI-блока. Инженерские ссылки сохранены.
3. Панель администратора, реестр и карточка оборудования не предлагают закрытые для его роли календарь, задания и сравнения. В карточке оборудования исполнитель переходит в свой кабинет.
4. Кнопка назначения бригады показывается только диспетчеру, добавления оборудования — администратору/диспетчеру; обе честно отключены до реализации сервисов.
5. Доступность редактора и самоприёмки берётся из серверных разрешений. Другой участник бригады видит режим просмотра.
6. Перед загрузкой фото и сдачей сохраняются текущие ответы и комментарий. Следующая команда получает новую ревизию. При ошибке загрузки сохранённая ревизия остаётся в редакторе, введённые данные не теряются.
7. Подтверждение сопоставимости фото и основание решения привязаны к конкретной попытке; при смене попытки сбрасываются.
8. Выход ожидает отзыв серверной сессии; ошибка выхода отображается. После входа восстанавливается исходная внутренняя ссылка, включая параметры и якорь.
9. Принятое или отменённое вхождение не остаётся следующим сроком оборудования; отменённое задание не показывается как плановое/просроченное. Дубли заданий в блоке внимания устранены.
10. Подпись принятой истории правильно называет инженера проверившим, а не исполнителем; статическая дата панели и неподтверждённое обещание отдельной резолюции главного инженера убраны.

## Границы соответствия

- `draft → assigned`, переназначение, создание и отмена задания, редакторы справочников, генерация/утверждение плана пока не реализованы в HTTP. Тесты проектных DTO не означают, что эти действия работают.
- В текущем runtime возврат использует действующее назначение: `rework_required → in_progress`. В исходной проектной архитектуре предусмотрен промежуточный этап `assigned`; сервис повторного назначения отсутствует. Это явное отличие от целевой схемы.
- В одном объекте сессия имеет одну роль из `site_memberships`; одновременная выдача нескольких ролей на одном объекте не реализована. Смена роли в БД учитывается даже для действующей сессии; запрет собственной приёмки остаётся.
- Все прежние попытки/фото/решения сохраняются в БД, но карточка показывает последнюю попытку; отдельного просмотра всей истории попыток в UI пока нет.
- Фото обязательных этапов и один ракурс проверяются, но система не доказывает фактическую последовательность съёмки и выполнения операции. CLIP не принимает работу.
- Idempotency-Key из целевых контрактов ещё не реализован. Защита действующих переходов опирается на блокировку задания и `expected_revision`.

Создаётся отдельный временный кластер PostgreSQL и независимые БД для SQL, HTTP и браузера; рабочие демоданные не используются. Сохранены все исходные тесты. Добавлены 48 UI-комбинаций «роль × экран» с проверкой всех видимых ссылок, проверка ролей для каждой мутации, запрет неверных переходов для восьми SQL-состояний с проверкой неизменности ревизии/аудита, права автора черновика и отзыв назначения.
