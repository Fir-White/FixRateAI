## 1. Что это за проект и где в нём backend

**FixRate AI** помогает инженеру-сметчику. Сейчас фото дефекта, текст заявки и паспорт дома лежат раздельно, а расценки ФЕР/ТЕР сметчик ищет вручную 30–90 минут. Система принимает фото + описание + характеристики здания и возвращает **черновик ведомости объёмов работ (ВОР)**: работы, объёмы, расценки со ссылкой на источник, предварительная сумма. Сметчик проверяет и утверждает.

Главный принцип: **нейросеть распознаёт и подбирает кандидатов, а деньги считает детерминированный код.** Модель не назначает цены, размеры и коэффициенты.

```
фото + текст + данные дома
   → CV (фото) + NLP (текст)        — Артём / ML
   → Hybrid RAG (поиск расценок)    — ML
   → валидатор → расчётный движок   — Артём
   → черновик сметы → сметчик
```

**Backend — «скелет» всей системы.** Через него клиент (пока Swagger, позже фронтенд) создаёт заявки, загружает фото, запускает обработку и читает смету. Остальные модули подключаются к нему через заменяемые адаптеры.

### 3.3. Как это устроено и почему

**`main.py`: функция `create_app()`.** Собирает приложение: настройки → логирование → middleware → обработчики ошибок → роутеры. Фабрика, а не россыпь глобальных действий, чтобы приложение одинаково создавалось в проде и в тестах.

**`core/config.py`.** Все настройки читаются из окружения и `.env`; значения по умолчанию безопасные. Секретов в коде нет (требование тимлида). Ключи `DATABASE_URL`, `STORAGE_DIR`, `ML_BASE_URL`, `JWT_*` пока только читаются, это задел под карточки 2, 3 и 5.

**`core/middleware.py`: `X-Request-ID`.** Для каждого запроса берётся заголовок `X-Request-ID`, если он безопасный (до 64 символов, буквы/цифры/`-`/`_`), иначе генерируется UUID4. Идентификатор:
1. попадает в каждую строку лога внутри запроса;
2. возвращается клиенту в заголовке ответа;
3. дублируется в теле ошибки.

Зачем: когда у QA упадёт демо, он присылает `request_id`, и по нему находится строка в логе. Это ключ к диагностике. Реализация сделана «чистым» ASGI-middleware (не `BaseHTTPMiddleware`), чтобы не ломать `contextvars` и порядок обработчиков исключений. В access-лог пишутся метод, путь, статус и время. **Query-строка не логируется** (в ней могут быть секреты).

**`core/errors.py`: единый формат ошибок** (контракт `plan.md` §8):

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные входные данные",
    "details": [{"field": "title", "issue": "Field required"}],
    "request_id": "37db53ee-849d-4517-852c-4c590374fbeb"
  }
}
```

Обработаны четыре случая:

| Ситуация | HTTP | `code` |
|---|---|---|
| Наша прикладная ошибка `AppError(status, code, message)` | любой | задаёт код |
| Неизвестный путь / метод | 404 / 405 | `NOT_FOUND` / `METHOD_NOT_ALLOWED` |
| Ошибка валидации Pydantic | 422 | `VALIDATION_ERROR` + `details[{field, issue}]` |
| Любое необработанное исключение | 500 | `INTERNAL_ERROR`, **без traceback** (он только в логе сервера) |

Зачем: фронтенд и QA получают предсказуемый формат; клиент не видит внутренностей (безопасность). В `HTTP_STATUS_TO_CODE` уже заведены коды из плана (`PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `DB_UNAVAILABLE`, `UPSTREAM_TIMEOUT` и др.), чтобы команда не придумывала свои.

> **Важно.** Нехватка масштаба, норматива или цены для расчёта это **не 500**. Это штатный статус заявки `needs_clarification` с вопросом пользователю (карточка 4).

**`api/v1/health.py`: `GET /health`.** Лежит в корне, а не под `/api/v1`: его проверяют Docker, балансировщики и QA, версия бизнес-API ему не нужна. Он **не ходит в БД** и не зависит от ML, то есть отвечает «процесс жив». Проверка БД появится отдельно в `/ready` (карточка 7).

**`api/v1/router.py`.** Пустой роутер с префиксом `/api/v1`. Он резервирует версию API: будущий фронтенд будет жить на стабильных путях. Новые роуты подключаются через `include_router`.

**Слои.** `api → services → repositories → adapters`. Роутер не содержит бизнес-правил, сервис не пишет SQL, репозиторий не знает про HTTP. Это позволяет подменять заглушки CV/NLP/RAG настоящими модулями «без переработки основного процесса» (требование карточки 4).

### 3.4. Принятые технические решения (из `plan.md` §3) и обоснование

| Решение | Почему |
|---|---|
| **Sync-стек** (SQLAlchemy 2.0 sync + psycopg3, роуты `def`) | Команда учебная, сроки в днях. Sync проще в транзакциях «заявка + фото + смета» и убирает класс ошибок event loop. FastAPI сам запускает `def`-роуты в threadpool |
| **Python 3.12** | Единая версия для всей команды |
| **БД без `create_all()`, без собственного Alembic** | Схему задаёт DDL архитектора (`db/`). Параллельная «схема на глаз» гарантированно разойдётся с его миграциями |
| **Фото на локальном диске за адаптером** (карточка 5) | Общего сервера и S3 нет. Интерфейс `save/open/delete` оставляем заменяемым |
| **Оркестратор как библиотека в процессе FastAPI** | Нет отдельного сервиса и распределённой транзакции. Отдельный ML-сервис возможен позже за тем же адаптером |
| **JWT + роли operator/estimator/admin** (карточка 3) | Нужны `created_by` и проверка сметы человеком. Полный SSO и OAuth не нужны |
| **Только DEMO-расценки в git** | ФЕР/ТЕР это охраняемые издания. Для MVP в репозитории только вымышленные расценки с пометкой `source_type=DEMO` |
| **Swagger как демо-интерфейс** | Фронтенда в команде нет. Путь `/api/v1` фиксируем, чтобы позже не ломать API |

Не тащим в проект: React, Celery, Kafka, Kubernetes, полный RBAC/SSO, pgvector-поиск, MinIO/S3, async SQLAlchemy.

## 4. Как запустить и проверить

Подробно в `backend/README.md`. Коротко, из каталога `backend/`:

```bash
python3.12 -m venv .venv && source .venv/bin/activate      # Windows: py -3.12 -m venv .venv; .venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
cp .env.example .env                                         # Windows: copy .env.example .env
uvicorn app.main:app --reload
```

| Проверка | Ожидание |
|---|---|
| `GET http://127.0.0.1:8000/health` | `200`, `{"status":"ok"}`, заголовок `X-Request-ID` |
| `GET http://127.0.0.1:8000/docs` | `200`, Swagger с заголовком «FixRate AI API» |
| `GET http://127.0.0.1:8000/no-such-path` | `404` и JSON `{"error": {"code": "NOT_FOUND", ...}}` |
| `GET /health` с заголовком `X-Request-ID: demo-123` | Тот же `demo-123` в ответе |
| `pytest -q` | `9 passed` |

**Что покрывают тесты** (`tests/test_smoke.py`): health, docs/openapi, генерация и эхо `X-Request-ID`, замена небезопасного ID, единый 404, 405, формат 422 с полем, маппинг `AppError`, скрытие внутренностей при 500.

**Результат самопроверки при подготовке:** на чистом venv с Python 3.12.3 `pytest` дал `9 passed`; живой запуск `uvicorn` вернул `GET /health` → 200, `/docs` → 200, неизвестный путь → единый JSON 404, в логах видны `request_id`.
**Не проверялось в моей среде:** `docker compose up` (Docker там нет), поэтому проверьте на своей машине.

## 6. Правила для всех, кто пишет код дальше (и для нейросетей)

1. Сначала посмотреть, какие файлы уже есть. Не плодить второй каркас.
2. Держать слои: `api → services → repositories → adapters`.
3. Секреты только из env. В git только `.env.example`.
4. Деньги и объёмы: `Decimal` / `NUMERIC`, не `float`.
5. Нет масштаба, норматива или цены: статус уточнения/ошибки. **Не подставлять выдуманные числа.**
6. Роуты с доступом к БД: `def`, не `async def`.
7. Ошибки только через `AppError` и контракт из §3.3.
8. Не логировать пароли, JWT, содержимое `.env`, тела файлов, query-строки.
9. Не вызывать `Base.metadata.create_all()`. Схема приходит из `db/`.
10. Не класть в git справочники ФЕР/ТЕР целиком. Реальные данные по лицензии хранить вне git (`data_private/`).
11. Не закрывать карточку, если её нельзя запустить: статус `BLOCKED` и причина.
