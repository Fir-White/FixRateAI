# Реализация загрузки и получения фотографий дефектов

**Статус:** DONE  
**Ветка:** `yana/backend/api`  
**Зона:** `backend/`, `db/`

## API

- `POST /api/v1/requests/{request_id}/photos` — multipart-поле `file`;
- `GET /api/v1/photos/{photo_id}` — получение обработанной копии по UUID.

Пример загрузки в PowerShell:

```powershell
curl.exe -X POST `
  -F "file=@C:\photos\defect.jpg" `
  http://127.0.0.1:8003/api/v1/requests/{request_id}/photos
```

Ответ содержит `photo_id`, безопасные storage keys, исходное имя, MIME,
размер и SHA-256. В БД оригинал и обработанная копия имеют разные ключи.
Оригинал находится в `STORAGE_DIR/originals`, обработанная копия — в
`STORAGE_DIR/processed`. Ключи генерируются сервером, имя клиента не
используется как путь.

## Проверки безопасности

Принимаются только JPG/JPEG, PNG и WEBP при совпадении расширения и заявленного
MIME. Pillow проверяет фактический формат, целостность и лимит пикселей.
Размер тела ограничен `STORAGE_MAX_FILE_SIZE` (по умолчанию 10 MiB), имена с
разделителями путей и управляющими символами отклоняются. Получение использует
только ключ из БД после проверки, что путь остаётся внутри storage root.

Обработанная копия нормализуется в JPEG с применением EXIF-ориентации. Это
отдельный файл; оригинал не изменяется.

## Запуск и миграция

```powershell
$env:DATABASE_URL="******localhost:5432/fixrate"
psql -X -v ON_ERROR_STOP=1 -f db/003_photo_processed_storage.sql
cd backend
python -m uvicorn app.main:app --host 127.0.0.1 --port 8003
python -m pytest -q tests/test_photos.py
```

Для повторного запуска серверу нужен тот же `STORAGE_DIR`, поэтому файлы
доступны после перезапуска. При ошибке БД после записи файлов сервис удаляет
обе копии и не оставляет метаданные.

## Самопроверка

Проверено: валидный JPEG загружается и читается после создания нового
экземпляра storage; повреждённый файл, несовпадающий MIME, недопустимое имя и
неподдерживаемое расширение отклоняются без записи в БД. Полный интеграционный
тест с PostgreSQL требует доступной БД и применённых миграций.
