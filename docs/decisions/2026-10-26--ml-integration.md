# Библиотечная интеграция ML и общий контракт

- ID: `ADR-2026-10-26-ml-integration`
- Дата: 2026-10-26
- Статус: принято (исходный `APPROVED`)
- Задача: —; сохранены прежние идентификаторы ADR-001, ADR-007.

## Исходное решение ADR-001: Выбор чистых Python-интерфейсов внутри монолита вместо микросервиса

* **Контекст:** В архивной ветке `master` / `ai/ml-service` ML-модуль проектировался как отдельный сервис на FastAPI с сетевыми вызовами через HTTP.
* **Проблема:** Сетевые накладные расходы, сериализация больших JSON, необходимость оркестрации нескольких контейнеров в Docker Compose (Redis, Celery/RabbitMQ), усложнение демонстрационного стенда при жестком сроке (07.11.2026).
* **Решение:** ML-модули оформляются как **библиотечные Python-пакеты с чистыми функциями** без побочных эффектов. Они вызываются синхронно из backend вне event loop (через `run_in_threadpool` при необходимости).
* **Последствия:** Упрощение архитектуры (один backend + одна PostgreSQL), отсутствие сетевых сбоев между компонентами, ожидаемое сокращение накладных расходов; <20 мс было проектной оценкой, а не замером.

## Исходное решение ADR-007: Унификация контракта ForecastResult для обоих методов

* **Контекст:** В системе работают два независимых метода: алгоритмический (по формуле регламента) и статистический AI (по истории).
* **Решение:** Использовать строго единый DTO [`ForecastResult`](../../backend/app/schemas/maintenance.py).
  - Поле `method` принимает значение `"algorithmic"` или `"ai"`.
  - Все поля (`recommended_date`, `mandatory_due_date`, `uncertainty`, `explanation`, `warnings`, `error_code`, `elapsed_ms`) идентичны по типам и валидациям.
* **Последствия:** Оркестратор и фронтенд работают с единообразной структурой, без дублирования DTO и написания сложных адаптеров.
