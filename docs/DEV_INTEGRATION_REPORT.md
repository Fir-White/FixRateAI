## Что согласовано

- Сохранена одна SQL-цепочка и один ORM/repository. Добавлена 005 для серверных сессий, canonical ролей, ревизий, замороженных чек-листов, привязок фото и контекста решения; появился транзакционный checksum-aware migration CLI.
- Реализован один FastAPI runtime. Он использует исходный RBAC helper и SQLAlchemy, а ML вызывает как `ml_service.app`, без второго конкурирующего сервера.
- SPA по умолчанию работает через настоящие cookie/CSRF и API проекции. Моки доступны лишь при явно выбранном demo режиме и в UI tests; при ошибке API fallback на fixtures отсутствует.
- Реализованы начало попытки, сохранение ответов/комментария, действительная загрузка/чтение фото, сдача, доработка и отдельная приёмка инженером с аудитом и контролем ревизии.
- Входы ML строятся из scope-checked БД; оба результата сохраняют один snapshot/hash. Customer AI честно unavailable, неподтверждённое правило — needs_input. Синтетический RF artifact проверяется по manifest и реально исполняется.
- Состояния SQL и UI преобразуются явно. Неизвестные даты, конец интервала и происхождение не подменяются fixture значениями. Исходный строгий low-level mapper неоднозначные случаи по-прежнему отклоняет.
- Устранён конфликт Python package `app` между backend и ML при общем pytest. Модель API изолирована от standalone глобального кеша.
- `db/tests` перенесён в `database/qa`; идентичные корневые README_1/p0 документы объединены в `tests`. Все изменения путей выполнены только в dev, исходные ветки не переименованы.
- Манифесты согласованы, Python окружение зафиксировано lock-файлом, frontend lock обновлён. Vitest обновлён до 4.1.12 после фактических audit findings; последующая проверка audit проходит.

Найденные и исправленные регрессии:

1. Общий pytest импортировал ML `app` вместо backend: добавлены package namespace и importlib режим, исходные тесты сохранены.
2. SQL QA ожидал SQLSTATE `restrict_violation` вместо фактического `foreign_key_violation` на PostgreSQL 16: поправлен ожидаемый SQLSTATE, проверки запрета удаления и сохранности истории не ослаблены.
3. Загрузка RF при startup API загрязняла глобальный кеш и ломала тест отсутствующей модели: модель перенесена в состояние приложения, добавлен изолированный вызов.
4. Browser test первоначально не выбирал select через точный label; использован доступный role locator и ожидание серверного обновления. Приложение не подменялось сетевыми моками.
5. Runner печатал Unicode лог через cp1251 при ошибке: stdout/stderr явно настроены на UTF-8.
6. CDN весов CLIP сначала отвечал Read timed out; ограниченная повторная подготовка завершилась успешно, использован именно закреплённый revision.

## Ограничения

- Основной лёгкий профиль работает без Torch/CLIP и честно сообщает недоступность модели. Дополнительный профиль `.venv/cv` установлен, pinned веса получены, настоящий CLIP inference через HTTP проверен на контролируемых изображениях. Качество на customer фото не оценивалось. JSON экспериментов источника остаются историческими артефактами.
- Customer-trained модель отсутствует; система возвращает unavailable, не выдавая синтетику или нормативную дату за AI. Неопределённые нормы/календарные сроки заказчика не утверждены.
- Универсальные редакторы/планировщик/назначения с навыками и доступностью описаны DTO и проектными документами, но не реализованы в источниках. Их отсутствие не скрыто фиктивными endpoints.
- Старые SQL сравнения без нового `ui` payload сохранены, но требуют явного backfill для отображения в новой SPA. Многопредметный наряд хранится repository; форма фото требует одну единицу оборудования.
- FK 004 остаётся NOT VALID для старых строк, прямой SQL-доступ не ограничен HTTP freeze, универсального Idempotency-Key store нет. Для публичной эксплуатации нужны отдельные инфраструктурные работы.
- Docker daemon недоступен; исполняемой Compose конфигурации в источниках нет. Проверен существующий стек через локальный PostgreSQL 16 и uvicorn. Linux/публичное развёртывание не запускались.

Сформирована локальная интеграционная версия всех реализованных компонентов с перечисленными границами. Проверка настоящего inference не является оценкой качества на customer данных или подтверждением промышленной готовности всей проектной дорожной карты.

## Git и публикация

Во время работы использовались выборочные `git restore --source=<зафиксированный SHA> --worktree -- <пути>` и ручная адаптация. Merge, rebase, cherry-pick, pull и новые merge-коммиты не выполнялись. Старые merge-коммиты main сохранены как часть истории.

Push, force push и запросы на слияние **не выполнялись**. Повторный `git ls-remote --heads origin` подтвердил те же 8 исходных SHA и отсутствие опубликованной dev. Изменений, сделанных другими участниками во время задачи, не обнаружено. [Протокол проверки источников](verification/2026-10-31/git_source_audit.json).

Исходная локальная main осталась на `d94f528df8c0e0f69c344ebd8c79a99bfbe5c1f2`; других локальных источников не было. Все новые коммиты созданы только в dev. Проверка `git rev-list --min-parents=2 d94f528..dev` не возвращает новых merge-коммитов.

Коммиты этапов: `10d314f` (версии/карта), `e326764` (SQL/ORM/RBAC/QA), `d14c953` (SPA/ML источники), `9d8b24e` (единый runtime и проверки), `d8c5729` (настоящий CV профиль). Завершающий обычный коммит содержит итоговую документацию; их собственные SHA не встраиваются в изменяемые ими файлы. Полный список воспроизводится через `git log --oneline d94f528..dev`.

Чужих незакоммиченных изменений в исходном дереве не было, реальные данные и секреты не использовались. Пароли временных tests генерировались заново и не записывались в репозиторий. Локальная dev не появилась на сервере.
