# Технологический стек прототипа

Дата решения: 26.10.2026. Основания: [аудит](repository_audit.md), срок демонстрации 07.11.2026 и необходимость одного сквозного процесса ТО. Выбран модульный монолит: один backend с Python-интерфейсами планировщика, AI и оркестратора, одна БД и локальное хранилище фото. Это целевой стек; его наличие в текущем `main` не подразумевается.

## Средства реализации

|---|---|---|
| React + TypeScript | Семь экранов, переиспользуемые карточки и типизация данных; соответствует предпочтениям команды | REST `/api/v1/maintenance`; типы выводятся из новой OpenAPI/JSON Schema, без отдельного вручную изменяемого Forecast DTO |
| Vite + Tailwind CSS | Сборка SPA и оформление интерфейса без разработки собственной системы компонентов | Vite proxy для разработки; сборка SPA отдаётся nginx в контейнере frontend. Окончательные совместимые версии фиксируются при создании frontend, существующего lock-файла нет |
| Python 3.12 | Единое окружение backend и AI; соответствует требованиям архивного backend | Отдельное venv/образ. Локальная проверка артефактов выполнена на имеющемся Python 3.11.9; это не проверка будущего runtime на 3.12 |
| FastAPI + Pydantic 2 | API, валидация DTO, OpenAPI; позволяет адаптировать старый каркас и формат ошибок | Роутер → сервис → репозиторий. DTO не отдают ORM-объекты напрямую и не выполняют SQL. Модели в `contracts/` — спецификация, а не готовый сервер |
| PostgreSQL 16 | Транзакции назначения/приёмки, FK, ограничения, история и JSONB снимков | Отдельная база `fixrate_maintenance` и отдельный volume; сметная БД не обновляется. Для прототипа pgvector не нужен |

| Последовательные SQL-скрипты + psql | В архиве именно этот механизм, Alembic отсутствует; сохраняется знакомый способ поставки | Новая независимая цепочка в будущем `db/maintenance/`; `psql -X -v ON_ERROR_STOP=1`, транзакции, таблица учёта версии/контрольной суммы и один процесс применения. | openpyxl | Чтение имеющегося xlsx и разворот дневных колонок в строки | Импорт только конкретного шаблона, preview → ручное уточнение → утверждение. Сохраняются hash, координаты и исходный текст; произвольный Excel-конструктор не нужен |

## Версии и воспроизводимость

Архивный backend использовал диапазоны `fastapi>=0.115,<1`, `sqlalchemy>=2,<3`, `psycopg>=3.2,<4`, Pydantic 2, Pillow и python-multipart. Это отправная точка, а не новый проверенный lock. При реализации команды фиксируют точные совместимые версии в lock/requirements, версию Node по выбранному Vite, digest образа PostgreSQL 16, commit весов CLIP, hash модели прогноза, feature schema и seed обучения. Не обновлять одновременно весь архивный стек без причины.

Проверка Pydantic-артефактов не требует установки FastAPI, Torch, scikit-learn или моделей. Машинная JSON Schema хранится рядом с моделями и обновляется тем же валидатором; runtime-модули будут отдельной задачей.

## Минимальная среда исполнения

Проектный стартовый бюджет: PostgreSQL, frontend и backend с одним worker; CPU inference, ограничение одного одновременного AI-вызова, заранее загруженные веса. Ориентир машины — 4 CPU / 8 ГБ RAM, но соответствие этому бюджету не измерялось. До 03.11 нужно замерить загрузку весов, пиковую память и обработку двух фото на фактическом демонстрационном компьютере. GPU не является обязательной частью архитектуры.

Фото и модель читаются из локальных volumes; PostgreSQL хранит метаданные и снимки, не байты фото. API не передаёт SQL или пути файлов от браузера к AI. Внешний текстовый GigaChat из архива можно подключать позже через адаптер, но он не нужен для демонстрации двух методов и не объявляется доступным визуальным анализатором без проверки.

Compose после реализации должен включать: healthcheck БД; одноразовое применение новой SQL-цепочки после готовности БД; readiness backend после миграций; статический frontend с `/api` proxy; volumes `maintenance_pgdata`, `maintenance_photos`, `maintenance_models`. Ошибка миграции останавливает запуск API. `Base.metadata.create_all()` и автоматический импорт старых сметных SQL запрещены проектным решением. Backup/restore демонстрационной БД и фото проверяется до репетиции; `down -v` в процедуру запуска не входит.

## Источники технических свойств

Документация проверена 26.10.2026; решения о применении к FixRate являются проектными выводами команды.

- Область жизни Session и её связь с транзакцией: [SQLAlchemy 2.0 — Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).
- Различие базы и схемы PostgreSQL, изоляция подключений по базе: [PostgreSQL 16 — Schemas](https://www.postgresql.org/docs/16/ddl-schemas.html).
- При оценке модели временные и групповые данные требуют подходящего разбиения: [scikit-learn — Cross-validation](https://scikit-learn.org/stable/modules/cross_validation.html).
- Готовые CLIP-подобные модели сопоставляют изображения с текстовыми классами без обучения на этих классах: [Transformers — Zero-shot image classification](https://huggingface.co/docs/transformers/en/tasks/zero_shot_image_classification). Это свойство не доказывает пригодность модели для приёмки ТО.
