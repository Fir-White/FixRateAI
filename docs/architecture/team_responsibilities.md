## Порядок передачи и изменений

1. Анастасия передаёт команде исходные значения и решения по неоднозначностям; Николай фиксирует границы модели и версий. Параллельно допустимо реализовывать UI/алгоритмы на явно синтетических fixtures.
2. Яна и владельцы вычислительных модулей принимают одинаковые DTO. Изменение статуса/единицы/имени поля требует изменения схемы, примеров, mapping и документации одним комплектом. До передачи запуск проверки контрактов обязателен.
3. Артём и Мухаммад передают pure interfaces и fixtures без сетевой/ORM-зависимости; Яна обеспечивает транзакционный вызов и запись. Блокировки и контроль версии остаются на backend даже при повторном подборе кандидатов.
4. Михаил Видякин и Николай подключают UI к API без собственных альтернативных расчётов сроков. Михаил Егоров проверяет интерфейс/сервер отдельно и сквозной путь на одной сборке.
5. Николай интегрирует результаты, сохраняя владельца каждого дефекта. Подтверждение демонстрационной готовности требует протокола QA и проверки исходных допущений Анастасией.

Архитектурный комплект сам по себе не закрывает реализационные критерии передачи из таблицы. Эти критерии определяют последующую работу, а не объявляют её выполненной.
