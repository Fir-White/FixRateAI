## Противоречия и ограничения

1. **Пустой main и вкладка backend.** Архив, а не открытая вкладка, является источником для аудита старого кода.
2. **Два разных `003`.** Архивные ветки имеют разные миграции под одним номером. Их нельзя собирать в одну цепочку по имени файла. Новая БД ТО будет иметь самостоятельную начальную цепочку; для существующей сметной БД нужна отдельная задача инвентаризации фактически применённых SQL и контрольных сумм.
3. **README отстаёт от кода.** В master README ещё относит файлы фото к будущим карточкам, но `photo_service.py`, storage и endpoint уже существуют. Приоритет факта — исходники, а не список намерений.
4. **JWT не реализован.** Настройки `jwt_secret` не подтверждают наличие входа и проверки токена. Нужна отдельная реализация контроля доступа.
5. **ER и версии схемы расходятся.** Старый draw.io не следует использовать как окончательный источник новой БД. Числа колонок до и после разных `003` также различаются.
6. **Форматы ML и канонического контракта различаются.** Сметный адаптер не заменяет единый формат новых прогнозов.
7. **Excel не задаёт полный исполнимый регламент.** Год, сроки ТО2, смысл трудоёмкости и квалификации неизвестны; подробности и вопросы — в [анализе Excel](customer_schedule_analysis.md).
8. **Нет эксплуатационной выборки.** Excel — план, не журнал фактических состояний/отказов. Прогноз на обученной модели и его достоверность этим файлом не подтверждены.

Git-ветки, старый код и миграции оставлены без изменений. Новые артефакты находятся только в `docs/architecture/`.
