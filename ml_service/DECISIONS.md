### ADR-001: Выбор чистых Python-интерфейсов внутри монолита вместо микросервиса

* **Контекст:** В архивной ветке `master` / `ai/ml-service` ML-модуль проектировался как отдельный сервис на FastAPI с сетевыми вызовами через HTTP.
* **Проблема:** Сетевые накладные расходы, сериализация больших JSON, необходимость оркестрации нескольких контейнеров в Docker Compose (Redis, Celery/RabbitMQ), усложнение демонстрационного стенда при жестком сроке (07.11.2026).
* **Решение:** ML-модули оформляются как **библиотечные Python-пакеты с чистыми функциями** без побочных эффектов. Они вызываются синхронно из backend (сервисов Яны) вне event loop (через `run_in_threadpool` при необходимости).
* **Последствия:** Упрощение архитектуры (один backend + одна PostgreSQL), отсутствие сетевых сбоев между компонентами, максимальная скорость вызова (<20 мс для прогноза).

### ADR-002: Выбор RandomForestRegressor для прогнозирования сроков ТО

* **Контекст:** Требуется модель v1 для предсказания остаточных дней до потребности в обслуживании оборудования ИТП.
* **Рассмотренные альтернативы:**
  1. *Глубокие нейросети (LSTM / Transformers)*: требуют огромных объемов данных телеметрии (десятков тысяч точек во времени), склонны к переобучению на малых выборках.
  2. *LLM (через промптинг)*: недетерминированы, дороги, имеют большие задержки (>1-2 с), склонны к галлюцинациям в числовых вычислениях.
  3. *Линейная регрессия*: не способна уловить нелинейные зависимости наработки и износа.
* **Решение:** Использовать `RandomForestRegressor` (`scikit-learn`):
  - Отличная работа на табличных данных малого и среднего объема (от 50 целевых событий).
  - Высокая устойчивость к выбросам.
  - Нативная оценка важности признаков (`feature_importances_`).
  - Возможность вычисления разброса деревьев (`tree_dispersion`) по перцентилям 10%–90% как меры неопределенности.
* **Последствия:** Быстрое обучение, мгновенный инференс, понятная интерпретируемость для инженера.

### ADR-003: Разделение данных на Набор А (заказчик) и Набор B (synthetic_demo)

* **Контекст:** Исходный файл заказчика `techical_service_schedule.xlsx` содержит лишь план обходов на октябрь без наработки и поломок.
* **Решение:**
  - **Набор А (Реальный)**: При попытке AI-прогноза по оборудованию заказчика система возвращает статус `unavailable` с диагностическим кодом `MODEL_NOT_READY` или `INSUFFICIENT_HISTORY`. Никаких фиктивных прогнозов под видом реальных данных.
  - **Набор B (`synthetic_demo`)**: Воспроизводимый синтетический сценарий (seed=42), где наработка, история и целевая переменная смоделированы; это не реальные наблюдения потребности или отказов.
* **Последствия:** Честная позиция перед заказчиком: мы демонстрируем работоспособность ML-пайплайна, не вводя в заблуждение относительно готовности модели на неподтверждённых исходных данных.

### ADR-004: Локальный CLIP ViT-B/32 для zero-shot оценки чистки

* **Контекст:** Требуется оценить качество выполнения операции 1.4 («Чистка всех узлов и агрегатов») по фотоотчёту «до» и «после».
* **Решение:** Использовать локальные открытые веса `openai/clip-vit-base-patch32` через библиотеку `transformers` (PyTorch).
  - Работа в режиме Zero-Shot Image Classification (без обучения на специализированном датасете ИТП).
  - Сопоставление с текстовыми описаниями чистой и загрязнённой поверхности узлов.
  - Локальный инференс на CPU машины (без обращения к внешним облакам).
* **Последствия:** Полная автономность решения, отсутствие расходов на API-токены, защита персональных данных и фото инфраструктуры заказчика от утечки во внешние сервисы.

### ADR-005: Запрет автономной приёмки работ AI-моделью

* **Контекст:** Может ли AI-модуль автоматически принимать выполненные наряды (`accepted`) или закрывать задачи?
* **Решение:** **Категорический запрет.** AI формирует исключительно техническое заключение [`PhotoReviewResult`](file:///home/handraqw/Projects/FixRate_AI/backend/app/schemas/maintenance.py#L423-L436). 
  - Решение о приёмке или отправке на доработку (`EngineerDecision`) имеет право принимать **только человек — главный инженер или инженер объекта**.
  - Инженер обязан учитывать заключение AI, но может принять работу даже при статусе AI `uncertain` или `not_verifiable`, указав обязательное текстовое обоснование (`reason`) и ссылки на дополнительные доказательства (`additional_evidence_refs`).
* **Последствия:** Исключение аварийных рисков на объектах теплоснабжения. Юридическая и техническая ответственность остаётся на персонале.

### ADR-006: Безусловный вердикт not_verifiable для скрытых операций

* **Контекст:** В регламенте есть операции 1.5 («Проверка точности приборов») и 1.6 («Выпуск воздуха из системы отопления»). Работники могут прикрепить фото манометра или крана Маевского.
* **Решение:** Модуль анализа фото проверяет атрибут `visual_verifiability` в чек-листе. Если значение равно `"not_verifiable"`, модуль **принудительно выставляет вердикт `not_verifiable`**, минуя оценку нейросетью.
* **Последствия:** Устранение риска ложного одобрения: фото циферблата не подтверждает точность поверки прибора, а фото крана не доказывает отсутствие воздушной пробки в контуре.

### ADR-007: Унификация контракта ForecastResult для обоих методов

* **Контекст:** В системе работают два независимых метода: алгоритмический (по формуле регламента) и статистический AI (по истории).
* **Решение:** Использовать строго единый DTO [`ForecastResult`](file:///home/handraqw/Projects/FixRate_AI/backend/app/schemas/maintenance.py#L206-L238).
  - Поле `method` принимает значение `"algorithmic"` или `"ai"`.
  - Все поля (`recommended_date`, `mandatory_due_date`, `uncertainty`, `explanation`, `warnings`, `error_code`, `elapsed_ms`) идентичны по типам и валидациям.
* **Последствия:** Оркестратор Артёма и фронтенд Михаила работают с единообразной структурой, без дублирования DTO и написания сложных адаптеров.

### ADR-008: Канонический хеш снимка и защита от утечки будущего

* **Контекст:** Для честного сравнения методов и аудита требуется гарантировать, что оба метода работали на одном и том же неизменном срезе данных.
* **Решение:**
  - Входной снимок [`ForecastSnapshot`](file:///home/handraqw/Projects/FixRate_AI/backend/app/schemas/maintenance.py#L148-L186) содержит поле `content_sha256`. Хеш считается как SHA-256 от канонического UTF-8 JSON снимка (с сортировкой ключей `sort_keys=True`, разделителями `,`/`:`, без поля `content_sha256`).
  - Все события в истории строго ограничены условием `performed_at <= accepted_at <= as_of`.
* **Последствия:** 100% защита от Data Leakage во времени и невозможность подмены исходных данных между вызовами.
