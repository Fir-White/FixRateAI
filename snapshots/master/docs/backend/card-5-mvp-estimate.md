# MVP: первая работающая смета с AI-заглушками

**Статус:** DONE
**Ветка:** `yana/backend/api`
**Ответственные:** Артём (ML pipeline), Яна (Backend API и PostgreSQL)

## Что реализовано

Backend использует существующий ML Service с mock CV/LLM/RAG и предоставляет:

- `POST /api/v1/estimates/requests/{request_id}` — запуск сквозной обработки;
- `GET /api/v1/estimates/requests/{request_id}` — последняя сохранённая версия;
- адаптацию заявки к JSON-контракту `schema_version=1.0`;
- сохранение `ai_runs`, `ai_results`, дефектов и производных измерений;
- сохранение черновика в `estimates` и `estimate_items`;
- статус `needs_clarification`, если обязательного масштаба недостаточно;
- версии смет при повторном запуске без подмены отсутствующих данных.

Реальные CV, NLP и RAG подключаются на стороне ML Service и не требуют
переписывания Backend-адаптера или расчётного процесса.

## Демонстрационный результат

Для текста:

```text
Трещина на фасаде длиной 3 м
```

mock NLP определяет `facade_crack`, расчётный движок выводит `0.3000 m2`,
а DEMO-расценка `850 RUB/m2` даёт:

```text
255.00 RUB
```

Источник помечен как `DEMO`; эти цены не являются ФЕР/ТЕР и предназначены
только для проверки интеграции.

## Пользовательские сценарии

### 1. Успешная заявка: трещина фасада

В заявке укажите описание с типом дефекта и длиной:

```text
Вертикальная трещина на фасаде здания, длина 3 м
```

Ожидаемый результат:

- статус запуска `completed`;
- дефект `facade_crack`;
- объём `0.3000 m2` по демонстрационной формуле `длина × 0.1 м`;
- расценка `DEMO-FACADE-CRACK-01`;
- итоговая стоимость `255.00 RUB`;
- сохранение запуска, результатов модулей и версии сметы в PostgreSQL.

### 2. Заявка без обязательного размера

Пример:

```text
Обнаружена трещина на фасаде здания
```

Система не должна угадывать длину. Ожидаемый результат:

- статус `needs_clarification`;
- `estimate = null`;
- вопрос с кодом `MISSING_CRACK_LENGTH`;
- поле уточнения `length_m`, единица `m`.

После добавления измерения через PATCH заявки можно повторно запустить
формирование сметы.

### 3. Скол плитки

Пример:

```text
На крыльце откололось 4 плитки облицовки
```

Ожидаемый результат:

- дефект `tile_chip`;
- площадь `0.3600 m2` (`4 × 0.09 m2`);
- расценка `DEMO-TILE-CHIP-01`;
- итог `432.00 RUB`.

Если количество или площадь не указаны, система возвращает уточнение
`MISSING_TILE_COUNT` и не создаёт смету.

### 4. Протечка на парковке

Пример:

```text
В подземном паркинге протечка, мокрое пятно площадью 10 м2
```

Ожидаемый результат:

- дефект `parking_leak`;
- расчётная площадь `11.5000 m2` с демонстрационным коэффициентом;
- расценка `DEMO-PARKING-LEAK-01`;
- итог `17250.00 RUB`;
- статус `needs_review`, поскольку причина протечки требует проверки.

### 5. Неизвестное или недостаточное описание

Если описание не содержит поддержанного типа дефекта, например:

```text
Обнаружена пробоина в плите у реки
```

система не должна выбирать случайную формулу или расценку. ML Service
возвращает:

- статус `needs_clarification`;
- `estimate = null`;
- вопрос `NO_DEFECT_DETECTED` с просьбой описать повреждение подробнее;
- предупреждение о том, что дефект не распознан.

Это штатный результат, а не ошибка PostgreSQL или расчётного движка.

### 6. Повторный запуск

Повторный вызов `POST /api/v1/estimates/requests/{request_id}` создаёт новую
версию сметы. Предыдущая версия не перезаписывается, что позволяет сравнить
результаты запусков и сохранить историю обработки.

### 7. Просмотр результата

`GET /api/v1/estimates/requests/{request_id}` возвращает последнюю успешно
сформированную версию. Если для заявки были только уточнения или неуспешные
запуски, endpoint корректно отвечает `404` с сообщением, что смета ещё не
создана.

## Ограничения текущих заглушек

### CV

- CV-заглушка не распознаёт реальные фотографии как полноценная модель;
- сценарии детекций заранее подготовлены и ограничены тестовыми типами;
- бинарная загрузка и хранение файлов остаются отдельным storage-слоем;
- отсутствие доступного изображения не даёт оснований выдумывать дефект.

### NLP/LLM

- mock NLP использует простые эвристики и ключевые слова, а не семантическую
  модель;
- поддерживаются только `facade_crack`, `tile_chip` и `parking_leak`;
- формулировки, синонимы, опечатки и новые виды повреждений могут не
  распознаться;
- числа извлекаются только из ограниченного набора форматов (`м`, `метра`,
  `м2`, `шт` и близкие варианты);
- неизвестный дефект переводится в `needs_clarification`, а не в
  автоматически рассчитанную смету.

### RAG и расценки

- каталог содержит только три демонстрационные расценки;
- источник `DEMO` не является ФЕР/ТЕР и не предназначен для реальных смет;
- применимость норм проверяется на тестовом каталоге, без полноценного
  нормативного поиска и экспертной интерпретации;
- цены, состав работ и коэффициенты условны.

### Расчётный движок

- реализованы только формулы пилотных сценариев;
- расчёт выполняется по тестовым измерениям и не заменяет обмеры;
- материалы, доставка, налоги, накладные расходы и другие реальные статьи
  затрат не рассчитываются;
- результат является предварительной ВОР и требует проверки сметчиком.

### Backend и эксплуатация

- используется demo-пользователь вместо JWT-аутентификации;
- API синхронно ждёт ответ ML Service;
- повторный запуск создаёт новую версию, но автоматического согласования нет;
- полноценное хранение бинарных фото, фоновые очереди, мониторинг и retry
  находятся за пределами MVP.

## Кодировка демо-данных

Поля `building_type` и `wall_material` входят в `input_snapshot` сметы.
Если seed применить из клиента с несовместимой кодировкой, PostgreSQL может
сохранить `?` вместо кириллицы, после чего Swagger будет честно показывать
повреждённые значения. Это не меняет формулу и итог демонстрационного
расчёта, но является дефектом качества входных данных.

В `db/002_seed_demo.sql` для этих полей используются PostgreSQL `U&`-литералы,
поэтому повторное применение seed восстанавливает значения независимо от
кодировки консоли:

```powershell
docker exec -i fixrate_postgres psql -X -v ON_ERROR_STOP=1 `
  -U fixrate -d fixrate < db/002_seed_demo.sql
```

После повторного запуска проверьте через Swagger новую заявку или новый запуск:

```json
"building_type": "жилое",
"wall_material": "панель"
```

Старые `input_snapshot` уже сохранены как история и автоматически не
переписываются; для проверки нужно сформировать новую версию сметы.

## Локальный запуск

Из корня проекта:

```powershell
$env:POSTGRES_PORT="5433"
docker compose up -d

cd ml_service
..\venv\Scripts\python.exe -m uvicorn app.main:app `
  --host 127.0.0.1 --port 8001
```

Во втором окне:

```powershell
cd backend
..\venv\Scripts\python.exe -m uvicorn app.main:app `
  --host 127.0.0.1 --port 8003
```

Откройте Swagger:

```text
http://127.0.0.1:8003/docs
```

Сначала создайте заявку через `POST /api/v1/requests`, затем вызовите
`POST /api/v1/estimates/requests/{request_id}`. Результат содержит `run`,
`estimate.total_cost`, позиции, формулу и источник каждой расценки.

## Приёмочная проверка

```powershell
$env:DATABASE_URL="postgresql+psycopg://fixrate:ChangeMe-local-only@127.0.0.1:5433/fixrate"
.\venv\Scripts\python.exe -m pytest -q backend\tests
.\venv\Scripts\python.exe -m pytest -q ml_service\tests
```

Проверены:

- успешный запуск и сохранение результата;
- получение последней сметы;
- повторный запуск;
- `needs_clarification` без выдуманного объёма;
- стабильные ошибки API;
- сохранение источников, формул и итоговой суммы.

## Ограничения MVP

- бинарная загрузка фото остаётся отдельным storage-слоем;
- ML Service работает на mock-провайдерах;
- расценки демонстрационные;
- JWT ещё не подключён, используется demo-пользователь;
- предварительная смета требует проверки сметчиком.
