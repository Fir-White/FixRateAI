## 1. Проект простыми словами

**FixRate AI** — помощник инженера-сметчика, не замена человеку.

Сейчас заявка на ремонт живёт в трёх местах: фото отдельно, текст отдельно, паспорт дома отдельно. Сметчик 30–90 минут ищет расценки в ФЕР/ТЕР и прайсах. Ошибка выбора расценки бьёт 15–20% сметы. Житель ждёт оценку днями.

Система принимает фото + описание + характеристики здания и возвращает **черновик ведомости объёмов работ (ВОР)**: работы, объёмы, материалы, расценки **со ссылкой на источник**, предварительную сумму. Сметчик проверяет, уточняет объёмы, подтверждает.

**MVP** — не «все виды ремонта страны», а несколько согласованных сценариев, которые можно показать и прогнать повторно. Полнота ФЕР/ТЕР не обещается.

**Главный принцип:** нейросеть распознаёт и подбирает кандидатов. **Деньги считает детерминированный код.**

```
фото + текст → CV + NLP → дефекты и параметры
    → Hybrid RAG (поиск норм) → валидация
    → расчётный движок → черновик сметы → человек
```

До готовности CV/NLP/RAG те же шаги идут через **заглушки с тем же контрактом** (карточка 4, lead Артём).

## 3. Зафиксированные технические решения

Яна не знала ответы команды. Ниже — **принятые по умолчанию**. Если тимлид скажет иначе, менять решение явно в этом разделе, не молча в коде.

### 3.1. Миграции и SQL (вопрос 2)

**Как лучше:** один источник схемы — **DDL архитектора**, не модели SQLAlchemy.

**Пока SQL не отдан (это текущий факт):**

- карточку 1 делать без БД;
- локальный `docker-compose` с `pgvector/pgvector:pg16` можно добавить сразу, **без init-скрипта с выдуманными таблицами**;
- папка-задел `db/` с `README.md`: «положите сюда официальный SQL»;
- **не** заводить свой Alembic с первой ревизией «из головы».

**Когда SQL появится:**

1. Положить файл в `db/` (например `db/001_init.sql`) — канон.
2. Применять его к пустой БД (entrypoint Docker или команда в README).
3. Модели SQLAlchemy срисовать 1-в-1 с DDL и specification.md.
4. Alembic подключать **только если архитектор так договорится**, и первая ревизия должна повторять уже существующий SQL, а не конкурировать.

**Где узнать, если нужно сдвинуть карточку 2:** комментарий в YouGile на карточке 2 тимлиду: «нужен DDL v2 / кто владеет миграциями / путь в репозитории». Пока тишина — статус BLOCKED, не выдумывать 18 таблиц.

### 3.2. Sync vs async (вопрос 3) — выбрано

**Стек: FastAPI + SQLAlchemy 2.0 sync + psycopg3 + обычные `def` эндпоинты.**

Почему:

- команда учебная, дедлайны дни, а не месяцы;
- sync-сессия проще в транзакциях «заявка + фото + смета»;
- меньше класса ошибок event loop;
- FastAPI сам кладёт sync `def` в threadpool — event loop не блокируется, если не писать sync-код внутри `async def`.

Правило: роуты, которые ходят в БД, объявлять как `def`, не `async def`.  
HTTP к будущему ML: `httpx.Client` с timeout в адаптере.

Асинхронный SQLAlchemy не начинать «на всякий случай».

Python: **3.12**. Зависимости: `pyproject.toml` + lock по возможности, иначе `requirements.txt` и `requirements-dev.txt`.

### 3.3. Авторизация (вопрос 4) — достойный MVP, не гигант

Полный SSO не нужен. Без авторизации MVP слабый: в схеме обязательны `created_by`, роли `operator` / `estimator` / `admin`, проверка сметы человеком.

**К 29.10 должно быть:**

- таблица `users` (когда появится DDL);
- `POST /api/v1/auth/login` — email + пароль → JWT;
- пароль только как hash (`password_hash`, bcrypt или argon2);
- `Authorization: Bearer <token>`;
- зависимость `get_current_user`: неактивный пользователь не входит;
- роли: operator создаёт заявки и грузит фото; estimator читает и (минимально) меняет статус сметы на review/approved; admin — seed;
- в README три демо-учётки, пароли только в `.env.example` как `ChangeMe-...`, не как боевые.

**Не в карточке 1.** Каркас только резервирует `JWT_SECRET`, `JWT_EXPIRE_MINUTES` в config.

**В карточке 3** (заявки) логин уже нужен, иначе нечем заполнить `created_by`. Если DDL пользователей ещё нет к 23.10 — временный fallback: один seed-пользователь в памяти **только как BLOCKED-костыль**, и это писать в карточке честно. Целевой путь — JWT по таблице `users`.

Не делать: OAuth, refresh-cookie карусель, Captcha, SSO Сбера, email-подтверждение.

### 3.4. Фото (вопрос 5) — пока локальный диск

Команды нет — берём диск, но **за адаптером**.

- `STORAGE_DIR` из env, по умолчанию `backend/var/storage` (в `.gitignore`).
- Каталоги `originals/` и `processed/`.
- Имя на диске = безопасный `storage_key` (UUID + расширение), не `original_filename`.
- Выдача файла только через `photo_id` в БД, не через путь клиента.
- Лимит по умолчанию **10 МиБ**, форматы **jpeg / png / webp**, проверка реального содержимого, не только расширения.
- Docker: volume на `STORAGE_DIR`, чтобы файлы переживали перезапуск контейнера API.

MinIO/S3 не внедрять, пока не появится общий сервер. Интерфейс адаптера (`save`, `open`, `delete`) оставить заменяемым.

Карточка 5 — реализация. Карточка 1 — только переменная env.

### 3.5. Оркестратор (вопрос 6)

Пока неизвестно устройство Артёма — **протокол в процессе FastAPI**.

```
service.process_request(request_id)
    → собирает snapshot
    → pipeline.run(snapshot)   # Protocol, impl: StubPipeline, позже ArtemPipeline
    → DTO (defects, rates, need_clarification, line_items)
```

### 3.8. ФЕР/ТЕР в репозитории (вопрос 9)

**Правильно так:**

Нормативные сборники ФЕР/ТЕР — охраняемые издания. Студенческий репозиторий **не место** для выгрузки сканов, Excel «скачанных из интернета» и полного корпуса расценок.

Для MVP в git:

- несколько строк `norm_sources` с `source_type=DEMO`;
- несколько `rates` с вымышленными, но правдоподобными ценами;
- в API и в смете явно видно, что источник демонстрационный (поле + текст в OpenAPI);
- утверждение сметы с DEMO не выдавать за «нормативую методику» (когда дойдёте до статусов — помечайте).

Настоящие фрагменты, если заказчик/аналитик даст по лицензии — **вне git** (локальный диск, закрытый контур), в `.gitignore`. RAG и pgvector подключат ML, когда появятся легальные тексты.

Это и юридически спокойнее, и честнее на защите: «пилот на ограниченном DEMO-прайсе, не промышленный ФЕР».

## 5. Модель данных — только то, без чего нельзя писать API

Полные поля — в `docs/database/specification.md`. Здесь шпаргалка для ассистента.

- UUID, `TIMESTAMPTZ`, деньги `NUMERIC`.
- Файлы **не** в БД, только `request_photos.storage_key` и метаданные.
- Составные FK `(entity_id, request_id)` — нельзя связать фото заявки B с дефектом A.
- Размер дефекта (`defect_measurements`) ≠ объём работы (`estimate_items.quantity`).
- Сметы версионируются: правка = новая строка `estimates`, `UNIQUE(request_id, version)`.
- Статус заявки, статус AI-запуска и статус сметы — **три разных** перечисления. Не использовать одно поле на всё.

**Заявка:** `created | processing | needs_clarification | ready_for_review | closed | cancelled | failed`  
**AI run:** `pending | running | completed | failed | needs_clarification`  
**Смета:** `draft | needs_review | approved | rejected | superseded`

Бизнес-правило приложения (SQL его не проверяет): у заявки есть **непустое описание или хотя бы одно фото**.

`updated_at` у заявки обновляет приложение.

### Карточка 1 — каркас (дедлайн 20.10, СЕЙЧАС)

**Цель:** на чистом окружении встаёт сервер, видны health и Swagger.

**Шаги, с которых начинать разработку:**

1. Убедиться, что нет уже начатого `backend/` — не дублировать.
2. Python 3.12, venv, FastAPI, Uvicorn, pydantic-settings, pytest.
3. `app/main.py`: создать приложение, подключить логирование, middleware `X-Request-ID` (принять заголовок или сгенерировать UUID, вернуть в ответе и писать в лог).
4. `GET /health` → `200 {"status":"ok"}`. Префикс `/api/v1/health` допустим, тогда в README указать канон. Рекомендация: `GET /health` снаружи и дубль не нужен; бизнес-API — под `/api/v1`.
5. Единый JSON ошибок, внутренний traceback клиенту не отдавать.
